# Changelog

This repository uses an `x.y.z` release scheme.

- Increment `x` for breaking changes.
- Increment `y` for user-facing non-breaking changes.
- Increment `z` for backend-only non-breaking changes that do not affect users directly.

Every stage or production deploy cuts a version: see "Cut a release" in [docs/development.md](docs/development.md).

## Unreleased

### WooCommerce webhooks no longer move the sweep cursor (backend / sync)

- **Fixed: a delivered webhook could hide an older missed order or product from the sweep for good.** In poll mode every admitted order webhook stamped `last_wc_order_sync_at` to now, and every successful product webhook stamped `last_wc_product_sync_at` to now. If order A changed and its webhook was missed, then order B's webhook arrived, the cursor jumped past A and the next sweep asked WooCommerce for changes after it, so A was never read. The sweep now owns both cursors: only a sweep that ended cleanly on an empty page writes them (read-start less 120 seconds, never backwards). A webhook writes its own stamps instead, `wc_order_webhook_last_processed_at` and `wc_product_webhook_last_processed_at`, which nothing reads as a sweep position.
- Nothing else depended on the webhook moving the cursor: the read-sync liveness stamp, the refusal watermark and the withdrawal-recovery marker are separate settings, and webhook-primary mode keys off `wc_*_webhook_last_received_at` and the reconcile cursors. One visible effect: after a long webhook-primary spell, the first poll sweep reads from its own last position instead of from the last webhook, so it re-reads the gap (idempotent; bounded by the page-walk ceiling). The Sync page's "Last order intake" / "Last product intake" now show the last sweep position rather than the last webhook.
- **Webhook-primary mode keeps the poll cursors close.** A clean reconcile now also carries its position to the poll cursor (atomic max, in the same commit; orders only when the reconcile's resolved status list contains the poll's), so a long webhook-primary spell no longer leaves the first poll afterwards a window larger than the page-walk ceiling. This replaces the "re-reads the gap" side effect above.
- Both new keys are cleared by the operator reset and are machine-managed (not writable from the settings form). No migration.

### WooCommerce pull cursors are taken at read start, not at commit (backend / sync)

- **Fixed: an order modified while a sweep was finishing could be skipped for good.** The order sweep stamped its `modified_after` cursor with the time it COMMITTED, after the final empty-page read. An order changed between that read and the stamp was never read by the run yet sat behind the next sweep's window, and with its webhook missed it was never processed. Every WooCommerce pull cursor (order poll and reconcile, product poll and reconcile, the initial import's completion stamp) is now the time the run STARTED, before its first WooCommerce read, less a 120 second overlap (`WC_PULL_CURSOR_OVERLAP_MS`, covering second-precision `date_modified` and clock skew between the IMS and WooCommerce hosts). Re-reading the overlap is safe: order import updates an order it already holds and product sync upserts by SKU.
- A commit never moves a cursor backwards: it writes the later of the stored value and the new candidate, in one atomic upsert (`GREATEST` semantics under the row lock), so two overlapping sweeps cannot move it backwards. The selection-widening and refusal-watermark rewinds are unchanged (they lower only where a run reads from). The conditional commit under the advisory lock and the read-sync liveness stamp (which stays the real commit time) are unchanged.
- No migration.

### EU VAT: an operator can settle a gift-card line the store left `unknown`

- **Fixed: after the gift-card cut-in, an order with a custom line or a deleted-product line was refused for good.** The plugin writes `unknown` on such lines and IMS treated that as missing, so the order was refused (`gift_card_flag_missing`) and re-importing could never clear it. The cut-in (`eu_vat_gift_card_flag_cut_in`) should not be set until this is deployed.
- **Now an operator answers per line.** **Sync > Exceptions > "Gift card or not? Order lines the store could not settle"** lists the held orders and the lines the refusal named; **Gift card** or **Not a gift card** records the answer with who and when (sync permission, fresh sign-in; the history is in the activity log). The regime builder uses the answer for that line only where the store left it unsettled: a flagged `yes`/`no` is never overridden, and an unanswered line keeps refusing (no default). Re-import the order afterwards and its held invoice is released.
- An answer is bound to the store it was given for (new column `store_identity`, the same normalised store URL the tax-rate mappings use) and is deleted when the store connection is changed to another store and by the operator reset. The stamp re-reads the answers under the order lock and writes nothing if one changed since the regime input was built.
- The section is filtered in the database before it is paged (50 orders a page, with Previous / Next), its heading shows the true count, and the count is part of the Sync > Exceptions badge, so a backlog is never hidden behind unrelated refusals.
- The refusal now says where to answer, and the parked refusal records the line ids. Migration: one new table, `eu_vat_gift_card_line_resolutions` (additive). Not done on purpose: no automatic "not a gift card" rule from the product, because IMS holds no gift-card marker on products to prove it.

### WooCommerce reconcile: a failed held-invoice sweep read answers 500 (backend / operations)

- **Fixed: invoices awaiting release could go unprocessed while the `wc-reconcile` heartbeat stayed green.** The held sales-invoice release sweep returned plain counters when the held-invoice queue read, or the order read behind it, threw, so the run read as ok. It now returns `heldSalesInvoices.readError` for either read, and for a numbered invoice whose hold lookup or queued-invoice confirmation threw (that was read as an absent hold or as a tolerated stuck invoice), the cron outcome mapping counts it as a failure, and the route answers 500 (and records `failed`). A database read cannot be refused by the outbound-write hold, so it is never held.
- No migration.

## 4.1.1 - 2026-11-14

### Fixed: the WooCommerce order sweep could not commit

- **Every clean order-sweep commit failed** with `Failed to deserialize column of type 'void'`: the commit took its per-cursor advisory lock with `$queryRaw`, and `pg_advisory_xact_lock` returns `void`, which Prisma cannot read back. It now uses `$executeRaw`, as every other advisory lock in IMS does. Seen on stage after 4.1.0; nothing was lost (the sweep re-reads its window), but the cursor and the liveness stamp did not advance. Unit tests mocked the call, so a source test now forbids `$queryRaw` for any `pg_advisory*` lock call.

## 4.1.0 - 2026-11-14

Numbered 4.1.0 (not 5.0.0): nothing in this release needs an operator action on upgrade. The additive migrations apply with the normal deploy, the new Sync > Exceptions sections are things to watch, and the EU VAT credit-note work is built and switched off.

### Ops notes

- **Cron heartbeats can now go red on a real failure.** A cron route that genuinely failed used to answer HTTP 200, so its Healthchecks heartbeat stayed green. It now answers 500, and the crontab wrapper's `curl -sf` reports the job as failed. Nothing has to be changed for this to work; expect that a heartbeat which was silently green over a failing job may turn red after the deploy, and treat that as a real failure to look at. A stage installation with no outbound grant stays green by design (held writes answer 200).
- **Watch Sync > Exceptions** for the new "WooCommerce orders — blocked from import" section: it lists orders that need a cause fixed, such as an unmapped tax rate.

### WooCommerce: orders blocked by a guard are recorded, so the initial import cannot strand them

- **Fixed: the initial order import could complete over orders it had refused, and those orders were never imported.** An order blocked by the tax-rate fallback guard (a line would use the order default tax rate because its WooCommerce rate is not mapped) or by the coupon guard was counted as a per-order error and outvoted by the orders that did import. The pass stamped `wc_initial_import_completed` and moved `last_wc_order_sync_at` to now, so the `modified_after` sweep started after the blocked orders and they were only ever imported if someone changed them in WooCommerce. (Seen on stage: 12 imported, 265 blocked, outcome complete.)
- **Now every guard block is durable.** The order is written to the by-id refusal queue (the one the 15-minute drain re-reads) with the guard's own sentence, and listed under **Sync > Exceptions** as "WooCommerce orders — blocked from import", with the order number, the reason and what to fix. Fix the cause (map the tax rate) and the drain imports the order by id. The guards themselves are unchanged and nothing is imported in a degraded way.
- **The initial import completes over recorded blocks** (the progress card and completion message show the blocked count, and the notification is a warning), and **holds exactly as before if a block cannot be recorded** (the "Import held" outcome).
- **A permanently blocked order no longer fails the ongoing sweep forever.** Once recorded, the poll and reconcile sweeps treat it as a resolved skip, advance their cursor and stamp their liveness, and the webhook acknowledges it; an unrecorded block still holds the cursor. A block that does not touch the "Import order statuses" selection no longer feeds the cursor-rewind watermark, and the guard's ERROR activity entry is written when the order is first recorded rather than on every re-check.
- **Fixed: data retention could delete the only record of a refused or blocked order.** A PENDING row of the by-id refusal queue (the pre-existing status and currency reasons as well as the new guard blocks) has no order id, so the age sweep did not protect it, and the drain only keeps it young while sync runs. Retention now never deletes a PENDING refusal row, whatever its age; a resolved one expires as before. Erasure updates such rows in place and never deletes them, the operator reset deliberately wipes the table together with the sync cursors, and the activity-log cleanup does not touch it.
- No migration (the existing `shopping_sync_logs` queue carries the new reasons). Accepted limit: the drain re-reads at most 50 queued orders per 15-minute run, so a very large blocked set is worked through over several runs.

### Cron routes answer non-2xx when their run failed (backend / operations)

- **A failed cron run no longer answers 200.** Every route under `app/api/cron/` now answers through one shared mapping, so the crontab wrapper's `curl -sf` (and the Healthchecks heartbeat behind it) sees a failing run as a failing job, on stage and in production. Before, `wc-reconcile` could record `failed` every hour while its heartbeat stayed green.
- **Four outcomes: ok, skipped, held, failed.** ok, skipped (a plugin or sync switched off, maintenance) and held answer 200; only failed answers 500. Held means the only problems were writes the outbound-write hold refused, which is the normal state of a stage installation (no outbound grant), so stage heartbeats do not go red by design. A held write next to a genuine failure is failed. Held writes are recognised by the hold's own reference, not by wording a destination could send.
- **Each route declares how its own result reports failure.** An entry per route in `lib/ops/cron-outcomes.ts` covers the shapes the routes really return: an uppercase `FAILED` or `PARTIAL` status with an error count (WMS order reconcile, Mintsoft stock, despatch, product, bundle and returns sync), counts of failed items (WMS order push and status, refund reservation release, e-mail outbox, Mintsoft webhook sweep, HS classification, observed lead times), `success: false`, and error lists. The WMS order push, WMS despatch and Xero accounting sweeps also report the writes the hold refused (`outboundHeld`) so those do not count as failures. A run a route calls failed is now recorded failed too (observed lead times recorded `completed` with failures).
- **Failures reported apart from the error list count too.** `wc-reconcile` counts permanent product import conflicts (`products.permanentErrors`), and the e-mail outbox counts parked, conflicted and unresolved-after-send rows.
- **A daily batch that finds another run holding its lock is a skip, not a failure.** It used to report an error text and would have answered 500; it now reports `skipped` with the reason `already-running`. The held count is subtracted only from the counter it belongs to, so a dead-lettered push is still a failure when pushes were also held.
- **Every producer that reports `outboundHeld` counts held refusals on every path.** The default Xero accounting outbox (main, retry, catch and follow-up paths), the WMS order push (create, update, hold, cancel and compensation), the WMS despatch sweep (read from the thrown class before the text is scrubbed) and the Mintsoft product and bundle verifies now count a write the hold refused in `outboundHeld`, so a stage installation whose destination is held does not turn its heartbeat red.
- **Failures a route or producer catches and carries on from now reach the result.** A failed remote backup upload (and a failed retention purge), a throwing accounting-sync sweep (back-reference repair, credit-note allocation re-enqueue, landed-cost journal outbox drain, provisional-refusal reconciliation), failed storefront status pushes in the WMS order status sweep, failed refund stock-correction queueing in the WooCommerce reconcile, TrackShip lookups that were refused or unanswered each add an explicit failure field, held-aware, so the run answers 500 instead of 200.
- **A new failure field in a producer fails CI until it is mapped or justified.** Each route's mapping now takes its producer's real result type, and a test reads those types with the compiler and requires every failure-like field (at any depth) to be consumed by the mapping, declared a breakdown of a parent count, or ignored with a reason. This closed three gaps: the exchange-rate job's pending order, receipt and orphan-receipt retry failures, the accounting revaluation's refused enqueues, and the storefront webhook inbox's dead-lettered events and reallocation sweep per-order errors now count as failures. A Mintsoft content failure (counted both in `errors` and `content.errors`) with the write held reads as held, not failed.
- **A skip never hides a failure, and the admission-refusal drain separates real failures from expected waits.** A run that says it skipped (accounting sync with Xero off, for instance) but also ran a sweep that failed now answers 500; every consumed failure field is tested with and without the route's skip state. The WooCommerce admission-refusal drain now counts a failed by-id read or import as `failed`, and keeps the expected states (the order is gone from the store, the first-import lock was busy, the withdrawal screen could not decide yet) as `unresolved`.
- **Two more edge cases.** A held WMS create whose only record could not be written (`shadowUnrecorded`) now fails the run, and the failure-field census name pattern was widened (unrecorded, unwritten, lost, missing, abandon, stale, mismatch, drift, invalid, denied, timeout, unavailable) so such names are found. The WMS order status sweep no longer counts "no storefront connector is runnable" (the plugin is off on purpose) as a failed push; it counts it as skipped (`pushSkipped`).
- **An invoice-documents sweep that stopped early fails the run, whatever it stored.** The sweep stops on an unexpected exception, a ledger refusal or rate limit, or three fetch failures in a row; with `stored` above zero the route used to answer 200. A non-null `stoppedEarly` is now failed (held when the ledger refusal is the outbound-write hold), and a document that failed this run also fails it. The recorded `cron_runs` status and the response now both come from the one mapping, so they cannot disagree. A rate-limit stop is failed, not skipped: the sweep's stop reason does not separate a rate limit from a refusal, work was left undone, and the next tick retries it anyway, so the 500 costs only an alert.
- **Progress no longer masks a failure in the census.** Every consumed failure field is also probed against a busy successful run (every progress counter, at any depth, above zero), and the failure-name pattern gained stoppedEarly, aborted, halted, interrupted, truncated and capped. Newly found and declared: `invoice-documents.stoppedEarly` (consumed), `invariant-check.reports.inventory.truncated` (ignored: the readiness gate fails on it) and `wc-reconcile.stock.sync.aborted` (ignored: a refused stock push is a by-design skip that leaves the pass due). The accounting revaluation's probes now start from a successful run, so `error` and `refused` are probed on their own.
- **A refusal at a redirect hop is a failure, not a hold.** The transport also throws the hold's error class at a redirect hop, after the first write already went out (`nothingSent` is false there). The cron runner and the reallocation sweep route now treat a thrown hold as held only when it proves nothing was sent; every other thrown-hold check in the producers already did. Hold text is unaffected: a hop refusal carries a different prefix and a `maybe-sent` reference, so it never reads as held.
- **A WMS order status sweep whose presence probe threw now fails the run.** The result carries `probeFailures` (probes that threw), separate from the expected unresolved states (no probe, order present without a readable status), which only withhold the read-sync stamp. The mapping consumes it and the census declares it.
- **A list cut for display never decides held or failed.** The WMS order status sweep listed only the first 20 push errors, so twenty held pushes followed by a genuine failure read as held (200). The sweep now returns whole-batch counts, `pushFailures` (genuine) and `pushHeld`, and the mapping reads `pushFailures`; the text list is display only. Every other cap on an error list in a cron producer was checked: the WooCommerce reconcile's `stock.errors` (cut at 10) keeps the whole result under `stock.sync.errors`, which the mapping reads, and the remaining caps are activity-log metadata or the manual push's progress record, not cron results. The census probes every consumed error list with 120 held errors followed by one genuine one.
- **A failure a call returns is no longer thrown away.** The FX refresh ignored the result of the connector push fan-out, which returns a WooCommerce push error (and logs it FAILED) without throwing, so the fx-rates cron answered 200. The refresh now carries `connectorPushFailures` (and `connectorPushHeld` for pushes the outbound-write hold refused, which stay 200) and `pendingWcOrderRetryFailures` (the retry of orders waiting for rates threw) into its result; the mapping reads both failure counts. The WooCommerce reconcile likewise carried only a throw of the refund stock correction queueing, not the per-refund `failed` count it returns; that count now reaches the result. A new test reads every cron route's module graph and fails on any other call that discards a failure-carrying result unless it is justified.
- **Orders newly parked by the WMS order push now fail the run.** An order whose payload cannot be built (parked VALIDATION_FAILED) or whose dispatched create has no recorded outcome (parked AMBIGUOUS_CREATE) is never retried by the create pass, so the run that parks it answers 500 (`validationFailed`, `createClaimParked`). Both are counted once, on the transition, never for the backlog, so the next healthy sweep is green again; the push recovery view and the production preflight keep showing the parked orders.
- **A swallowed throw in the WMS order push now fails the run.** A withdrawal-fence check that threw (`fenceCheckErrors`), a create-claim transaction that threw (`claimErrors`) and a recovery-pass link write that threw (parking or releasing a held link, re-queuing a revalidated order or a parked create, binding a parked create: `linkWriteErrors`) skipped the order and answered 200. Each is now counted and fails the run; an ordinary fence refusal or a claim another worker won is still a normal skip. A new test reads every cron route's module graph and fails on any other catch clause that neither reports its failure nor is justified.
- **A failed storefront stock enqueue after a stock change now fails the cron run.** After an applied Mintsoft alignment (an align-down leaves the store advertising a higher quantity: an oversell window), a reallocation pass and a booked-in receipt, a failed enqueue was logged and dropped; the daily stock reconcile is windowed and conditional, so it is not a dependable backstop. The Mintsoft stock sync, the reallocation sweep and the booked-in sweeper now count `stockEnqueueFailures` (and `stockEnqueueHeld` for an enqueue the outbound-write hold refused, which stays 200) and their cron mappings read it. Two more windows of the same kind were closed: a WooCommerce product webhook whose stock correction threw answered 200 (it now answers a retryable 500, which the webhook inbox retries and counts), and an imported order whose sales invoice could not be queued was recorded as imported with nothing to post it. That import is now a failed import for every caller (the order poll, the FX retry, the admission drain, the withdrawal sweep and the webhook, which the inbox retries): it leaves a FAILED sync row, and the FX retry keeps its pending row instead of marking it synced. And it no longer leaves the invoice without a retry: the invoice payload the import built is parked as a held sales invoice, which the WooCommerce reconcile's release sweep queues through the same enqueue (same idempotency key on order and invoice number) once the ledger row is confirmed. A new nullable column, `sales_orders.sales_invoice_owed_at` (additive migration, no backfill), records that an invoice is owed from the transaction that commits an imported order the import will invoice until the transaction that queues the invoice or parks it clears it; a redelivery of the order never queues a second invoice and never reads as success while the mark is set and neither a held invoice nor a SALES_INVOICE row (in any status) stands for it, even if the enqueue, the park and the failure log all failed. Orders imported before this change have the column unset and behave as before. This closes the missing-invoice follow-up.
- **Nothing else recorded changes.** `cron_runs` still shows `failed` for a held-only run, with the held texts as the reason. Routes that did not write a run row are now classified from their result by the same rules; `accounting-fx-revaluation` now answers 500 (was 400) when the revaluation does not succeed. A test reads every cron route and fails if one builds its own response. The contract is in `docs/installation.md` (Cron Jobs).

### WooCommerce order sweep no longer fails when the withdrawal plugin is not active

- **The order poll and reconciliation now skip an EU withdrawal status the store has not registered, instead of failing the whole run.** WooCommerce refuses any order query naming a status it does not know, so a store without the WebToffee EU Order Withdrawal Button plugin made every sweep fail and import nothing. IMS now reads the store's registered order statuses once per run and drops only the unregistered withdrawal statuses, with a WARNING in the activity log (at most every six hours) naming the plugin and saying withdrawal requests are not seen until it is active. A status you ticked under "Import order statuses" (or `completed` on reconciliation) that is not registered still refuses the run with an error; if the registered statuses cannot be read, nothing is dropped.
- **Re-activating the plugin cannot skip orders.** While a withdrawal status is skipped, IMS records only that it was. The first run after the plugin returns reads every order currently in a withdrawal status (no date limit), imports each the normal way, and only then clears the record; a failed read holds the run and is retried.

### EU IOSS / VOEC / DDP credit-note treatment (built and switched off: behind the Sales Invoices switch)

- **Added: the EU VAT treatment of a sales credit note** (`lib/domain/accounting/eu-vat-credit-note.ts`, pure; wired by `lib/domain/sales/eu-vat-credit-note-treatment.ts`, called by the refund hand-off that every refund, whole-order reversal and accounting retry goes through). A credit note on a scheme order takes the regime and VAT account from the order's write-once stamp, never decided again; goods and shipping go on the type the INVOICE was posted on (recorded with the stamp, snapshotted on the refund line; a stamp that never recorded it is a refused row posted by hand), a refunded landed-cost fee on 232 on No VAT (only the fees the refund touches), ONE VAT line carries the refund's own tax on the stamped account on No VAT, and the credit note totals the refund exactly, never a store-credit line. A scheme order with no stamp (imported before the switch was on) gets a refused credit-note row that is never sent and is settled by hand on /sync after the credit note is posted in Xero; the Sync Exceptions hand-recording of a parked refund passes the WooCommerce gross, and a refund with none totals its own recorded amounts rounded once; a WooCommerce refund whose tax is booked on rate 182 (EAS re-pricing) is parked for manual recording in this release.
- **The invoice treatment now honours the stamp's recorded posting type** (a rate mapping moved to another zero-rated type after the order was stamped refuses the invoice instead of posting it on a type a credit note would not reverse), and an unstamped order is recognised as a scheme order by an IMS-queued treated invoice before the rates' current mapping (accepted limit for pre-cut-over orders documented in the help).
- **Added: the posting type and the stated gross are snapshotted** on the refund (additive migrations `20261113090000_refund_scheme_posting_snapshot` and `20261113100000_refund_line_scheme_tax_rate_value`: nullable `posting_tax_type` and `scheme_tax_rate_value` on refund lines and `stated_gross_foreign` on refunds; every scheme refund freezes its line rates and its gross at creation, so a retry never re-prices from a changed rate), only while the switch is on and the order is on a scheme.
- **The poster re-checks the recorded regime policy and the zero-rated type** for a treated credit note before it claims the row and as the last step before the request leaves (`pushCreditNote` now takes the same pre-socket authorization as an invoice); a difference refuses with a working instruction (restore the setting and retry on /sync, or post by hand and settle).
- **Unchanged while the Sales Invoices switch is off, for new refunds:** a refund created with the switch off is not snapshotted or treated, and its credit-note payload is byte-identical (a golden test compares it with origin/development). A refund already recorded under the scheme keeps its treatment, or its refusal, even if the switch is turned off later. Nothing is switched on by this change.

### EU IOSS credit notes: rate-182 refund VAT posts to the stamped account, the first 10 held (built and switched off: behind the Sales Invoices switch)

- **Changed: a WooCommerce refund whose VAT the EAS compliance plugin booked on rate 182, on a scheme-stamped order, is now recorded instead of refused** (while the Sales Invoices switch is on). Its VAT is the tax the refund states across all rate ids, confirmed against the refund's own stated gross (to within rounding) and held to the order's collected VAT not already refunded; it is posted as the credit note's one VAT line on the order's stamped account, and the credit note totals the refund exactly. A refund that fails either check is refused as before; a 182 figure that cannot be read is still parked.
- **Added: the first N such credit notes are held** (owner ruling 2026-11-09). While `eu_vat_refund182_held_count` is below `eu_vat_refund182_hold_threshold` (default 10), the credit note is queued as a refused row that is never sent, with wording to check it in Xero and settle it on /sync; the count is taken under a row lock, and the refused row, the count and the held stamp commit together (no stamp or count without the row), so concurrent refunds cannot exceed the threshold and a retry never counts a refund twice. A held credit note stays held on every later retry whatever the switch says. The VAT bound is on the aggregate across the order's refunds with one fixed rounding allowance (`lib/domain/sales/refund-182-hold.ts`). Later ones post normally.
- **Added: two nullable columns on refunds** (additive migration `20261113110000_refund_eas182_hold`): `eas182_stated_tax_foreign` and `eas182_held_at`, written only for a rate-182 refund while the switch is on.
- **Added: `scheme_treated_at` on refunds** (additive migration `20261113130000_refund_scheme_treated_at`): written under the order lock whenever a refund is created under the scheme path (switch on and the order scheme-stamped, or an unstamped order classified a scheme order on immutable evidence), whether or not any pricing field could be filled. A persisted scheme decision outranks the Sales Invoices switch: a credit note for such a refund (or one carrying any scheme snapshot field) is scheme-treated or a refused settle-by-hand row, never an ordinary credit note. Residual: a refund created before this column with every snapshot field null carries no evidence and is still skipped on a switch-off (none that matter exist).
- **Unchanged while the Sales Invoices switch is off, for new refunds:** the refund sync treats rate 182 exactly as before (golden tests), and nothing is counted. A rate-182 refund already held keeps its hold even if the switch is turned off later.

### Operator actions (breaking)

Numbered 4.0.0 because these changes need operator action when Xero sync is on. Each line names the topic below that it comes from.

- **Map a Xero tax type to every VAT rate that supplier bills use, and keep those rates active** (Settings > Accounting > Tax, import the purchase tax rates from Xero if needed). A supplier bill or supplier credit note whose line has no mapped tax type, or is priced on an inactive purchase tax rate, is now refused (nothing is sent to Xero) instead of posting as "No VAT". With Xero sync on, check the rate on each open purchase order and each bill still to be raised before relying on them. See *Xero accounting audit fixes: bill VAT, supplier-document tax types and payment dates*.
- **Re-save any queued bill that has a non-vatable cost line** (one edit-and-save) so it is re-derived on the corrected rules. Same topic.

Raise the credit in Xero by hand (it is not sent from IMS). Same topic.
- **Re-save an older bill before crediting it, if the credit is refused.** A supplier credit against a bill booked before this release is refused when the order's current rates no longer reproduce the VAT that bill recorded (mapping rates does not fix this). One edit-and-save of the bill records its tax treatment; then post the credit again. Same topic.

### Merged Mintsoft orders: a cancelled order's lines are taken out of the combined order

- **A cancelled (or fully refunded) IMS order that Mintsoft merged into another is now removed from the combined order automatically.** Mintsoft keeps every original line on the merged order under its original line id (confirmed live 2026-11-12, including a SKU both orders share, which stays as two separate lines). IMS now records those line ids when it pushes an order (one read-back right after the create, and again after an amendment) and, on the cancel, deletes exactly that order's lines from the combined order, reads the combined order again after each delete, proves the line is gone and every other line unchanged, tries to leave a warehouse note naming the order and the lines removed (best effort; not guaranteed), and marks the order's link cancelled. The combined order itself is never cancelled while it holds another order's lines; when the cancelled order's lines are the only ones left, it is cancelled normally.
- **It only acts while the combined order can still be changed** (New or On backorder, the statuses a cancel works on). Past that, or when the line ids were not recorded (an order pushed before this change), or a line is missing or its SKU or quantity differs, or a delete or re-read fails, IMS does nothing further and raises the existing "Cancel not honoured" notice, which now names the exact SKUs, quantities and line ids to take out by hand. If some lines were deleted before a failure, the notice says exactly what was removed and what is still on the combined order; nothing partial is silent.
- **Cancelling the ABSORBING order no longer cancels the combined order.** The absorbing order keeps the combined order's id, so its link can still read as a plain order until the dispatch sweep re-points it. Every hold or cancel now reads the order first; an order that is flagged as merged (or carries a combined "a+b" number) is never cancelled for one of its orders. The link is marked merged and the cancel takes out only that order's own lines (or cancels the combined order when they are the only ones left); a hold raises the notice. If the read fails nothing is sent and the next sweep tries again.
- **Safeguards on the recorded ids and the last-lines cancel.** The line ids are stored only when the order read back is not flagged as merged and its lines are exactly what IMS sent; a combined number alone does not make an order merged (it must be flagged). Just before cancelling a combined order whose only lines are this order's, IMS re-reads them and cancels only if they are still exactly those; otherwise it cancels nothing and raises the notice. Mintsoft has no conditional cancel, so a line added in the instant between that re-read and the cancel is an accepted limit.
- **A stale snapshot is never kept.** After an accepted amendment the recorded line ids are replaced only by a verified re-read; if that cannot be had (read-back failed or did not match, the write failed, or the line changes did not finish) they are deleted, so a later removal falls back to the notice instead of working from lines that predate the amendment.
- **Crash-safe ordering and a flag-independent re-check.** The recorded line ids are replaced (or deleted) before the link is marked as amended, so a crash in between leaves the amendment still due rather than an old snapshot behind an up-to-date link; and the re-read before cancelling a combined order's last lines is required whatever the merge flag says.
- **A merged order is never amended.** If an order Mintsoft merged into another is changed in IMS before IMS has noticed the merge, the amendment is refused (the order is flagged merged, or no longer carries its own number) before any order or line write, the link is marked merged, and the change is left for a person to apply in Mintsoft. Without this the amendment would have deleted or consolidated the other order's lines.
- **A change that could not be sent to a merged order now has an exception row.** "Change not sent to the warehouse (merged order)" appears under Sync > Exceptions with an **Acknowledge** button; it stays until acknowledged. Separately, the recorded Mintsoft line ids are marked untrustworthy before any amendment of the lines and trusted again only by a verified fresh snapshot, so a crash or failed cleanup can never leave stale ids that a later removal would act on (it raises the notice instead). Migration (additive): `20261112140000_wms_push_link_amend_notice_and_snapshot_unsafe` adds two nullable columns to `wms_order_push_links`.
- **Overlapping amendments cannot make stale ids trusted.** Each mark of the recorded line ids carries a generation token (additive migration `20261112160000_wms_push_link_line_snapshot_token`); only the amendment holding the current token can store its snapshot or clear the mark.
- **Two sweeps cannot amend the same warehouse order at once.** The order-push sweep is not single-flight, so each link's amendment now takes a durable 10-minute lease (additive migration `20261112180000_wms_push_link_amend_lease`) before anything is sent and releases it with the snapshot write; a link another sweep is amending is skipped, and a merged removal cannot settle while a lease is live. A stalled remote write outliving the lease is an accepted limit.
- **An interrupted amendment's untrusted mark is never cleared by a retry that writes nothing.** The acquisition reports whether the mark was already set; a no-op retry (not NEW, or refused as merged) then only releases its lease. Only a verified fresh snapshot, or deleting the stored ids, clears a pre-existing mark.
- **Removal and amendment of a merged order are mutually exclusive.** The removal takes the same per-link lease as an amendment, claiming the lease, the mark and the recorded line ids in one locked transaction and holding the lease through the remote deletes, the cancel and the link settlement; a link whose lease another sweep holds is skipped (left due, nothing noticed), so a removal can never act on ids an in-flight amendment is about to change.
- **The create's line snapshot is written in the same transaction as the SYNCED link.** There is no moment when a created order is live without its snapshot, and the later tokenless snapshot write is gone (the amendment's token is now required), so a late create write can never overwrite an amendment's snapshot. A failed read-back writes the link with the untrusted-ids mark set.
- **A changed order whose Mintsoft number no longer matches is no longer treated as merged.** Only an order Mintsoft flags as merged is marked merged. An unflagged order with a different number (a merge whose flag is missing, or a rename) gets no order or line write, stays linked and due, and shows once under Exceptions as "Change not sent to the warehouse (order number mismatch)" with Acknowledge; a later successful amendment clears it.
- **One identity check before every write to an existing Mintsoft order.** A hold, cancel, change or merged-line removal now proceeds only when the fresh order detail carries exactly the number IMS pushed (with the same id and client) and is not flagged merged. A missing number, or a different one (including an unflagged combined `a+b` number), writes nothing, leaves the link live and not merged, and raises a notice once; a flagged merge takes the merged paths as before. The connector contract passes the expected number to `cancelOrder`, `cancelMergedOrder` and `removeOrderItems`.
- **IMS verifies the Mintsoft order's identity immediately before each write phase.** An amendment verifies it directly before every header POST (the first and each courier fallback) and again before its line changes; a cancel, hold or merged-line removal verifies it in the read that precedes the write. Anything other than a verified match writes nothing in that phase. A structural source test pins that every write to an existing order is directly preceded by the gate. Accepted inter-system limit: a merge performed in Mintsoft within the single request round-trip between that verification and the write cannot be detected by IMS.
- **A merge is proven before IMS follows it.** When Mintsoft no longer returns an order and a combined "A+B" order lists its number, that number is only a candidate: IMS re-points the order at the combined order (and the despatch sweep applies its despatch) only when the combined order's lines hold every line id IMS recorded for the order, with the same SKU and quantity. Otherwise the order stays as it was and a notice says a possible merge could not be proven.
- **A re-point can no longer undo a concurrent cancel.** The despatch sweep's re-point of a link at a merged order is a compare-and-set on the link still being live on the same warehouse order; if it was cancelled, released or re-pointed in the meantime nothing is written, no despatch is applied and the link stays as it is.
- **A hold is unchanged:** a held order that was merged still only raises the notice. The removal sits behind the same producer-side hold and outbound write grant as the other Mintsoft cancels: with the grant off nothing is sent and the work is recorded as shadowed.
- **Migration (additive):** `20261112120000_wms_order_push_items` adds the table `wms_order_push_items` (one row per warehouse line of a pushed order: line id, SKU, quantity; deleted with its link). No backfill: orders pushed before this change have no rows and keep the notice. The table is classed "must be empty" for a first load.
- **Not changed:** the absorbing order's goods are never touched; a notice changes nothing about an order's status, stock or money.

### Xero accounting audit fixes: bill VAT, supplier-document tax types and payment dates

- **Fixed: bill VAT uses each line's own rate.** IMS recorded a bill's VAT as the order's total VAT divided by its goods subtotal, so goods 100 at 20% plus vatable freight 50 recorded 45 of VAT (a "30%" rate) instead of 30, and a mixed-rate order billed in part was wrong too. The bill's VAT is now the sum of each billed line's own rate on its own net (a vatable cost line at the order's rate, a non-vatable one at none), so its total agrees with what Xero computes from the tax types. Tax types sent to Xero are unchanged.
- **Fixed: a supplier bill or supplier credit note line with no tax type is refused, not posted as "No VAT".** The connector defaulted a blank type to `NONE`, so input VAT recorded in IMS was not claimed in Xero. A blank type, or an unexplained explicit `NONE`, now fails the sync row (*NOTHING WAS SENT...*, naming the line) before anything is sent. `NONE` is posted only where IMS decided it: a cost line marked not vatable, a rate that is itself "No VAT", or a credit note against a bill with no VAT. Bills queued before this change with a non-vatable cost line need one edit-and-save.
- **Fixed: the payment poller and the payment reconcile read Xero's `/Date(ms)/` dates.** `FullyPaidOnDate` was read with `new Date()`, which is an Invalid Date for Xero's `/Date(1750000000000+0000)/` form, and a missing date became "now". Both now go through one Xero date parser (zone-less ISO is read as UTC). A paid invoice whose date is missing or unreadable is skipped with a WARNING on the activity log (`payment_date_unreadable` / `bill_payment_date_unreadable`) and `paidAt` is not set; the poll cursor is not held, and the payment reconcile lists the document.
- **Fixed (review follow-up): a bill's cost lines post on the tax type of the rate the order was charged at.** A vatable cost line (freight, duty) took its VAT at the order's recorded rate but its Xero tax type from the supplier's current default, so an order overridden to 5% under a 20% supplier default recorded 5% in IMS and was charged 20% in Xero. The type is now the one mapped to the rate the order was charged at; if no rate at that percentage has a mapped type (or two different types share it) the line is refused rather than guessed. An order with no recorded VAT needs exactly one 0% purchase type. The supplier default is used only when it is active, purchase-usable, not compound and not reverse charge. A compound goods rate's VAT now comes from the rate's components (the sales-side maths), not from a line's rounded tax over its net, which distorted small lines (20.72% for 21%). Before a bill is saved its tax types are checked against the stored Xero tax-rate list: a type that charges a different rate than IMS taxed the line at refuses the bill.
- **Fixed (review follow-up): bill VAT is rounded per line, as Xero does.** Each billed line's VAT is rounded to the bill currency's minor unit and the bill's VAT, total and base figures are the sum of those rounded amounts, so three 0.03 lines at 20% record 0.03 (0.01 each), not 0.018.
- **Fixed (review follow-up): a bill line keeps the tax treatment it was booked with.** New migration `20261112100000_purchase_invoice_line_tax_snapshot` (five nullable columns on `purchase_invoice_lines`, additive, no backfill) stores, when a bill is created or edited, the tax type sent, the effective rate, the IMS rate id and the reverse-charge flag. Changing the order's VAT rate afterwards no longer re-prices the bill on an edit or a supplier credit. A bill booked before this is re-derived from the order's current rates only where that reproduces the VAT it recorded; otherwise a supplier credit is refused until the bill is re-saved.
- **Fixed (review follow-up): a supplier credit with an undecided tax type stays a draft.** The credit's tax type is validated before it is claimed, so a bill line with no mapped tax type (for example a legacy line that reproduces the right VAT) refuses the credit with the operator wording instead of leaving it posted with no Xero credit and no way to post it again.
- **Fixed (review follow-up): a bill with an undecided tax type is not saved.** When bills go to Xero, a new bill or edit with a line that has no tax type is refused (*The bill was not saved: no tax type on line N*) and nothing is written, so a blank can no longer be frozen as a booked treatment and block the repair. A blank snapshot that already exists is treated as not booked, and an unchanged save of such a bill re-derives its tax from the corrected mapping and re-queues the corrected first posting.
- **Fixed (review follow-up): a new bill bills a goods line at the rate its order line was recorded at.** The rate editor refreshes only draft orders, so a non-draft line recorded at 20% could bill at a linked rate that now says 5%. A new bill compares the current rate with the recorded one (stored tax over stored net) and, where they differ, bills at the recorded rate on an active purchase code for it, or refuses when there is none. A line with a net under 1 is accepted only if the current rate reproduces the recorded tax within a minor unit.
- **Fixed (review follow-up): a supplier credit refuses a bill with any untyped line.** A blank tax type is undecided whatever the line's rate, so a bill with a 20% line and an untyped zero-rate line is no longer credited as taxable.
- **Fixed (review follow-up): a bill booked before the snapshot is trusted only when its reconstruction is tight.** The reconstructed VAT must match the bill's recorded VAT to within one minor unit in total (it was a unit per line, so a 100-line bill could accept a different rate), and each goods line's rate must reproduce the rate its order line recorded. Otherwise a credit is refused until the bill is re-saved.
- **Fixed (review follow-up): a supplier credit is checked against the ledger's rate for its booked code** before it is posted, as a bill is; a mismatch beyond rounding refuses it.
- **Changed (review follow-up): supplier credits against reverse-charge bills are not posted from IMS yet.** A Xero-bound supplier credit against a bill with any reverse-charge line is refused before it is claimed (the credit note stays a draft) with *raise this credit in Xero directly*: IMS holds a reverse-charge bill gross while Xero holds its net, so the credit amount, the allocation and the transit movement could not agree. Credits with sync off, and credits against bills without reverse-charge lines, are unaffected. A proper reverse-charge credit is separate work.
- **Fixed (review follow-up): a supplier credit note derives reverse charge from the bill's own lines.** A bill is credited as reverse charge only when every line is reverse charge; a reverse-charge line together with any other treatment (for example a non-vatable cost line) is a mixed bill and is refused.
- **New: inactive VAT rates are refused on the purchase side.** A new bill, a bill edit, and a supplier credit note being sent to Xero are refused when a line is priced on an inactive rate (its own, the order's, or the booked rate), mirroring the sales-side refusal. A rate retired by a tax re-key is not counted.
- **Fixed (review follow-up): a supplier credit note copies the bill it credits, and refuses a bill it cannot mirror.** Its tax type comes from the selected bill's booked lines (type and rate), not the supplier's current default. A bill with one tax treatment is credited on it (VAT type, "No VAT" or zero-rated); a bill that mixes treatments (taxable plus exempt, or two VAT types) is refused before posting (*raise the credit in Xero by line, or credit each line separately*) and stays a draft; per-line credits are a follow-up. A bill that carried VAT with no findable type is refused by the poster.
- **Fixed (review follow-up): a PAID document skipped for an unreadable payment date is revisited, and never lost.** It is remembered in a new table `xero_payment_date_pending` (migrations `20261110180000_xero_payment_date_pending` and `20261111100000_xero_payment_date_pending_tenant`, additive, ids only, scoped to the connected Xero organisation) and re-read by id on every poll (200 at a time, least recently checked first) and applied once the date is readable. A row is forgotten only when Xero's answer shows the retry is unnecessary; a document Xero leaves out of the answer stays. Remembering is a condition of the poll moving on: if the save fails the poll holds its position. Nothing is evicted. The WARNING stays.
- Help: *Xero sync*, "Supplier bills and supplier credit notes: no tax type, no document" and "Bill VAT: each line's own rate".

With the setting set to a date or an ISO instant, an order created at or after it whose goods lines do not ALL carry a readable flag is refused by the EU VAT regime resolver (`gift_card_flag_missing`), in both modes and for any destination; an unreadable setting refuses every order (`gift_card_cut_in_unreadable`). ### EU IOSS / VOEC / DDP invoice treatment (behind the Sales Invoices switch)

- **Added: the EU VAT treatment of a WooCommerce sales invoice** (`lib/domain/accounting/eu-vat-treatment.ts`, pure; wired by `lib/connectors/woocommerce/sync/eu-vat-invoice-treatment.ts`). Before an imported order's invoice is queued (or parked for a missing number) the order's regime is decided and stamped once under the order lock, and a scheme order's goods, shipping and discount go on the scheme's zero-rated type, landed-cost fees on 232 on No VAT, and ONE VAT line carries all the collected VAT on the stamped account (821 IOSS/VOEC, 232 DDP) on No VAT. - **The scheme's zero-rated posting type is proven zero-rated and ACTIVE** against the stored Xero tax-rate list before an order is treated, and again by the poster before such an invoice is sent. An untreated held invoice is treated and released on re-import once the switch is on, after its parked lines are verified against the order; a treated hold is re-verified (lines, totals, regime, VAT) before release, and a changed order keeps it PENDING as needing a rebuilt invoice.

Draft versus live follows the existing *Sales invoices* posting mode (`draft` for the parallel phase); nothing here sets it. Credit notes and manual orders are not treated. A hold parked while the switch is off is not released untreated once it is on.

## 3.1.0 - 2026-11-12

No operator action is required: there is no configuration change, and the two migrations are additive and nullable. Behaviour changes to know about before relying on the screens:

- An in-app dispatch of a Draft, On Hold or Pending payment order is now refused. A warehouse despatch of an On Hold or Pending payment order that already has a shipment is recorded without promoting the order (administrators get a notice); a warehouse despatch of a Draft order, or of a held order with no shipment, is held as a stuck despatch on Sync > Exceptions.
- Financial reports (revenue, AR Aging, Customer Aging, Currency Summary, Sales Analytics) now count archived orders and use one invoiced-revenue basis, so figures for a past period can differ from what was shown before.
- A refund entered by hand is now strictly bounded by what the order line and the customer paid, and the refund dialog sends the credit-note figure it shows.
- A despatch from the warehouse for an order cancelled or fully refunded in IMS is not applied; it shows as a stuck despatch for a person to decide.
- A report that hits its row limit now says so instead of showing zeros.

### Dispatch completion: orders always follow the dispatch, and services no longer hold an order open

- **Fixed: dispatching the last shipment of an On Hold, Processing, Draft or Pending payment order no longer fails after the goods have left.** The order promotion used to run in a second transaction after the dispatch had committed and threw because those statuses have no direct step to Shipped; the operator saw a failure for a dispatch that had happened, the activity rows, storefront push, invoice trigger, despatch email and stock sync were skipped, and every retry failed the same way. The promotion now runs inside the dispatch transaction: the stock decrement, FIFO/COGS and the order flip commit together or roll back together. An order still in Processing is moved to Shipped through Allocated, and an "Order shipped from a non-fulfilment status" warning is logged.
- **An in-app dispatch of a Draft, On Hold or Pending payment order is refused.** Under the order lock, before any stock or cost work, with a message naming the next step (finalise the draft, release the hold, record the payment). A dispatch never finalises a draft, clears a hold or stands in for a payment.
- **A warehouse (Mintsoft) despatch for such an order is recorded without touching the order.** For On Hold or Pending payment orders that already hold shipments, the shipments, stock, FIFO and COGS are booked as for any warehouse despatch, but the order is not promoted, the hold is not cleared, no storefront completion is queued, and administrators get a "Despatch on an order that is not ready to ship" notice. Whether the order is treated as unreleased is decided under the order lock at the moment of dispatch, and the notice is re-raised by the next sweep until it has actually been saved. A despatch for a Draft, or for a held order with no shipment, is not recorded (recording it would finalise the draft or lift the hold) and goes the stuck-despatch route (retried, then Sync > Exceptions).
- **Fixed: a warehouse (WMS) dispatch retry now promotes the order.** When every shipment was already shipped but the order was not (the promotion failed or was interrupted after the dispatch committed), the sweep logged success on every tick and the order never reached Shipped, so no storefront completion, despatch email or on-shipped invoice followed. The retry now reconciles the order under its lock and reports success only once the order is Shipped.
- **Fixed: a service, fee or delivery-charge line no longer keeps an order in Allocated for ever.** The in-app completion check counted these lines as outstanding although they can never be allocated or shipped; it now excludes them, as the warehouse path and the backorder report already did. Orders with such a line complete, invoice on shipment and push the storefront completion like any other.
- **Not changed:** the order state table (manual transitions are unchanged), whether On Hold stops fulfilment from starting, and partial shipments (the order still waits for the rest).
- **No migration.**

### Sales and purchase order lists search every order; a report that hits its row limit says so

- **Fixed: the Sales Orders and Purchase Orders lists searched only the newest 200 records, silently.** Search, the status filter and paging now run in the database over every order, 50 per page, with "Showing 1-50 of N" above the table and a pager below. Search, status and page are in the address. A sales search covers order number, storefront order number, customer name and email, tracking number (order and shipments) and line SKU; a purchase-order search covers reference, supplier name, supplier reference, tracking number and line SKU. The permission checks are unchanged.
- **Fixed: Completed and Delivered orders vanished from the list and from search without a word.** The sales list now has a visible **Hide completed** tick (on by default) and says how many orders it hides. A search always includes Completed, Delivered and archived orders, and an archived order shows an **Archived** badge. A new **Include archived** tick shows archived orders in the everyday list (sales and purchase orders). Archiving still only hides an order from the default list; nothing a financial report counts has changed.
- **Fixed: a report that hit its source-row limit showed zeros and "No rows".** Every report that refuses an over-large scan (sales, purchasing, finance, inventory costing, stock position, reorder, backorder, component shortage, manufacturing) now shows a red "This report hit its row limit (N rows); narrow the date range or filters" banner, dashes in the summary tiles and "Report not computed" in the table. The CSV export of such a report is still refused (HTTP 413), now with the same message and a `reportNotComputed` flag in the body, so a file of zeros can never be downloaded.
- **Short searches do not scan.** One or two characters only match an order number or reference exactly, and the list says "Type at least 3 characters to search". A report that is not computed also shows dashes in its table footer totals.
- **No migration.** Searches are case-insensitive substring matches over the existing tables, ordered by the existing `createdAt` index; no new index was added.

### Mintsoft order push: landed creates, merged orders, holds and cancels the warehouse cannot honour

- **A create that timed out or lost its link write is no longer parked for good.** The sweep (and **Replay** on the "Create outcome unknown" row) now looks the order up in Mintsoft by read only, and links it only when exactly one live order of this client carries this order's own number AND its own reference, read back by id. Anything else (another reference, several matches, a full 10-row result page, a cancelled order, a read that fails) stays parked with the reason on the row. The same rule applies when Mintsoft answers a create with "Order Number already exists!": a cancelled order keeps its number, and IMS no longer links to it. A create that landed but whose link write failed keeps the id Mintsoft returned instead of discarding it.
- **Verification is stricter.** An order is proved ours only when it carries both the number IMS sent and its own reference, exactly, and a present status other than cancelled. A missing field leaves it unverified (retried, then quarantined for an operator); a cancelled order is never proved ours.
- **Merged orders are detected.** When Mintsoft merges an order into another, IMS no longer cancels or holds the surviving order for one absorbed order, because it also holds the other order's goods. A hold or cancel that finds the order gone (404) does one read-only search: a flagged same-client survivor that lists this order's number as a part re-points the link to it as merged and raises a "merged" notice with a note for the warehouse; a search that cannot tell (an error, a full page, several candidates) is retried for 5 sweeps and then raises an operator notice; only a conclusive "no such order" gives the plain not-found notice. A merged-order create that was absorbed is parked with guidance that names the survivor and says not to cancel it.
- **A 404 is no longer recorded as a successful cancel or hold,** and a hold or cancel past NEW no longer dead-letters the link. The link stays live so a later despatch is still recorded, and **Sync > Exceptions** shows "Hold not honoured" / "Cancel not honoured" rows with the reason. The warehouse gets one note per notice; a failed note is retried until it is posted. A notice is cleared when the IMS order leaves the held or cancelled state. A cancel on a backordered Mintsoft order now works, and an order Mintsoft already cancelled is reported as already cancelled rather than as a fresh cancellation.
- **A despatch is refused for an order IMS no longer intends to ship.** If an order is cancelled, or fully refunded and not yet despatched, in IMS when the warehouse despatches it, the despatch is not applied (no shipment, stock movement or storefront write, split orders included). It surfaces as a stuck despatch for a person to decide. The decision follows the order's current state, so a cancel that was reversed does not block a real shipment.
- **Migrations (additive, nullable, no backfill):** `20261110100000_wms_push_link_operator_notices` adds `hold_notice_at` and `cancel_notice_at` to `wms_order_push_links`; `20261110120000_wms_push_link_notice_comment_delivery` adds `hold_notice_comment_at` and `cancel_notice_comment_at`. Existing links read as "no notice".
- **Not changed:** nothing in a notice changes an order's status, stock or money. (IMS did not remove an absorbed order's items from a merged survivor in this release; the next entry above does.)

### Sales order, refund dialog and PDF figures: one basis, reconciling

- **Fixed: the order page no longer grosses its figures up a second time.** Line totals, subtotal and shipping were multiplied by the order's header rate whenever the display flag said "prices include VAT", so a WooCommerce order (stored net) or an order whose lines carry a different rate (for example 0%) showed a subtotal larger than its total. The page now follows the basis the amounts are stored in (`storedAmountsIncludeVat`), takes each line's own VAT, grosses shipping up exactly as the invoice is sent, labels every column and total "incl. VAT" or "excl. VAT", and says so on screen if the figures do not add up to the stored total.
- **Fixed: the refund dialog now shows, and sends, the credit note.** It used to send quantity x the typed unit price as the NET refund, so on a VAT-inclusive order the credit note added VAT to a gross price (28.80 confirmed, 34.56 credited). It now sends the refunded line's stored net pro rata and shows net, VAT and the credit-note total incl. VAT before Confirm; the Refunds panel and the invoice dialog show the same credit-note figure from the same helper.

### Manual orders and bills: three posting defects

- **Fixed: a manual order with VAT-inclusive prices and "No VAT" as its default rate no longer posts its VAT twice.** The stored amounts cut each line's net out of the typed gross at the line's own rate, but the invoice was sent inclusive or exclusive from the header rate alone, so a £120 line at 20% reached the ledger as £120 net + £24 VAT. That combination (Incl. VAT with no default rate while a line carries VAT) is now refused when the order is saved, in the form and in `createSalesOrder`; with the default rate chosen the order is stored and posted inclusive at the prices typed. The Incl. VAT box is shown even when the rate is "No VAT". A draft already stored that way is not finalised and no invoice is queued for it. Orders already queued or posted are not changed.
- **Fixed: a clone is a Draft until it is finalised like any other order.** Cloning (and any allocation of a Draft) promoted the order straight to Allocated and skipped finalisation, so no sales invoice was ever queued. Allocation now declines a Draft; finalising allocates and queues the invoice once. A clone also carries the source's VAT basis: a manual order's "prices include VAT" flag is copied (it was left at the default, which read an inclusive order's gross prices as net), and a clone of a WooCommerce order is an exclusive document, because the importer stores every amount net whatever the store displays. Clones already made and shipped before this fix have no invoice and need one raising by hand.
- **Added: a draft is not finalised when its invoice would not book to the order's total.** Before finalisation moves anything, the invoice that would be queued is built and its total (from the payload: inclusive or exclusive, shipping and the order discount at the order's default rate) is compared with the order's stored total, within one penny per line plus two. A mismatch refuses the finalisation with both figures. This catches an order whose shipping is taxed differently from its default rate (a WooCommerce order with zero-rated shipping, whose clone cannot carry the shipping rate because the order does not store it), and the next basis defect of the same kind.
- **Fixed: a WooCommerce fee the shop charged no tax on no longer picks up VAT on a re-queued or cloned invoice, and the reconciliation prices tax from the codes actually sent.** A fee stored with no product, no tax rate and no VAT is sent on the no-tax code naming why (as the importer's own invoice does), instead of falling through to the order's taxable code. The invoice-to-order reconciliation now computes an exclusive document's tax from the code each line, shipping and the discount is sent on (a code no single active rate carries falls back to the stored VAT), not from the VAT stored on the order, so a change of code is caught.
- **Changed: a live order whose invoice would not book to its total is refused at creation, and the reconciliation allowance is capped.** `createSalesOrder` builds the invoice from the rows it has just written, inside the creating transaction, and a mismatch rolls the order back (nothing saved, allocated or queued) instead of leaving a live order with only a warning. The allowance is 0.005 per line plus 0.03 (half a minor unit per computed tax figure, the shipping and discount together, and the total), capped at 1.00 in the order currency.
- **Fixed: an invoice is reconciled against the lines the connector will actually send.** Shipping and the order discount are sent only when their accounting account is set; a positive amount with no account used to count in the reconciliation while the connector dropped it, so the invoice posted short of (or over) that money. The Xero builder, the tax-type check and the reconciliation now share one emit decision, and an order with shipping or a discount whose account is not set is refused (at creation and at finalisation) with a message naming the missing account. Set the shipping and discount accounts under Settings, Accounting before raising orders with shipping or a discount.
- **Fixed: finalising a draft, and creating a live order, are each ONE transaction with the invoice.** Finalising a draft used to commit the status, then allocate stock, then build and queue the invoice, and swallowed a failure of the last step, leaving a live order with no invoice. The status flip, the stock allocation and the sales invoice (built, reconciled to the order's total, and queued) now commit together; a failure of any of them (no stock, an invoice that does not reconcile, an unmapped account, a refused or failing enqueue) rolls everything back and the order is still the draft it was. A live order created in the form is invoiced inside its creating transaction in the same way, so it is either saved with its invoice queued or not saved. Only one place decides what basis an order's stored amounts are in: a WooCommerce order is always net (whatever the store displays), any other order follows its "prices include VAT" flag; the invoice builder, the reconciliation, the clone and the chargeback discount all use it, so an inclusive WooCommerce draft now finalises as a 120 invoice for net 100 + 20 VAT instead of being refused.
- **Changed: a live order created with no stock to allocate is created, invoiced, and the shortfall is shown.** Creation (order and invoice) is atomic; allocation is a separate step that may legitimately leave the order unallocated (a backorder), as a WooCommerce import does. The result of that allocation was previously dropped, so a shortfall or a failed allocation was silent unless the allocator happened to log it; it is now returned to the create screen as a warning, and an `allocation_failed` entry is written on the order's activity log where the allocator wrote none.
- **Fixed: two edits of one bill can no longer overwrite each other.** An edit calculates its figures from the bill as it read it; if another edit committed before the bill lock was taken, the late edit is refused with a request to reload, instead of silently replacing the first.
- **Fixed: editing a bill before its first posting reached the ledger is no longer lost.** The queued posting kept the pre-edit figures and went out unchanged, so the ledger and IMS disagreed. The edit is now written into the still-unsent first posting (no update, no second posting) and the transit subledger takes the difference. If the first posting is in flight, was sent but not linked back, or failed after a request left, the edit is refused with nothing saved. A bill created before postings were keyed to the bill has a posting keyed to its purchase order: it is refreshed only when it is provably this bill's (the only bill on the order still waiting for a document, the only such posting, and the same supplier invoice number) and unsent; otherwise the edit is refused until posting is resolved.

### Purchase orders: edit, close and cancel at every stage

- **Changed: a purchase order can be edited from Draft through Part-received.** An order nothing has touched (no goods received, no supplier bill, no return, no warehouse ASN) is fully editable at RFQ Sent, Quote Received, PO Sent and Shipped, so quoted prices can be entered and a typo in quantity, price or warehouse corrected after sending. Once goods, a bill or an ASN touch it, it is amended in place: line ids are kept, received, billed or returned lines keep their price and cannot be removed, a quantity cannot go below what was received, billed or returned, and supplier, currency, exchange rate and VAT are fixed. On a part-received order with freight or cost lines, quantity and line-set changes are refused because they would change the cost of goods already in stock.
- **Changed: Close and Cancel are available at every stage from RFQ Sent to Part-received.** With nothing received, Close ends Closed and Cancel ends Cancelled. A Draft can only be cancelled and a fully received order can only be closed.
- **Changed: cancelling a part-received order no longer reverses the received stock.** Cancel and Close are now the same operation on a part-received order, **close short**: the unreceived balance is dropped, the received stock, its cost layers and its journals stay as they are, and the order ends Closed (shown as "Closed short: received 60 of 100"). No reversal movement or journal is created. To take received goods back out, use Return Items first. The confirmation says exactly what will happen, with the quantities.
- **Changed: closing short re-spreads the order's freight over the units that arrived.** The freight on the order (its own cost lines and linked freight orders) was spread over the full ordered quantity at receipt. Closing or cancelling a part-received order now spreads all of it over what landed (BY_VALUE by landed value): the remaining cost layers are revalued, the sold units' share goes to cost of sales, in-transit units carry theirs, and the journals (DR Inventory / CR Transit, DR Cost of sales / CR Transit) are posted behind the usual holds, once. A freight credit larger than the goods cost is floored at 0.00 with a warning. Other orders sharing a freight order keep their own share. Orders without freight post nothing.
- **Changed: an order with an open warehouse ASN cannot be closed or cancelled, and its lines cannot be reduced or removed,** until the ASN is booked in or retired. Closing with a supplier bill for more than was received succeeds with a warning naming the lines and the amount billed ahead of receipt.
- **Fixed: a supplier return on a part-received order no longer strands the unreceived balance.** The order stays Part-received while any quantity is still due, so it can still be received, edited, closed or cancelled and stays in the incoming figures; it moves to Partially Returned or Returned only when nothing is left to receive. An order already stranded in Partially Returned can be closed or cancelled. A return is also refused if the order was closed while it waited.

### Reconciliation pack: the comparators and the report writer (no item runners yet)

- **New (backend only, nothing runs yet): the core of the reconciliation pack** in `lib/reconciliation-pack/`. It holds the R1 to R15 catalogue (claim, tolerance rule and value, cadence, phase applicability, dependent streams), pure keyed comparators (identity on one side only, differing, unsettled, outside the recorded population, excluded; counts derived from the lists; exact quantities to 0.0001, absolute tolerances, the R5 composite and the order-currency minor-unit rule), the rule that a difference fails only after two later successful runs of its stream (distinct last-success stamps, never ordered), closed reason codes, and the identity-token sanitiser. It also holds the report writer (evidence file, Markdown, then the JSON as commit record, a hash chain by sequence, an exclusive run lock) and the trend reader that verifies every pair and the chain. There is no command and no vendor call yet, and the readiness gate does not read it yet. The exit-code table, the reason and refusal codes, the item catalogue and a table of the failure classes the design guards against are in the installation guide under "Reconciliation pack".
- **A pass must prove itself, and a live lock holder is never displaced.** In the report builder and again in the reader, an item may only be a pass if it carries a proof (identities compared, or a named proof that an empty population is true), exactly its catalogue sources, and an equal start and end stamp for every stream it depends on; fail, inconclusive and not-applicable have their own invariants. The run lock is reclaimed only when its holder is provably dead (process gone, or start time or boot id changed), never by age; where that cannot be shown the run is refused. The commit claims its sequence number with an exclusive file and links the JSON into place without overwriting.
- **The comparator no longer reads an unreadable input as equal.** A key part that is not a non-empty string or a safe whole number (an object, NaN, negative, empty, a control character) refuses the row (`BAD_KEY`) instead of sharing one canonical form with every other such value. A value-bearing comparison needs a decimal on both sides of every row (`VALUE_MISSING`); presence-only comparison is a mode fixed per item in the catalogue (R13, R14), never a fall-through. A minor-unit comparison checks both currencies against a known list and has no default number of decimals (`CURRENCY_UNKNOWN`); minus zero reads as zero; a missing tolerance, mode, completeness flag, population set or carried state is refused. The installation guide lists every refused input shape with its code, and a test runs a case for each.
- **The evidence now proves what the report claims, and the builder serialises nothing the caller owns.** Every identity, equal ones included, is a line of `evidence.jsonl`; the reader recomputes every count and the digest of the equal identities from those lines and re-judges each line against the item\'s catalogue row (the value shape of its mode, the true delta, the tolerance verdict of the catalogue measure, the currencies). The input is copied field by field into plain objects (unknown fields, accessors, symbol keys, Proxies, class instances, holes and oversized lists are refused), and the finished report passes the reader\'s validation before any file is created.
- **A bucket is derived from what an entry records, and only compared identities prove anything.** Every entry records whether each side had the identity (explicit presence flags); the builder and the reader derive the bucket of a pair entry from those fields in both modes and refuse a label that disagrees (a one-sided identity can no longer be published as an equal one). The comparator issues its "compared" proof only for equal, in-population, non-excluded identities; excluded, out-of-population and unsettled identities are listed but prove nothing, and a comparison with only those needs a named empty-population proof or is inconclusive. A table test runs every combination of buckets in both modes from the comparator to the parsed report.
- **No free-form field reaches output, and a credential-shaped SKU is digested.** The system identifier is exactly what PostgreSQL produces (10 to 20 digits); the lock\'s host is a DNS-style name; every field that can reach the JSON, the Markdown, the evidence, a file name or the lock has an anchored allowlist grammar in a single-sourced table that a test checks against a real published report. Identity tokens keep their allowed-character pattern and now also pass a credential screen (a credential-ish word, a 24-character opaque run, or over 64 characters means a `sku#` digest is printed instead). Tokens are trusted data keys and the screen is defence in depth; the installation guide lists what it does not cover.
- **Changed (internal):** `readTrustedRegularFileBytes` returns the bytes `readTrustedRegularFile` decodes, so a digest can be taken over exactly what was parsed.

### First load: the apply runner core (no database side yet)

- **New (backend only, nothing runs yet): the core of the first-load apply runner** in `lib/first-load/apply/`. It reads and verifies a prepared run from bytes (every file against the prepared report's SHA-256, size, rows and the importer's header; unique keys; every parent, component, warehouse, FX rate and zero-cost pair backed by the files or refused; WooCommerce variant parents only from a re-verified snapshot), computes per step which rows are still to load, and drives plan, apply and resume through ports. The accounting is taken from the database, never from the importers' counters. It opens no database or network connection and adds no command yet. Documented in `docs/first-load-apply.md`.

### Payments: several payments on one invoice, told apart by the receipt

- **Fixed: a balance recorded after a deposit that had already posted is no longer refused.** The last check before a payment is sent judged every payment already sent against the invoice, so a posted deposit blocked its own balance (and a failed one blocked the next receipt). IMS now identifies a payment by the receipt (payment row) it was recorded for. A *different* live receipt never blocks, a *repeat of the same receipt* is always refused, and a registration that cannot be shown to belong to a different receipt (imported before this change, or whose receipt was deleted) still blocks. One rule is shared by the registration decision, the final check, the over-settlement guard and the manual retry, so they cannot disagree. A deposit's payment in Xero is recognised by the reference IMS wrote on it, never by amount and date.
- **Changed: a paid WooCommerce order is imported with a payment row**, and the payment registered in Xero carries that receipt's identity. A hand-recorded receipt on the same order therefore registers normally.
- **New: `sales_orders.cancelled_at`** is stamped by the database when an order becomes cancelled. Receipts can now be recorded on a cancelled order; one dated after the cancellation is held (nothing sent, a warning says so) because Xero books that money as an overpayment, which IMS does not create yet. Paid before or at the cancellation, or with no known cancellation time, registers as before.
- **Unchanged on purpose:** a payment above what is outstanding is still refused (Xero refuses it too), so no excess is ever posted as a payment.

### Mintsoft: the despatch poll is scheduled, and a bundle create is not repeated after an uncertain send

- **The `mintsoft-dispatch-sync` job is now a registered scheduled job (every 15 minutes, on by default).** The installation guide always listed it as automatic, but nothing scheduled it, so a despatch in Mintsoft did not progress the IMS shipment unless someone added a crontab line by hand. **Upgrade step: open Settings > System > Scheduler and use Save & Apply once** so the new job reaches an existing crontab. The poll only reads from Mintsoft, does nothing while the Mintsoft plugin is off, and **never logs in**: a username/password login replaces the tenant API key for every integration that shares it, so with a fixed API key the poll runs, and in username/password mode it runs on the stored key and skips with a reason once that has expired. Use a fixed API key for an unattended poll. The read-sync liveness check now names the job and reports the poll as off when the job is switched off.
- **Fixed: a Mintsoft bundle create that may have been sent no longer releases its claim.** A timeout, a dropped connection or an unusable answer used to delete the claim, so the next run could send the create again. The claim is now kept, the bundle is looked up straight away (a read) and linked only if it matches IMS, and no further create is sent by the clock: a claim whose create may have reached Mintsoft stays until a lookup returns a complete, matching bundle or an operator resolves it on **Sync > Mintsoft > Bundles** (link the Mintsoft bundle, or state that a search found none; that release is refused until the create can no longer be in flight and a fresh lookup reads "no bundle", and it is audited in the same transaction). A worker re-checks its claim immediately before sending (and sends nothing if it changed) and never overwrites a link written meanwhile; a process frozen for longer than the release window between that check and the send can still duplicate, which Mintsoft's lack of idempotency prevents IMS from closing. Only a claim marked as never sent is ever retaken; legacy `pending:<time>` claims count as sent. A bundle answer with component entries IMS cannot read is never compared or linked. A create the outbound-write hold refused before it left still releases its claim. Adds no environment variables.

### Readiness gate (`npm run readiness:gate`) and a stricter rollout-readiness endpoint

- **New: `npm run readiness:gate -- --phase P0|P1|P2`** reduces the switchover checks to one verdict (GO, GO-WITH-ACCEPTED-WARNINGS, NO-GO) with a JSON and Markdown report. It performs no database or checkout write. Documented in docs/installation.md, "Readiness gate".
- **Changed behaviour of `/api/admin/rollout-readiness`: a PARTIAL newest accounting reconciliation run now BLOCKS (HTTP 412, including with `?allowWarnings=true`).** It used to be a warning that `allowWarnings=true` turned into 200. A FAILED newest run also cannot prove completeness, and a RUNNING, queued or unrecognised-status newest row (the newest row of ANY status, not the newest finished one) blocks with a message saying a run is in progress or unrecognised; only a COMPLETED run can clear an earlier truncation; an unreadable newest-run read is a blocker instead of a warning; a truncated newest run is a blocker; runs created at the same instant are read together and judged as the worst of them, and never clear each other's truncations.

### WooCommerce initial-import rehearsal (`npm run rehearse:woo-import`)

### The deploy admin database credential is root's alone (o3d-1bgr, o3d-bpbv)

- **The application account no longer holds, inherits or can read the admin database credential.** It used to
  sit in the application's own `.env`, was handed to the account on `runuser ... env VAR=secret` command lines
  (readable in `ps`), was inherited by every command started as that account whenever it was typed on
  `sudo env ...`, and the fence helper itself ran as that account. The credential now lives in
  `/etc/ims-db-admin/deploy-admin.env` (root:root 0600 in a root:root 0700 directory) or on the root
  invocation; the fence helper runs as root with a scrubbed environment and nothing secret on any command line;
  the exported variable is un-exported at once. **A copy left in the application `.env` is refused before
  anything is stopped**, naming the file to move it to.
- **The migration no longer connects as the admin.** `options=-c role=<app>` is a session default, so
  `SET ROLE NONE` on that connection was the superuser admin, handed to application-owned bytes (prisma, the
  migration SQL, package scripts) for the whole window. The migration now logs in as a role with no privilege of
  its own (`<application role>_migrator`, created by `install.sh` for a local server; for an external database
  `fence-db-connections.mjs --ensure-migration-role`, or the three statements in docs/installation.md), with a
  fresh random password minted for each window and sent as a SCRAM verifier, and closed again by the release.
  The server is asked, not the configuration: a migration role that is a superuser, holds CREATEROLE/CREATEDB/
  REPLICATION/BYPASSRLS, reaches a role the application cannot, cannot `SET ROLE` to the application role, has no
  `CONNECT` of its own or cannot be altered by the admin is refused by `--preflight` before anything is stopped.
- **A migration role this tool did not create is never adopted** (marker comment; refused before any grant, in one
  transaction), a marked role that owns or is granted anything of its own anywhere in the cluster, carries per-role
  settings or reaches a role the application cannot is refused by `--preflight`, the minted URL keeps only
  transport-trust query parameters from the admin URL (an admin URL carrying `password=`, `user=`, `host=` and the
  like is refused) and is opened once to prove it authenticates as the migration role, and a release whose login the
  server cannot confirm closed now FAILS (retryable) instead of reporting success, **before any CONNECT is
  restored** (the login is closed first; a failure leaves the fence standing). The audit also refuses a marked role
  holding anything beyond CONNECT on the application database, and any direct membership besides the application
  role (PostgreSQL 16+ INHERIT/SET options are not trusted to compare).
  A release that fails after its grants may have committed now reports `FENCE_STATE=held|restored|unknown` read from
  the ACL on a fresh connection, and the three entrypoints and the wrapper clear their "fence is up" state on
  anything but `held`; `--preflight` and `--fence` (again at the end of the drain) refuse a migration login that is
  already open (LOGIN or a stored password). The fresh state read must be on the same server as the release (else
  `unknown`), and the password check no longer requires a superuser admin (separate `pg_authid` statement, only when
  the admin may read it). An unreadable system identifier never matches in the release probe (`unknown`). The
  single-cutover-host assumption is documented.
- **The operator recovery wrappers** read the root file, run the helper as root, and (o3d-bpbv) take the cutover
  lock first, resolve the documented pointer once, hash that directory and execute the helper by the resolved
  path, so a publication landing between the hash and the exec can no longer substitute a different release.
- **Operator action on upgrade:** move `DEPLOY_ADMIN_DATABASE_URL` out of `.env` into the root file, and make sure
  the migration role exists. A fresh installation needs neither step. No migration.

### First-load preparation tool: validates and prepares the incumbent exports for the existing importers (o3d-zjsb5)

- **New command `npm run first-load:prepare`, file in and file out (no database, no network).** It reads Qoblex, 3PL and
  WooCommerce export files through a column map (or already-canonical CSVs) and writes importer-ready files with the
  importers' exact template headers, plus a JSON and Markdown validation report that accounts for every input row as
  emitted, excluded or rejected. It checks SKU coverage across the systems, that the recipe graph has no cycle, collapses FIFO
  lots to one exact weighted-average cost per SKU and warehouse, reports zero on-hand separately from missing, reduces open

### Late landed cost on stock in transit between warehouses now reaches Inventory (o3d-nrl4)

- **A freight order added, edited or cancelled after the goods were bought now posts the share that belongs
  to units still on a warehouse transfer.** The revaluation used to move only the on-hand units' share out of
  Stock in Transit and queued nothing for units dispatched but not yet received (or aligned by the WMS), so
  the freight debit stayed in Stock in Transit and Inventory stayed understated, in a way no reconciliation
  showed. The landed-cost reclass journal (`STOCK_IN_TRANSIT`) now includes those units at the moment the landed
  cost changes (DR Inventory / CR Stock in Transit, reversed for a decrease); the later receipt or dispatch
  cancellation posts nothing. A manual receipt, a WMS book-in and a WMS alignment credit all count as landed.
  The revaluation audit run lists the amounts under `inTransitResidue`. No migration. Amounts left in transit by
  revaluations made before this change are not repaired.

### Purchase-order lines have a landed-quantity definition (o3d-papk, first half)

- **A manual purchase-order receipt can no longer be booked on top of units the WMS stock-sync
  alignment already brought in.** The alignment lands stock and a cost layer without writing
  `qtyReceived`, so the receipt guard saw the whole line as outstanding: aligning 6 of a 10-unit line
  and then receiving 10 by hand put 16 units into stock for 10 physical ones, with a second cost layer
  and a second `STOCK_RECEIPT` journal. The guard now refuses more than `qty − landed`, read inside the
  transaction under the order lock.
- A purchase order is RECEIVED (after a manual receipt or a WMS book-in) once every line has *landed*,
  not only once `qtyReceived` reaches `qty`; the alignment planner caps a PO line at its own residue and
  refuses an ASN whose order is CANCELLED or CLOSED; the EOL-archive incoming figure and the product
  incoming badges count a PO line by what has landed. No migration.
- **A WMS book-in no longer lets a line's landed quantity fall (o3d-papk follow-up, o3d-67kw3).** The booked-in
  reconciliation took the line-wide `qtyReceived` as "manual receipts against this ASN" and applied it before the
  snapshot cover, so align 6, receive 4 by hand, book 6 left landed at 6 and the guard accepted another 4 (stock 14
  for 10 physical units), and a line partly received by hand and then covered by an ASN sized for the rest lost
  units at book-in (line 10, manual 4, ASN 6, booked 6: only +2). The snapshot cover now comes first, the manual
  term draws on a branded pool (the line's unreconciled manual receipts less the new
  `wms_asn_line_maps.manualQtyBaseline`, written when an ASN row is created or resized), and transfer lines get the
  same fix. **Migration:** one additive column, `NOT NULL DEFAULT 0`, no backfill.
- **A purchase-order ASN is sized by what has landed, and a credited reservation is never deleted or resized in
  place (o3d-papk follow-up; the minimal purchase-order half of o3d-6b9c).** A retry, the post-mismatch discard
  and the finalize conflict used to delete the pending reservation, cascading the alignment credit that is the
  only record that units landed (landed fell from 10 to 4 while stock stayed at 10), and the ASN sent to the live
  warehouse was sized `qty − qtyReceived`, so landed units were asked for again. The creator now sizes by landed
  outstanding (branded all the way to the wire), retires a credited reservation (closed, credit kept) and
  reserves the remainder on a new one, disposes under `purchase_orders` → ASN header → ASN lines, returns
  operator refusals so a retirement commits, and refuses to claim a retired reservation (both creators).
- **The WMS stock-sync alignment advances a purchase order's status (o3d-papk follow-up).** An order stocked
  entirely by alignment stayed PO_SENT with `receivedAt` unset. The alignment now derives the status from the
  landed quantity under the order lock it already holds (forward only); the manual receipt and the book-in use
  the same derivation.

- **A WMS booked-in callback no longer receives against a cancelled or closed purchase order, and never overwrites an
  order's status (o3d-papk round 2, o3d-yaazk).** A partly received order cancelled while its ASN stayed open took stock,
  a cost layer and a journal from a later callback and then had CANCELLED overwritten with PARTIALLY_RECEIVED/RECEIVED. The
  callback is now held for review with an approval-blocked `parent_not_receivable` warning, and the status is only written
  along the purchase-order workflow.
- **Two ASN-create requests that reserved the same row can no longer retire or reopen it under each other (o3d-papk round 2).**
  The discard only touches an unclaimed, open reservation, and the finalize is a compare-and-set that fails closed (retaining
  the id of the ASN the warehouse created) instead of reopening a row whose expectation a retirement had rewritten. Both creators.

### Fixes (landed-cost precision)

- **Landed-cost snapshot refreshes now keep returned quantities and replacement unit costs Decimal-safe until serialization.** Customer and supplier return helpers now return `Prisma.Decimal`, and cost-layer snapshot refreshes accept Decimal inputs before explicitly preserving the existing JSON number shape for `unitCostBase`. Manufacturing cost-layer recalculation now also keeps unit deltas, consumed quantities, COGS deltas, and inventory deltas Decimal-safe until the journal/server-action return boundary.
- **Landed-cost revaluations now write audit runs.** Direct and linked landed-cost recalculations persist before/after cost-layer snapshots, affected COGS refresh counts, planned accounting adjustment idempotency keys, captured warnings such as BY_WEIGHT fallback, and the triggering user where a server action initiated the recalculation.

### Fixes (allocation precision)

- **Allocation availability now uses Decimal arithmetic internally.** Sales allocation stock maps, product graph component quantities, kit requirement expansion, coverage checks, and reservation deltas now keep fractional quantities as `Prisma.Decimal` through the allocation service. This avoids binary floating-point drift when allocating fractional kit/component quantities while preserving existing UI and report number boundaries.

### Fixes (refund correctness)

- **Refund return-stock idempotency now includes the return warehouse.** Split returns of the same refund line to different warehouses no longer collide on the same `RETURN_INBOUND` idempotency key. Because IMS is not live yet, no old-key compatibility path is kept; persistent dev or staging databases with old-shape refund return keys should reset those `RETURN_INBOUND:refund:*:line:*` movement idempotency keys or rebuild the database before replaying refund returns.
- **Refund restocking now requires shipped-stock evidence.** Allocation-only refund rows no longer silently restock from unshipped reservations when no shipment line exists on the original order. Those attempts now return a clear operator message and should be processed as cash-only refunds or corrected to refund a shipped line.

### Fixes (VAT and tax correctness)

- **Sales-order creation now validates caller-supplied line tax assertions.** Import/API callers may pass `taxForeign` per line as an assertion; IMS rejects values that do not match the resolved line tax rate and inclusive/exclusive pricing mode before creating the order. VAT report coverage now separately pins inclusive taxable-base reporting (`totalBase - taxBase`) and exclusive taxable-base reporting (`totalBase`).

### Fixes (manufacturing valuation)

- **Manufacturing WIP and cost-layer timing now align with finance expectations.** WIP reporting includes both consumed component value and manufacturing cost-line totals, production-created cost layers receive the production completion timestamp for FIFO ordering, and manufacturing cost-line parsing now drops sub-half-penny negative rounding dust while still rejecting real credit-style negative adjustments.

### Fixes (purchase cancellation and freight)

- **Purchase-order cancellation and linked freight receipt guards are stricter.** Cancelling a partially received PO reverses remaining receipt cost layers, and repeated cancellation of an already-cancelled PO is now idempotent. Linked freight POs can only auto-receive from committed states (`PO_SENT`, `SHIPPED`, `PARTIALLY_RECEIVED`, `RECEIVED`), blocking draft, RFQ, and quote freight orders.

### Fixes (stock and cost-layer precision)

- **Stock removals require FIFO cost-layer coverage.** Negative stock movements using strict FIFO consumption now fail before stock levels are written when cost-layer evidence cannot cover the removal.
- **Purchase receipts reject invalid unit costs before stock writes.** Receipt costs must be finite and zero or greater; zero-cost receipts remain allowed for replacement, sample, or consigned stock.
- **Cost-layer snapshots use Decimal-safe six-decimal strings.** Transfer, shipment, refund, WMS, and Mintsoft snapshot writers now share one serializer for persisted FIFO snapshot quantities and unit costs.
- **Landed-cost recalculation adjustments carry freight PO attribution.** Adjustment idempotency now separates different linked freight POs; non-live deployments can rebuild freely, but live queues should be drained or rewritten before deploying this key-shape change.
- **COGS entries preserve six-decimal consumed quantities.** `CogsEntry.qty` is widened to `DECIMAL(14,6)` and COGS writers now share one Decimal-safe create-data helper.

### Fixes (Mintsoft webhook security)

- **Mintsoft ASN booked-in webhooks now bind the freshness timestamp into the HMAC signature.** IMS verifies `HMAC_SHA256(secret, "${timestamp}.${rawBody}")` and rejects body-only signatures.
- **Mintsoft ASN booked-in webhooks now acknowledge after durable persistence.** Accepted webhooks are stored idempotently in `wms_inbound_receipt_events` and return `202 Accepted`; the Mintsoft webhook sweeper applies stock and purchase-order effects asynchronously.
- **Mintsoft booked-in reconciliation now uses direct ASN lookup.** The processor fetches the referenced ASN by id through the WMS connector instead of listing all ASNs and searching client-side. `MINTSOFT_USE_BULK_ASN_LOOKUP=true` is available as a temporary rollback flag if Mintsoft endpoint discovery shows a different direct endpoint shape.
- **Mintsoft booked-in webhook sweeping is configurable.** `MINTSOFT_WEBHOOK_SWEEPER_PAGE_SIZE` controls how many persisted booked-in events one sweeper run drains; the default remains `250`.
- **Mintsoft booked-in webhook retry state is now queryable.** `wms_inbound_receipt_events` stores typed processing status, retry attempts, next retry time, dead-letter timestamp, and last error, replacing the old `processingError` retry-state mirror so the sweeper no longer scans or parses encoded retry JSON.

### User-facing (sales allocation and backorders)

- **Sales allocation now distinguishes physical reservations from backorder demand.** Auto-allocation reserves only stock that physically exists; oversell-eligible shortfalls remain unallocated and appear as backorder demand instead of inflating `reservedQty`. Operators may see existing phantom over-reservations corrected on the next re-allocation, with affected lines shown as `Backorder` or `Unallocated` in the sales-order allocation panel.
- **Allocation activity logs include backorder details.** Allocation entries can now include unallocated quantities and per-line backorder metadata. The activity-log UI has no action allowlist, but downstream log parsers should expect the new `backorder_recorded` action and the longer allocation descriptions.

### Breaking operator change (cron authentication)

- **Production cron endpoints now require bearer authentication by default.** Localhost-only cron calls without `Authorization: Bearer $CRON_SECRET` will receive `401` in production. This is an operator-facing breaking change and should ship in the next major release (`2.0.0` under the release scheme above).
- **Before deploying this change, update existing production crontabs.** Replace bare localhost cron calls with commands that read `CRON_SECRET` from the protected app environment file and send the cron bearer token, for example:

  ```bash
  CRON_SECRET=$(grep -m 1 '^CRON_SECRET=' /opt/one-two-inventory/.env | cut -d= -f2-) && curl -fsS -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/fx-rates
  ```

- **Fresh installs are handled by `scripts/install.sh`.** Installer-generated cron entries now read only the `CRON_SECRET=` line from `${APP_DIR}/.env` at runtime, keeping the cron secret in the existing `imsapp:imsapp` mode-`600` environment file instead of duplicating it into the crontab or sourcing the full environment file.
- **Emergency bypass is explicit and narrow.** Production localhost bypass is only available when `CRON_SECRET` is not configured and `ALLOW_LOCALHOST_CRON_BYPASS=true` is set. Do not use this on shared or externally reachable deployments.

## 1.7.1 - 2026-04-25

### Fixes (manufacturing-cost component, post-review)

- **Sync processors now handle the new types.** `MANUFACTURING_JOURNAL` and `MANUFACTURING_RECLASS` were missing from the Xero and QuickBooks sync-processor switches, causing queued rows to fail with `Unknown sync type` and never post. - **Reclass journal now captures the inventory leg.** Retro edits previously posted only the COGS delta on consumed units, leaving the remaining-inventory delta unposted (and skipping the journal entirely when no units had shipped).
