# Mintsoft Connector

Mintsoft is the first WMS connector behind the connector-agnostic WMS boundary (see [`wms-connector-boundary.md`](./wms-connector-boundary.md)). It covers stock alignment, ASN creation, product verification, bundle sync, returns polling, signed ASN booked-in webhooks, outbound order-dispatch push (Phase 8), inbound dispatch ingestion (despatch → IMS shipment, with per-part partial shipments to the storefront for split orders and survivor reconciliation for merged orders), and order-status tracking on sales orders.

## Authentication And Bindings

- Connection settings are managed in Sync settings and stored as connector settings.
- Warehouse-level behavior is controlled by `ExternalWmsBinding`.
- `WmsStockSyncMode` decides whether a warehouse is notification-only or allowed to align IMS quantities to Mintsoft.
- `WmsReturnsMode` controls returns polling/webhook behavior per warehouse.

### Authentication mode

Mintsoft's `POST /api/Auth` does **not** hand out a session token. It **mints a
new tenant API key and invalidates the previous one** — the key belongs to the
Mintsoft tenant, not to the caller. Three systems share that tenant:

- this connector
- the `woocommerce-mintsoft-sync` order sweep + webhook
- the `woocommerce-mintsoft-shipping-label-sync` label service

So whenever one of them logs in, the other two are silently knocked offline
until their own refresh cycle runs. Issue **one fixed key** and point all three
at it.

Set the mode under Integrations → Mintsoft → Edit Mintsoft Connection:

| Mode | Behaviour |
|---|---|
| **Username & password** (default) | Logs in and auto-renews the 24-hour key. **Regenerates the tenant key on every renewal.** |
| **Fixed API key** | Uses the configured key verbatim and **never** calls `/api/Auth` — not on a cache miss, not on expiry, not on a 401. A blank key is a hard error, never a fall back to logging in. |

While `PRODUCER_HOLD_ENFORCED_DESTINATIONS` names Mintsoft and the installation is not in its live phase, username & password mode does not log in at all: a renewal or connection test is refused before anything is sent (`MintsoftKeyMintingHeldError`, a hold text with no credential in it), because a new key would invalidate the one the other integrations use. Reads continue on a stored unexpired key or a fixed key. With the variable unset nothing changes.

Storage notes:

- The fixed key lives in its own setting, `mintsoft_static_api_key`. It is
  deliberately **not** stored in `mintsoft_api_key` — that key is the cache for
  the rotating 24-hour token, so a credentials-mode refresh would overwrite it.
- Both are in `SENSITIVE_SETTING_KEYS`, so both are encrypted at rest.
- Saving the connection clears the cached rotating token, so no stale token
  survives a switch in either direction.
- In fixed-key mode the connection test does a read-only authenticated `GET`
  rather than logging in — the credentials test would otherwise invalidate the
  very key it is testing.

When switching the estate over, set the key and the mode on **all three**
systems close together: any system still in credentials mode will regenerate
the key and break the ones already switched.

### Connection Test Gate

Mintsoft connector settings cannot be marked active until a **Test Connection** succeeds against the current credential fingerprint. The save form runs the test inline before persisting, so saving with bad credentials is impossible from the UI. The fingerprint (a SHA256 of the credential payload) is written to the activity log on each test, so silent credential rotation is visible in the audit trail. Changing any byte of the credentials invalidates the gate and forces a fresh test before sync resumes.

## Stock Alignment

- Mintsoft stock is normalized and sorted before comparison with IMS.
- **The figure compared is ON HAND (o3d-4pzls).** `GET /api/Product/StockLevels` returns two numbers per SKU: `TotalStockLevel` is physical **on hand** (including units allocated to open orders) and `Level` is **available** (on hand minus allocated). IMS `stock_levels.quantity` is on hand (reservations are tracked separately in `reservedQty`), so the sync compares, snapshots (`wms_stock_snapshots.externalQty`), reports and aligns on `TotalStockLevel`; `Level` is carried on the stock line (`available`) for diagnostics only and is never used as a fallback. The fields are read by exact name. A response is **refused as a whole** (the run ends FAILED with the reason, nothing is snapshotted, flagged or aligned) when it is not an array, or any row has no `SKU`, no `TotalStockLevel`, a `TotalStockLevel`/`Level` that is not a non-negative integer number (null, string, negative, fractional), a `Level` above `TotalStockLevel`, or when one SKU appears twice. Duplicate rows are never summed or picked between.
- After this change the first sync on a warehouse shifts IMS-vs-Mintsoft comparisons by exactly the units Mintsoft has allocated to open orders (the live probe of EAR2/MIL1 showed 2 and 28 units across 13 SKUs). Under **Align To WMS** the previous behaviour would have aligned IMS down by those allocated units.
- Open discrepancies are stored in `wms_stock_discrepancies`; partial unique indexes prevent duplicate open discrepancy rows for the same connector, warehouse, category, and product/SKU.
- Alignment should only change IMS stock after the binding permits it and discrepancy thresholds are satisfied.
- **Warehouse Bindings row actions are labelled buttons, each confirmed where it matters.** **Go live…** (enabled only for an unconfirmed `ALIGN_TO_WMS` binding with a completed dry run) opens a dialog that names the warehouse, says that going live turns on live stock corrections (align-up always; align-down only when the binding has an align-down reason), and enables **Go live** only after the warehouse code is typed. `confirmMintsoftAlignmentMode` refuses unless the call carries `{ confirmed: true, typedName }` and `typedName` equals the binding's warehouse code, before it looks for the dry run or writes anything; the `settings.company` permission check still runs first. **Deactivate…** opens a confirmation (client-side) before the binding is switched to disabled. Saving a binding that points at a different IMS warehouse, Mintsoft warehouse id or connection clears its live-corrections confirmation and stamps `pairingChangedAt`, so it returns to a dry run and needs a fresh review and typed confirmation. A dry run only counts as evidence for going live if it started after `pairingChangedAt` and its recorded summary names the binding's current Mintsoft warehouse id and connection; runs recorded before the connection was stamped, and every run that existed when the column was added (existing bindings are stamped with the migration time), are treated as not matching. The confirmation write is a compare-and-set on the warehouse, Mintsoft warehouse id, connection and `pairingChangedAt` that were read for approval, so a re-point made while someone is confirming makes the confirmation fail instead of arming the new pairing. **Go live…** is enabled by the same rule. Saving a binding is itself atomic: under the binding's row lock (the one a stock-sync reservation takes before it records a run) the save writes only if the row still has the pairing, mode and approval it was computed from, and otherwise refuses with "The binding changed while you were saving it. Reload the page and try again." Under the same lock, pointing a binding at a different IMS warehouse, Mintsoft warehouse or connection is refused while a stock sync for it is running (RUNNING with a heartbeat inside the reclaim window; a dead run does not count), because a running sync keeps the pairing and dry-run flag it started with. Remaining window: a sync that starts after the save sees the new pairing, which is correct; a save that is refused for a running sync can simply be repeated once the run finishes. The handover a save writes when it disables a binding or takes it out of Align To WMS (a SUCCEEDED stock-sync job plus the binding's last-sync stamps) is written inside that same transaction, after the running-sync check and the successful compare-and-set, so a refused save leaves no handover and cannot reset the stale-sync alert. The check that unreconciled alignment credits block leaving Align To WMS only reads, so there is nothing of it to roll back. **Sync now** runs a notification-only stock sync and needs no confirmation. Success and error messages for these actions appear beside the Warehouse Bindings heading.

### Align up (Mintsoft holds more)

Upward deltas are absorbed into open ASN lines as provisional goods-in receipts (cost layers from the source PO/transfer line), tracked as alignment snapshot credits that the booked-in webhook later reconciles. A delta no open ASN line can explain stays a manual discrepancy.

**A PO-backed align-up is a receipt writer, and posts like one (o3d-6nd55).** It credits stock and
lays a purchase-order-linked FIFO cost layer, so it is the third path that raises inventory value from
a purchase order — beside the receipt entered in IMS and the WMS booked-in webhook. Two things were
wrong and are fixed together:

- **the cost was always zero.** The branch read `landedUnitCostBase ?? unitCostBase`, and
  `landedUnitCostBase` is `Decimal @default(0)` and NOT NULL while `createPurchaseOrder` never sets
  it — so the `??` could never fall through and an ordinary purchase order aligned up at a unit cost
  of **zero**: a zero-cost cost layer and a zero-value stock movement for goods that cost real money.
  Inventory was understated for those units for ever, and no journal would have repaired it because
  the cost itself was wrong. Align-up now calls `computeGrossUnitCostBaseByLine` — the same helper the
  IMS receipt and (since o3d-8f0p6) the book-in use: the goods cost plus that line's share of the
  order's own and its linked freight orders' additional cost lines. **One value feeds the movement,
  the cost layer and the journal.** A genuinely free line (a sample, a warranty replacement) has a
  zero goods cost, so the gross cost is zero, stock is still credited and nothing is posted — which is
  correct, and is why no null-vs-zero column change was needed;
- **it posted nothing.** No `STOCK_RECEIPT` journal and no transit subledger row. It now queues the
  same two-line journal the IMS receipt does — **DR Inventory / CR Stock in Transit** — plus the
  signed transit subledger row for −value, **in the same transaction as the movement, the cost layer
  and the stock level**. All of it lives or none of it does: if the enqueue fails, the alignment
  credits no stock and the ASN line does not claim to have absorbed the units, so the next sweep tries
  again.

The journal's idempotency key is `wms-align-up:<asnLineMapId>:<movementId>`, so it can collide with
neither the webhook's `wms-purchase-receipt:<poId>:<eventId>` nor the IMS receipt's
`purchase-receipt:<poId>:<receiptRef>`, and one sweep crediting two ASN lines of one order posts two
journals for two disjoint quantities. **The two WMS paths do not double-post, in either direction:**
align-up journals the quantity it credits and records it on `wms_asn_line_maps.qtyAccountedViaSnapshot`
in the same transaction, which is exactly the `coveredBySnapshotQty` a later book-in subtracts before
journalling; and the reverse is `resolveWmsAsnLineResidualQty`, which caps align-up at
`expectedQty − max(qtyAccountedViaSnapshot, lastProcessedReceivedQty)`, so units a book-in already
landed are outside every allocation align-up can make.

**Transfer-backed align-up allocations post nothing, deliberately** — a transfer moves units the
business already owns between its own warehouses, so their value never left inventory and never
entered *purchase* goods-in-transit. `app/actions/transfers.ts` queues no accounting sync either.

**The cost inputs are LOCKED, and so is the account mapping (o3d-6nd55 r2).** Round 1 read both with
no lock and tried to defend itself by re-reading and refusing on a difference, which holds nothing: a
re-read sees only a change that has *already* committed, so a change landing after it still ends up in
committed books. Both are now locks held to commit:

- **the cost rows** — `purchase_orders`, then `purchase_order_lines`, then `freight_cost_lines`, for
  the primary order *and* every linked freight order — taken at step 2 of the global row-lock order
  (`lib/domain/wms/transfer-asn-lock-order.ts`). That sub-order is not new: it is the one
  `app/actions/purchase-orders.ts` already uses in both of its invoicing transactions. A landed-cost
  or freight edit therefore cannot commit between the moment the alignment reads a cost and the moment
  it commits the layer and the journal for it. A PO-backed ASN line whose order appeared *after* those
  locks were taken is refused as a raced row and left to the next sweep, exactly as a raced transfer
  is. Every cost is then read in one pass **before** any movement, layer, journal or stock row is
  written, so the read-then-write order is structural rather than something a reader has to verify;
- **the two account codes** — through `lockAccountingMappingSelection`, which is the *existing*
  accounting-selection lock (the same advisory key `queueAccountingSyncTx` already takes) with the two
  mapping rows added to its row set, so there is one lock and one order rather than a second one. It is
  read once per alignment and reused, so an alignment spanning several purchase orders cannot put
  earlier orders on the old mapping and later ones on the new one. A remap is **serialised**, not
  refused: it waits and lands once the alignment commits.

**A CANCELLED linked freight order contributes nothing (o3d-6nd55 r2).** Cancellation leaves the link
row in place, marks the freight order `CANCELLED` and the link unallocated, and both landed-cost
recalculation paths already exclude it — so including it here would have added freight the business had
cancelled into the cost layer, the movement and the journal, and disagreed with what recalculation
computes for the same units. The predicate has one definition,
`CONTRIBUTING_LANDED_COST_LINK_WHERE` in `lib/domain/purchasing/landed-cost-service.ts`, which all
three readers derive from. It filters on the freight order's **status** and deliberately not on
`LandedCostLink.allocated`: `allocated` records whether the uplift has been written to
`landedUnitCostBase` yet, and valuing a receipt whose freight is not yet allocated is the whole purpose
of the shared gross-cost helper.

Why this had to be fixed at the source rather than in a sweep: nothing downstream derives a receipt
journal from a stock movement, and the reconciliation that should have caught the omission **hid** it.
The Xero daily batch does not read `stock_movements` at all; its inventory reconciliation posts
Inventory ↔ *Rounding difference* and only for a sub-unit `sweep` gap (a receipt-sized gap is `flag`,
surfaced and never posted); and the transit reconciliation aggregates `transit_subledger_movements`,
which are written **at post time**, so a posting that never happened is absent from *both* of its sides
and that window ties out exactly. Proven by
`tests/concurrency/mintsoft-align-up-stock-receipt-journal.concurrent.test.ts`.

### Align down (Mintsoft holds less — shrinkage / already-shipped)

Downward deltas are auto-corrected by posting a negative stock adjustment (FIFO consumption + inventory GL journal via `applyStockAdjustment`), but only when EVERY gate passes; otherwise the discrepancy stays open carrying the hold reason:

1. **Write-off reason configured** — the binding's *Align-Down Write-Off Reason* (an active `AdjustmentReason` **with a GL account code**) must be set; the write-off posts `DR reason-account / CR Inventory`. No reason → align-down never runs.
2. **Thresholds configured and not breached** — the binding's discrepancy thresholds double as the auto-fix ceiling; unconfigured thresholds or a breaching delta stay manual (a WMS API glitch must not write off a warehouse).
3. **No pending inbound** — open ASN lines with outstanding expected receipts or unreconciled alignment credits hold the correction (the lower Mintsoft balance may be receipt timing, not shrinkage).
4. **Persistence across two runs** — the same delta must have been recorded by a *previous* sync run, so in-flight dispatch webhooks/sweeps get a full cycle to land before stock is written off.
   - **In-flight despatch (gate 4b, o3d-hqvrp.118)** — before the persistence gate, align-down holds while `loadInFlightDispatch` (`lib/connectors/mintsoft/sync/in-flight-dispatch.ts`) is positive: allocations on orders with a Mintsoft push link, not yet SHIPPED/COMPLETED/DELIVERED/CANCELLED in IMS, unless the cached WMS status (`wms_order_status_snapshots`) is FRESH and not despatched (fresh = fetched at or after the run start, or within 45 minutes: the sweep's 30-minute stale threshold plus its 15-minute cron). A despatched, missing or stale status, or a dead-lettered/quarantined dispatch, holds. The held orders are logged (`mintsoft_align_down_held_in_flight`) and the gate is re-checked under the stock-level lock at the write. It adds no live Mintsoft read. The one-cycle wait above only protects a despatch that lands within one interval; this holds for as long as the despatch is unrecorded.
5. **Reservations** — on-hand is never driven below `reservedQty`; the oversell aftermath (orders reserving stock that doesn't exist) must be resolved by an operator.

Applied corrections log `mintsoft_align_down_applied` (WARNING) with before/after quantities and the movement id, and are idempotent per sync job. Dry-run mode (before alignment confirmation) previews align-down the same way it previews align-up.

## ASN Flow

- IMS creates outbound ASN payloads for purchase orders and transfer lines.
- A **transfer** ASN line's expected quantity is the line quantity less what has already **landed**,
  by the one definition in `lib/domain/inventory/transfer-landed-quantity.ts`: `qtyReceived` plus any
  `wms_asn_line_maps.qtyAccountedViaSnapshot` credit a receipt has not yet absorbed. It is deliberately
  NOT `qty - qtyReceived` (o3d-zzgp): the stock-sync alignment above raises stock and lays cost layers
  without writing `qtyReceived`, so that subtraction asked a live warehouse to expect units already on
  its own shelves. The reservation and its pre-push revalidation read the same figure under the
  transfer's row lock, so they cannot disagree and refuse every create. **Purchase-order ASN lines are
  sized the same way** (o3d-papk): `qty` less the PO line's *landed* quantity, by the one definition in
  `lib/domain/inventory/po-line-landed-quantity.ts` (see below), read under the `purchase_orders` row lock;
  the branded figure travels to the wire quantity and the pre-push revalidation compares it, not a number.
- A **retry** of a transfer ASN create never deletes or resizes a reservation that already holds
  credit. `wms_asn_line_maps.qtyAccountedViaSnapshot` is the ONLY record that the alignment brought
  those units in and costed them, so the reservation is **retired** instead: `closedAt` is set (which
  removes it from the alignment candidates, the reuse lookups and the overdue-ASN watchdog), each
  line's `expectedQty` is shrunk to exactly what that row was credited so its own residue is zero, and
  the shrunk figures are recorded in the line's `note`. Any quantity still outstanding is then reserved
  on a NEW ASN with a zero credit, so the historical credit and the fresh remote expectation are two
  different rows rather than two meanings of one. A reservation that holds no credit is still deleted
  or resized in place, which is what keeps a retry loop from leaving one closed row per attempt. A
  retired reservation stays visible in the transfer's ASN list as a closed `CREATE_PENDING` row.
  The credit check and the disposal are ONE transaction that first takes the global lock order
  (`stock_transfers` → `wms_asn_maps` → `wms_asn_line_maps`, see
  `lib/domain/wms/transfer-asn-lock-order.ts`), so an alignment cannot credit a line between the
  check and the delete; it waits on the transfer row and re-reads afterwards. The delete also refuses
  a header whose lines visibly hold credit, but that is a backstop only — it is evaluated against the
  delete statement's own snapshot and does not stop a credit that commits mid-statement.
  A retirement (or the delete of an uncredited emptied reservation) is COMMITTED even when the same
  attempt then refuses the create — "nothing outstanding", "not linked to a Mintsoft product": the
  reservation transaction returns the refusal and the action raises it after commit, because a refusal
  thrown inside the transaction would roll the retirement back and leave the reservation open.
  **The same rule now applies to a purchase-order ASN create** (o3d-papk): the retry, the post-mismatch
  discard and the finalize conflict branch all dispose of a pending reservation through the one
  generalised `disposePendingAsnReservation` (`lib/domain/wms/pending-asn-retirement.ts`), which takes
  `purchase_orders` (step 2b, a gate only) → `wms_asn_maps` → `wms_asn_line_maps` first. A credited PO
  reservation is retired (the retired row keeps counting in the line's landed quantity) and the landed
  outstanding is reserved on a NEW reservation with a zero credit; one holding no credit is still deleted or
  resized in place. Operator refusals that can follow a disposal write are returned, not thrown, so the
  retirement commits. The claim also refuses a retired row (`closedAt IS NULL`) for both creators.
  **Two requests that reserved the same row** (o3d-papk, Codex round 2): the discard only ever disposes of an
  UNCLAIMED, OPEN reservation (`status = CREATE_PENDING AND closedAt IS NULL`; the claim is what moves a row to
  `CREATE_IN_FLIGHT`), so a request whose revalidation failed cannot retire the row another request has claimed and
  is pushing. The finalize is a compare-and-set under the parent and header locks, before any write: the row must
  still be open, in the status its own step left it in (`CREATE_IN_FLIGHT` after a claim, `CREATE_PENDING` for a
  duplicate-recovery adoption) and carry the same lines at the quantities that were reserved. If it does not, the
  finalize FAILS CLOSED: nothing is written to the row (it is not reopened, mapped or resized), and the id of the
  ASN the warehouse did create is retained on the failed job's summary (`unrecordedExternalAsnId`) and a WARNING
  activity entry, exactly as for an ASN whose read-back did not verify; the next create attempt is refused by name
  by the duplicate matcher (or adopts the ASN if the row has come to match it), so no second ASN is created and the
  orphan is neither lost nor silently adopted. Both creators.
- Mintsoft callback metadata preserves the source type, source line, product, and expected quantity.
- Booked-in webhook receipt is idempotent via `wms_inbound_receipt_events`.
- Accepted webhooks are persisted and acknowledged with `202 Accepted`; stock and purchase-order mutations run later through `/api/cron/mintsoft-webhook-sweeper`.
- Retry state is stored in typed `wms_inbound_receipt_events` columns: `processingStatus`, `processingAttempts`, `nextRetryAt`, `deadLetteredAt`, and `lastError`. The sweeper selects pending/due rows from these fields directly.
- Booked-in processing looks up the referenced ASN directly by id through the WMS connector. Bulk ASN listing remains available for reconciliation/backfill flows and as a temporary rollback path.
- **The rule for creating an ASN at a live warehouse, stated once (o3d-bhvu rounds 6–7).** A create proceeds **only on a positive proof that the ASN is not already there**; every other outcome — a remote state that cannot be read, cannot be proven, or merely differs from what IMS holds — refuses by name and names the remote ASN id. That rule lives in `lib/connectors/mintsoft/api/asn-creation-rule.ts` and both sides of the create go through it: the pre-create duplicate matcher (`asn-recovery.ts`, called by both creators) and the post-create read-back (`client.ts`). It is one comparison (`compareMintsoftAsnAgainstExpectation`) and one table of which differences are determinate evidence of absence (`isProofThatMintsoftAsnIsNotThisOne`), with a single gate (`requireMintsoftAsnCreationVerdict`) that is the only function in the connector able to answer "create one". **A proof of absence needs two different things (round 7):** that the remote ASN is a *different consignment* — only readable content that differs shows that, so another `POReference` or a set of source lines sharing none of ours — **and** that it is not the ASN a create whose response was lost left behind, which only IMS's own `wms_asn_maps` can show, because "lost" means *IMS never recorded it*. An overlapping line set and a differing quantity have the first and not the second, so for those two, and only those two, the table takes the ASN's mapped state: **mapped is proof of absence, unmapped refuses, and a map that could not be read refuses.** Six review rounds each found the same class of defect in a different branch, which is why the answer is in one place rather than at each decision point.
- **Duplicate recovery before an ASN push reads the whole ASN list, or refuses (o3d-bhvu).** Before creating an ASN, both creators look for one an earlier attempt may already have created. They read `GET /api/ASN/List`, not `GET /api/ASN`: live Mintsoft answers that with 405, because it is the create route.
  - **How the list is read.** The list pages at 100 (`Limit` above 100 is an HTTP 400) and its row order is not stable across pages. IMS reads it page by page with `Limit=100` and `IncludeASNItems=true` **across the whole tenant**, not just the ASN's warehouse, and gives up after 50 pages. A read is accepted only when all of these hold, and every other outcome aborts the attempt:
    - every page before the last returned exactly 100 rows;
    - **the short page that ends the scan is proven to be the end**, by asking for the page after it and requiring `[]` (live Mintsoft answers a page past the end with an empty array). A short page used to be *assumed* to be the end, and a truncation that repeats — a server answering page 1 with 23 rows every time — then looks exactly like a complete list on every re-read;
    - no ASN ID appeared twice in the scan, and two consecutive scans returned exactly the same set of ASN IDs. Together with the two rules above this excludes a row that moved across a page boundary: the scan collects exactly as many distinct rows as the last page says the tenant holds, so omitting one that exists would mean collecting one that had been deleted mid-scan — and Mintsoft's delete is permanent with no ID reuse, so that row could not come back in the next scan, which would then disagree;
    - **an independent, differently-filtered read agrees.** Before the full scans, IMS reads `GET /api/ASN/List?SinceLastUpdated=<30 days ago>` (IDs only, same warehouse scope). Those rows normally fit in one page, so that read has no page boundary to lose a row at, and any ASN it serves must appear in the accepted scan. This is the only check that can catch a full scan which omits the same ASN every time; it can only ever refuse — an ASN it does not serve changes nothing.
    - What remains assumed, and cannot be established from this API (no total count, no cursor, no ordering parameter, no filter by our reference): that `PageNo`/`Limit` are a window over the whole current set rather than a walk that could skip a row identically every time. This reader therefore fails closed. The complementary answer now lands with the create itself: a successful create is verified by reading the ASN back by id and requiring the `POReference` and every `SourceLineId` sent, so a lost response is resolved by reading what was written rather than by proving a tenant-wide absence.
  - **How an ASN counts as the same one.** The reference must equal Mintsoft's `POReference` exactly (surrounding whitespace ignored; `PO-1` never matches `PO-10`). It must carry the same number of items **as Mintsoft returned them** — an item whose `SourceLineId` is determinately not one of IMS's (a numeric one, where every IMS source line id is a cuid string) still counts, so an ASN with an extra item is not this one — and each reservation line must be present by `SourceLineId` at its expected quantity. Matching on `SourceLineId` needs Mintsoft to store and return IMS's line id unchanged, which is **now proven live** (o3d-vcw8, 2026-09-24: a created ASN returned the cuid-shaped `SourceLineId` verbatim on its `ASNItem`, and `POReference` round-tripped exactly).
  - **Two ASNs that both match are refused, not ranked.** The list's row order is not stable, so "the newest wins" would mean "whichever page it came back on wins" — and two ASNs carrying this reference and these line ids mean the duplicate has already happened. The error names both ids and nothing is created.
  - **A quantity only rounding could explain is refused too.** Mintsoft stores `ASNItem.QuantityExpected` as a whole number, so a reservation line of 2.5 comes back as 2 or as 3 by a rule Mintsoft does not publish. Reading that as "no match" would create a second ASN at a live warehouse; adopting it would record an expectation IMS never asked for. The error names the ASN, the line and both figures. A difference rounding *cannot* explain is refused as well, by the conflict rule below — what differs is which error names the state, because "Mintsoft rounded our 2.5" and "somebody changed the quantity" need different things done about them.
  - **An expected quantity that cannot be READ is refused too, and outranks a quantity that merely differs.** If a row carries this reference and exactly these `SourceLineId`s but an item comes back with no usable `QuantityExpected` (the key absent, `null`, a string, a `NaN`), IMS cannot tell that ASN apart from the one an earlier attempt created. Reading it as "a different quantity" answered a degraded response with "create another one". The error names the ASN, the line and the expected figure. Likewise an item that carries one of IMS's `SourceLineId`s but no item `ID` of its own is refused by the list normalizer rather than dropped: dropping it made the ASN look like somebody else's, because the item count still counted it.
  - **A quantity that merely DIFFERS is an unresolved conflict, not a different ASN (o3d-bhvu round 6).** A row carrying this reference and *exactly* these `SourceLineId`s whose `QuantityExpected` differs by more than rounding could explain used to be answered with "no such ASN exists" — and the creator pushed a second inbound ASN at a live warehouse for lines the first already covered. That state is what an ASN a lost create really made looks like once the source quantity has changed (the reservation checks validate the CURRENT LOCAL quantities, never whether the earlier remote ASN exists); it is also what an operator's edit at the warehouse looks like, and what a later partial over the same lines looks like. Nothing available to the matcher tells them apart, so it is refused by name, naming the ASN, the line and both figures. **Round 7 supplies the discriminator round 6 was missing** (o3d-54al): if IMS has already mapped that ASN id it is a partial IMS recorded, not what a lost create left behind, so it is proof of absence again and a second legitimate partial over the same lines goes through without an operator. An *unmapped* quantity conflict — an ASN a lost create made whose quantity has changed since, or an operator's edit at the warehouse — still refuses by name.
  - **An overlapping line set is refused unless IMS has already mapped that ASN (o3d-bhvu round 7, Codex HIGH; this is o3d-54al's already-mapped check).** A row carrying this reference whose line set merely *overlaps* the reservation's — the ASN at the warehouse holds `{a,b}`, the retry covers `{a,b,c}` because a line was added to the order between a create whose response was lost and the retry (`reserveAsn` refreshes a pending reservation's lines from the order's current outstanding lines, which is what makes the sequence reachable) — used to be read as a different ASN, and a second inbound ASN went out for `a` and `b`: the warehouse expected the same goods twice. It cannot simply be refused, because every ASN for a purchase order carries the *order's* reference and a second ASN over a different set of its lines is how a partial delivery works — refusing every overlap would put an operator in front of every multi-ASN order. **The ASN map separates the two populations exactly:** a create whose response was lost leaves an ASN with no `wms_asn_maps` row, so an ASN IMS has *mapped* is a partial it recorded and stays proof of absence, while an *unmapped* overlap is the lost-response shape and refuses by name (`MintsoftAsnRecoveryLineSetOverlapError`), naming the ASN and the shared source lines. Both creators read the map (one helper, `readMintsoftAsnMapKnowledge`) and pass the ids into the matcher, which stays pure; **if that read fails it passes `unreadable`, not an empty set**, and the two verdicts that depend on the map refuse (`MintsoftAsnRecoveryMapUnreadableError`) — an unreadable map is not permission, exactly as an unreadable list, line identity or quantity is not. Verdicts that need no map (another reference, a line set sharing nothing with ours) are unaffected, so an unreadable map does not block an ordinary create.
  - **A line identity that cannot be read is refused on ANY row carrying this reference, before the line sets are compared.** If a row with this `POReference` has an item whose `SourceLineId` is absent, `null` or blank — or an item that is not an object at all — that row cannot be excluded: it may be the ASN an earlier attempt created, with one item's identity degraded on the way back. Dropping the item made the line sets differ, the row read as somebody else's, and a second ASN was pushed for lines the first already covered. The error names every such ASN, in sorted order. A **determinate** identity that simply is not IMS's (a numeric `SourceLineId`) is not unreadable: it is another integration's item, dropped and counted as before.
  - **A match at another warehouse is refused, never adopted and never duplicated.** This is the case where the warehouse binding changed between an attempt whose response was lost and the retry. The error names the ASN and both warehouses.
  - **Any read that cannot be shown complete aborts the attempt without creating anything.** That includes a failed page, more than 50 pages, a short page the next page contradicts, a row the recently-updated read served and the full scan did not, a row without an ID, a row returned without its items, and an item carrying a `SourceLineId` without an item `ID` (each error names the ASN id). The aborted attempt is left `CREATE_PENDING`. While that condition persists, **ASN creation fails everywhere in the tenant**, because the scan is tenant-wide, until the offending ASN is fixed in Mintsoft or the list shrinks below 5,000 ASNs. This is deliberate: a partial list read as "no such ASN" would create a duplicate at a live warehouse.
  - **A recovered ASN the warehouse has ALREADY booked in is reconciled, not recorded as still to arrive (o3d-bhvu round 8, Codex HIGH).** 198 of this tenant's 220 live ASNs are `COMPLETE`, so the ASN a lost create left behind is *usually* one the warehouse has already received against. The matcher still ignores the status — a COMPLETE ASN carrying this reference and exactly these line ids and quantities **is** the ASN the lost create made, and adopting it is right; what the status changes is what is **owed** once it has been adopted. Until round 8 the list normalizer never read the status at all (`status: null`) and the creators' normalizer collapsed that — and every value it did not recognise — to `OPEN`, so a booked-in ASN was written down as an ASN still to arrive and the only reconciliation run was `replayMintsoftBookedInEventsForAsn`, which re-drives receipt-event rows that **already exist**. A callback that was never delivered leaves none, so nothing was replayed: IMS reported a successful recovery while the goods on the shelves were in no IMS stock figure and no cost layer until somebody pressed *Re-check*. Now:
    - **the status is read and interpreted in one place** (`lib/connectors/mintsoft/api/asn-status.ts`), against the 13 statuses `GET /api/ASN/Statuses` served live on 2026-09-24. `ASNStatus` is an object carrying `Name` alongside a numeric `ASNStatusId`, and it has **no `ExternalName`** (that grouping is order-only), so there is nothing on the wire to classify by and the table is enumerated deliberately — which is also what makes a fourteenth status safe: it is not in the table, so it reads as **unknown**;
    - **unknown is neither open nor booked in.** A status that is absent, blank, or outside the table refuses (`MintsoftAsnStatusUnreadableError`) **before anything is written**. Guessing `OPEN` loses the stock; guessing `BOOKED_IN` invents a receipt;
    - **and Mintsoft's vocabulary is the only one a remote status is read against (o3d-bhvu round 9, Codex HIGH).** Round 8's interpreter also carried a table of IMS's own `WmsAsnStatus` names, and the two vocabularies overlap textually, so a remote `ASNStatus.Name` of `OPEN` — with an `ASNStatusId` nobody recognised beside it — was accepted as *known*, recorded `OPEN` and skipped the receipt recheck; `BOOKED_IN` and `PARTIALLY_BOOKED_IN` arriving from the wire even **invented** a receipt. The IMS-name table is **deleted**, not relocated: `interpretMintsoftWireAsnStatus` resolves the 13 published statuses and nothing else, `WmsAsnStatus` is an output of that module and never an input, and `tsc` enforces that no IMS status name can be added to Mintsoft's table (`_VOCABULARIES_ARE_DISJOINT`);
    - **`ASNStatus.Name` and `ASNStatusId` disagreeing is unknown, not a precedence contest (round 9).** Round 8 read the name first and used the id only as a fallback, so an unrecognised id beside a recognised name was discarded and two recognised fields naming different statuses were resolved silently by order. A disagreement is evidence the wire shape is not what this code thinks, and the two directions are not symmetric in cost, so **every** status signal the row carries must resolve in the table and all of them must name the same status. Otherwise the ASN refuses, and the refusal names the fields and what each said. Against the live tenant this costs nothing: all 220 ASNs sit in one of the 13 statuses and ASN 6114 served the same status on all three fields;
    - **the two fields Mintsoft's contract names are STRICT; the guessed spellings are not (round 9, self-review).** `ASNStatusId` and the `ID` inside the `ASNStatus` object are `int32` in the swagger and were integers on every live read, so one of them **present** carrying something that is not an integer is itself a wire-shape change: it counts as an unreadable signal and the ASN refuses, naming the field and the value. Before this, `{ ASNStatus: { Name: 'COMPLETE' }, ASNStatusId: '3' }` resolved to `COMPLETE` and the `'3'` vanished — the round-9 finding with the types swapped. `null`/`undefined` stays *absent*: a warehouse may legitimately say nothing there, and the remaining signals — or the absence of all of them, which also refuses — decide. The other spellings the reader accepts (`Status`, `status`, `AsnStatus`, `asnStatus`, `asnstatus`, `AsnStatusId`, `asnStatusId`, `StatusId`, `statusId`) are **guesses** inherited from the pre-round-8 reader and live Mintsoft serves none of them: a usable integer on one is still a signal, but anything else is ignored, because refusing on some response wrapper's unrelated `status` would block ASN creation tenant-wide over a field this API does not have. Narrowing the lists to the canonical two is tracked on **o3d-nvy1**;
    - **`closedAt` is never set from the warehouse's status.** It means *the receipt is accounted for* — it removes the ASN from the alignment's candidate query, the overdue-ASN watchdog and the post-maintenance recheck sweep — so setting it on adoption would close the very populations that would otherwise catch the missing stock. The booked-in service sets it, from the quantities it really booked in;
    - **a booked-in recheck is enqueued after mapping**, for any status where goods may already have been received (`BOOKEDIN`, `COMPLETE`, `PARTIALLYBOOKED`, `BOOKEDIN-PARTIAL`, `DISCREPANCY`, the put-away statuses — and `DELIVERED`, which is *recorded* `OPEN` but still asked about, because a recheck is idempotent and a receipt nobody looks for is stock that never arrives). It reconstructs the trigger; `processBookedInEvent` re-reads the ASN and applies only the delta, so the warehouse stays the authority;
    - **and it cannot end quietly.** Reconciled → ordinary success. Left pending, awaiting review or failed → the action still succeeds but says so in the operator's message, because an event row exists and the sweeper will retry it. Nothing at all (the recheck threw, or applied nothing and left no row) → the action **fails**, the job is marked FAILED and an ERROR activity entry (`mintsoft_asn_receipt_unreconciled`) names the ASN. The ASN stays mapped in every case, so no duplicate can go out; the remedy is *Re-check* on the ASN table.
    - **Known gap, tracked separately (o3d-btiw).** The shared ASN line normalizer still does not read the live item's `QuantityReceieved`/`QuantityBooked`, so a recheck against live Mintsoft currently computes a **zero** received quantity for every line. Round 8 closes "no reconciliation is even attempted"; whether the attempt moves any stock depends on o3d-btiw, which is open.
  - **What recovery still does not look at.** Two narrower cases are also left, deliberately: a **rounding-explainable** quantity and a **warehouse mismatch** refuse whether or not the ASN is mapped, because their content is indistinguishable from (or identical to) what is about to be sent, so nothing has shown a different consignment; and if *every* line of a purchase order were deleted and re-added between a lost create and the retry, the earlier ASN would share none of the new line ids and would read as unrelated.
- **ASN creation, the contract Mintsoft actually accepts (o3d-vcw8, proven live 2026-09-24).** The create is `PUT /api/ASN` — there is no `POST /api/ASN`; the swagger's POST route is the UPDATE (`POST /api/ASN/{id}`), which is why live `GET /api/ASN` answers 405. The body is a `NewASN`: `WarehouseId`, `POReference` (**not** `Reference`), `Items` (**not** `Lines`, each with `SourceLineId`, `ProductId`, `SKU`, `Quantity`), `EstimatedDelivery` (**not** `ETA`), `GoodsInType` and a header `Quantity`.
  - `GoodsInType` is **REQUIRED** even though the swagger does not mark it so (a create without one comes back `Success: false, "Invalid GoodsInType:  See ASN/GoodsInTypes for valid types"`). IMS maps its packaging type onto the names `GET /api/ASN/GoodsInTypes` serves — `PARCEL`→`Carton`, `PALLET`→`Pallet`, `CONTAINER`→`TwentyFtContainer` — and sends `Carton` when a reservation names none.
  - The header `Quantity` is the **package count, not a quantity of goods** (it matched the item sum on only 3 of this tenant's 223 ASNs). Units live on `Items[].Quantity`.
  - `ClientId` is **never sent**, though `NewASN` declares it: our key is a client user and Mintsoft answers `"Client Users cannot specify a ClientId when creating an ASN!"`. Mintsoft sets it on the created row itself.
  - `Carrier` and the supplier reference have no `NewASN` field; they are preserved as labelled `SupplierNotes` rather than dropped.
  - **Every failure is an HTTP 200.** The reply is a `ToolkitResult`, not an ASN: all three live attempts returned 200, two with `Success: false`/`ID: 0` and one with `Success: true`/`ID: 6117`. IMS requires `Success === true` **and** `ID > 0` and raises the `Message` otherwise; trusting the status code recorded a phantom ASN id of `0`.
  - **The create is verified afterwards, not assumed — against the same rule duplicate recovery uses.** The `ToolkitResult` carries an id and nothing else, so IMS reads the ASN back with `GET /api/ASN/{ID}` (which is also where the `ASNItem.ID`/`SourceLineId` line mapping comes from) and requires **the `POReference`, the exact item set, every `QuantityExpected` and the `WarehouseId`** to be what was sent. Round 5 checked the reference and the *presence* of each `SourceLineId` only, so an ASN created at another warehouse, with an extra item, or expecting a different quantity — including Mintsoft's `int32` store turning a fractional quantity into a whole one — was recorded as though it were the request, with the reservation's own quantities written against it and the job marked succeeded (o3d-bhvu round 6). If the read-back does not confirm all of it, nothing is recorded, the error names the ASN id and **that id is retained** on the failed sync job's summary (`unrecordedExternalAsnId`) and on a WARNING activity entry (`mintsoft_asn_create_unverified`), because the ASN exists at the warehouse and only an operator can remove it — `DELETE /api/ASN/{id}` is Mintsoft's only removal (there is no cancel route and no cancelled status).
  - **A quantity Mintsoft cannot store never leaves the box.** `NewASNItem.Quantity` and `ASNItem.QuantityExpected` are `int32` and IMS quantities can be fractional, so a fractional line would be created at the warehouse as some other number and only then refused by the read-back — with the ASN already there. The create request is refused before it is built instead (`MintsoftAsnQuantityNotRepresentableError`, naming the line): nothing is sent and no ASN exists to reconcile. Adjust the outstanding quantity to a whole number and retry.
  - A new ASN lands on `ASNStatusId 1`/`NEW`. `ASNStatus` is an OBJECT and carries **no** `ExternalName` — that trick is order-only — so ASN state is derived from `ASNStatusId`/`Name` against the enumerated live status table (`asn-status.ts`, o3d-bhvu round 8), which since round 9 must find **every** status field the row carries in that table and find them all in agreement. o3d-btiw's remaining half is the ASN *item* quantities (`QuantityReceieved`/`QuantityBooked`), still unread.
  - Never test ASN creation against the live tenant without explicit owner sign-off: Mintsoft fulfils what it is sent. The e2e fake (`app/api/e2e/mintsoft/[...slug]/route.ts`) implements this same contract, including the two rejections above and the HTTP-200-with-`Success: false` shape.
- **There is no ASN callback field, anywhere in Mintsoft's API.** The string "Callback" occurs zero times in the whole API document, so the `CallbackUrl`/`AutoCallback` IMS used to send never reached anything and no ASN can carry a per-ASN URL. The booked-in callback is configured tenant-side in Mintsoft; the "Enable booked-in callback" toggle checks only that IMS is ready to receive one (public app URL set, webhook secret saved) and records the URL on the activity entry so it can be pasted into Mintsoft. Correlation of a booked-in event is by the `externalAsnId` the payload carries, or by `POReference` + `Items[].SourceLineId` over the sweep.
- `/api/cron/mintsoft-webhook-sweeper` drains at most `MINTSOFT_WEBHOOK_SWEEPER_PAGE_SIZE` persisted events per run. Leave it unset for the default `250`.
- Line deltas are applied only for previously unaccounted received quantities.

#### What IMS books in: `QuantityBooked`, not `QuantityReceieved` (o3d-btiw)

A live Mintsoft `ASNItem` carries four quantities — `QuantityExpected`, `QuantityReceieved` (Mintsoft's
own misspelling), `QuantityBooked` and `OnOrder` — and IMS reads them in exactly one place,
`lib/connectors/mintsoft/api/asn-quantities.ts`.

- **`QuantityBooked` is the quantity the booked-in path acts on.** IMS's book-in raises
  `stock_levels.quantity`, lays FIFO cost layers and moves the source line's `qtyReceived`; that is a
  STOCK figure, and IMS's stock at a WMS warehouse is also reconciled continuously by the stock-sync
  alignment against **the quantity Mintsoft holds in stock**, which only moves when an ASN is booked in.
  Crediting on the dock count instead would leave IMS higher than the warehouse, and an `ALIGN_TO_WMS`
  binding would then align DOWN over a receipt whose cost layers are already laid.
- **`QuantityReceieved` is carried, not discarded.** Units that have arrived but are not yet booked in
  appear as `remoteArrivedQty` on every dry-run line (so in `reviewDetails`), and a processed callback
  that finds any such line is logged as a **WARNING** naming the lines and both quantities. A partial
  book-in is normal, so it reports rather than blocks.
- **There is no fallback and no maximum between the two.** An unreadable `QuantityBooked` is
  `remote_quantity_unreadable` even when `QuantityReceieved` is perfectly readable.
- **`OnOrder` and the ASN header's `Quantity` are never read as goods quantities.** `OnOrder` tracked the
  expected quantity on one ASN and was zero on another; the header `Quantity` is a count of goods-in
  PACKAGES (`GoodsInType`) and equalled the sum of its items' expected quantities on only 3 of the
  tenant's 223 live ASNs.
- **An absent or unreadable quantity is never zero.** Zero means the warehouse booked nothing in. Absent,
  non-numeric, `NaN`, `Infinity` or negative means UNKNOWN: the line is pinned to what has already been
  accounted for, nothing is applied, and the callback goes to `REQUIRES_REVIEW` with an
  approval-blocked warning. Before o3d-btiw the shared normalizer looked for `qty`/`Quantity`/
  `receivedQty`, none of which a live ASN item carries, so every line read as a measured zero: a real
  callback applied nothing, and a second one reported the warehouse as having gone backwards
  (`remote_regression`).

The e2e fake (`app/api/e2e/mintsoft/[...slug]/route.ts`) serves `GET /api/ASN/{id}` in this shape, with
per-item `receivedQuantity`/`bookedQuantity` a seed can set, so an ASN that has arrived but is not booked
in is expressible. It previously served an invented `AsnId`/`Reference`/`Status`/`Lines` shape that
agreed with the equally invented reader, which is how every e2e run passed.

**A purchase-backed book-in commits, as of o3d-gles (#703).** It used to fail at commit: the service
wrote its `PURCHASE_RECEIPT` movement with `referenceType: 'WmsAsnMap'` while
`stock_movements_reporting_evidence_guard` accepts only `'PurchaseOrder'`, and o3d-btiw was masking
that — with every received quantity reading zero, the movement was never inserted. The service now
names the purchase order, so the guard's evidence join is satisfied by the cost layer the same
transaction lays. Transfer-backed book-ins write `TRANSFER_IN`, which the guard does not cover.

**A PO-backed book-in posts its accounting, as of o3d-8f0p6.** It used to write no `STOCK_RECEIPT`
journal and no transit subledger row where the manual receipt writes both, so stock and cost layers
landed while the transit clearing account never drained and the GL inventory balance was understated
against stock that was physically there. The book-in now queues the same two-line journal the manual
receipt does — **DR Inventory / CR Stock in Transit** — plus the signed transit subledger row for
−value, **in the same transaction as the movement, the cost layer and the stock level**. All of it
lives or none of it does: if the enqueue fails, the book-in commits no stock.

Four details are load-bearing:

- **the receipt cost is the SHARED gross cost, not `landedUnitCostBase`** (o3d-8f0p6 r2). That column
  is `Decimal @default(0)` and NOT NULL, and `createPurchaseOrder` never sets it — so the old
  `landedUnitCostBase ?? unitCostBase` could never fall through, and an ordinary purchase order was
  booked in at a unit cost of **zero**: a zero-cost FIFO layer, a zero-value movement and, once this
  path started queueing a journal, no journal at all. The book-in now calls
  `computeGrossUnitCostBaseByLine`, the same helper the manual receipt uses, and that one value feeds
  the movement, the cost layer **and** the journal. It is never worse than the old expression: once
  landed cost has been allocated the recalc writes `landedUnitCostBase = grossUnitCostBase`, so the two
  coincide. A genuinely free line (a sample, a warranty replacement) has a zero goods cost, so the
  gross cost is zero and nothing is posted — which is correct, and is why no null-vs-zero column change
  was needed;

- **the amount is the value this book-in actually laid layers for**, not the reconciled quantity.
  `qtyReceived` also covers `coveredBySnapshotQty` (units a prior stock-sync alignment already brought
  into stock and layered) and `reconciledManualQty` (units a manual receipt already journalled);
  journalling either would post the same inventory value twice;
- **the idempotency key is `wms-purchase-receipt:<poId>:<receiptEventId>`**, so a redelivered or
  replayed webhook cannot queue a second journal, and it can never collide with the manual path's
  `purchase-receipt:<poId>:<receiptRef>`. A genuinely new event booking a further quantity is a
  different receipt and gets its own key;
- **transfer-backed book-ins still post nothing, deliberately.** A transfer moves units the business
  already owns between its own warehouses: their value never left inventory and never entered
  *purchase* goods-in-transit. The manual transfer receipt (`app/actions/transfers.ts`) queues no
  accounting sync either, so this is parity rather than a second gap.

**The account mapping is LOCKED for the whole receipt** (o3d-8f0p6 r4). Reading the codes over the
pool bound nothing, and re-reading them inside the transaction was not enough either: a re-read under
READ COMMITTED sees a remap that has already committed but holds nothing, so a remap committing *after*
it — while the book-in walks on through the transfer loop and the ASN updates — still ended with a
journal on stale codes, and on an ASN spanning several purchase orders could put earlier POs on the old
mapping and later ones on the new one inside one event.

The book-in now takes the **accounting-selection lock** before reading the codes and holds it to
commit — and nothing else: the re-read-and-refuse was removed once a mutation showed it could no
longer fail, because a check that cannot fail is not a guarantee. It is the *same* lock `queueAccountingSyncTx` already takes — the same advisory key, with the
two mapping rows added to its row set — so there is one lock and one order (advisory first, then rows
in one `ORDER BY key`), and the enqueue's own later acquisition is a no-op re-entry. `saveXeroSettings`,
the only writer of those rows, takes it too. The read is **memoised per event**, so every purchase order
in one ASN posts on one mapping by construction. A remap attempted mid-receipt is **serialised**, not
rejected: it waits and lands once the receipt commits. The connector is resolved once and pinned to the
enqueue, so the mapping and the queued row cannot come from two independent resolutions of "which
ledger".

**What happens if a book-in does refuse.** The refusal path is not self-healing and the recovery is
manual, so it is written down rather than implied. A failed attempt is rescheduled with backoff by the
internal sweeper, and after **eight** failed attempts (`MAX_FAILED_ATTEMPTS`) the event is
**dead-lettered**: `processingStatus` becomes the dead state, `nextRetryAt` is cleared and
`deadLetteredAt` is stamped, and **the sweeper will not pick it up again**. A fresh delivery of the same
Mintsoft event resets the attempt counter, so a warehouse that re-sends recovers on its own; an event
that has already dead-lettered needs a **redelivery or a manual replay** (*Re-check* on the ASN, or the
sync exception inbox) before its stock moves. Nothing else notices on its own.

**Freight allocation and unweighed lines.** The receipt cost uses the same distribution the manual
receipt uses, which means a `BY_WEIGHT` cost line allocates only across lines that HAVE a weight: a line
whose product weight is null gets no share of it while a sibling with a positive weight takes the lot,
so a **partially weighed PO silently allocates freight to only some of its lines**. That is
pre-existing and consistent between the two receipt writers rather than new here, and it is recorded
because it is a real allocation behaviour an operator would not otherwise see. (`BY_VALUE` and
`BY_QUANTITY` are unaffected; and when NO eligible line has a positive basis the helper falls back to
an equal split and warns.)

> **ALL THREE WMS-side receipt writers now post (o3d-8f0p6 then o3d-6nd55).** This webhook path was
> the second of three. The WMS stock-sync **align-up** path — which also credits PO-backed stock and
> lays cost layers — posted nothing either, and because it wrote to *neither* ledger the transit
> reconciliation tied out and hid the omission, so shipping this change alone did not make the transit
> account auditable. It does now: align-up queues the same journal and the same transit row, in its own
> transaction, and the two exclude each other's quantities (see **Align up** above). The caveat this
> paragraph used to carry — "the PO-backed webhook path now posts", not "WMS receipts now post" — is
> discharged.

Why it had to be fixed at the source rather than in a sweep: nothing downstream derives a receipt
journal from a stock movement. The Xero daily batch does not read `stock_movements` at all, its
inventory reconciliation posts Inventory ↔ *Rounding difference* and only for a sub-unit `sweep` gap
(a receipt-sized gap is `flag`, which is surfaced and never posted), and the transit reconciliation
aggregates `transit_subledger_movements` — rows written at post time — so a posting that never
happened is absent from both sides and that window ties out exactly. Proven by
`tests/concurrency/wms-purchase-receipt-journal.concurrent.test.ts`.

### Purchase-order lines have a landed-quantity definition (o3d-papk, first half)

The WMS stock-sync alignment credits `wms_asn_line_maps.qtyAccountedViaSnapshot` for a PO-sourced row,
lays its cost layer and queues its `STOCK_RECEIPT` journal, and **never writes
`purchase_order_lines.qtyReceived`** (writing it through is rejected: the booked-in reconciliation reads
the line-wide `qtyReceived` as manual receipts against *this* ASN, so aligned units parked there would be
read as manual and a replacement ASN would add no stock). So an aligned line has landed units and a
`qtyReceived` of zero. `lib/domain/inventory/po-line-landed-quantity.ts` is the one definition:

> **landed = `qtyReceived` + Σ over every `wms_asn_line_maps` row of the line (closed and retired rows
> included) of `max(0, qtyAccountedViaSnapshot − qtyAccountedViaReceipt)`**

and *outstanding* is `max(0, qty − landed)`, zero for a CANCELLED or CLOSED order. These now use it:

- **the manual receipt** (`receivePurchaseOrder`) refuses more than the outstanding quantity — read inside
  the transaction under the `purchase_orders` lock — so a receipt can no longer be booked on top of units
  alignment already brought in (previously 10 aligned-6 then 10 received gave stock 16 for 10 physical
  units, a second cost layer and a second journal);
- **the PO status** after a manual receipt, a WMS book-in **or an alignment** is RECEIVED when every line's
  *landed* quantity reaches its quantity (one derivation, `derivePurchaseOrderReceiptStatus`, so the three
  cannot drift). The alignment moves an order only FORWARD along the purchase-order workflow (PO_SENT / SHIPPED
  → PARTIALLY_RECEIVED → RECEIVED, `receivedAt` set on RECEIVED) and under the `purchase_orders` lock it already
  holds; a RECEIVED, INVOICED, returned or closed order is left as it is. An order fully stocked by alignment
  alone therefore no longer stays open for ever. (The freight-order auto-receipt cascade a manual receipt runs
  is not run by the book-in or the alignment, as before.)
- **the alignment planner** caps an allocation by the PO line's own residue (`qty − landed`), shared across
  that line's open ASN rows, as it already did for transfer lines; and it refuses an ASN whose PO is
  CANCELLED or CLOSED as *unusable* (never as *raced*, which would block the SKU for ever) while a healthy
  sibling keeps aligning;
- **the receipt-timing check** on align-down, the **EOL auto-archive incoming figure** (which also stops
  counting a PO line's own open ASN row a second time) and the **incoming-stock badges** in the product
  list and detail pages.

**Also in this change (the second commit, the PO half of o3d-6b9c, minimal).** The PO ASN creator is
sized by landed outstanding and a credited pending reservation is never deleted or resized in place — see
"ASN Flow" above for the rule and the lock order. Deliberately NOT done here and still open: the creator's
other defects (otay: never-created ASNs still count as alignment candidates; l2u6: claim/catch-demotion

#### Booked-in reconciliation: the manual-receipt pool (o3d-papk follow-up, o3d-67kw3)

A WMS book-in has to split each newly booked delta into three things: units the alignment **already put in
stock** (covered by the ASN row's unabsorbed snapshot credit), units a **manual receipt** already put in stock,
and genuinely new stock. `lib/domain/wms/asn-reconciliation.ts` does it in that order:

> `covered = min(delta, unabsorbed credit)` first; `manual = min(delta − covered, manual-receipt pool)` second;
> `qtyReceived += delta − manual`; `stock added = delta − covered − manual`.

and the invariant, property-tested over a grid, is that **a book-in changes landed by exactly the stock it
adds**. The previous order took the manual term first, which let landed *fall* (align 6, receive 4 by hand,
Mintsoft books 6: `qtyReceived` rose by 2, `qtyAccountedViaReceipt` by 6, landed 10 → 6, the PO flipped back to
PARTIALLY_RECEIVED and a second manual receipt of 4 was accepted: stock 14 for 10 physical units). The same
defect existed for transfer lines and is fixed in the same function.

The **manual-receipt pool** is branded (`ManualReceiptPool`; only `resolveManualReceiptPool` builds one, so a
caller cannot pass the raw `qtyReceived` again) and is the line's manual receipts that no ASN has reconciled:

> `pool = max(0, qtyReceived − Σ lastProcessedReceivedQty over every ASN row of the line (closed included) − this row's manualQtyBaseline)`

`qtyReceived − Σ lastProcessed` is an exact identity (the only writers are the manual receipt, the PO book-in and
the transfer book-in, all under the parent order's row lock). **`wms_asn_line_maps.manualQtyBaseline`** (migration
`20261001220000`, `NOT NULL DEFAULT 0`, no backfill: 0 is the old behaviour) removes the manual receipts that
**pre-date** the ASN row: the creators store that same figure, read under the parent lock, when a row is created or
resized. That is o3d-67kw3: line 10, manual 4, ASN sized for the 6 outstanding, Mintsoft books 6 used to add only 2
(4 units lost); the 4 are now in the baseline, the pool is 0 and all 6 land. The dry-run (the review an operator
approves) and the applied book-in read the same pool, so the figure shown is the stock added.

Not resolvable by IMS, filed as a policy question: a manual receipt of *different* units than the ASN's, on the same
line, while the ASN is still open, is indistinguishable from the same units received twice (o3d-papk S4).

### Receipt Review

Booked-in callbacks pause in `REQUIRES_REVIEW` before stock mutation when the dry-run finds reconciliation warnings. **A callback against a CANCELLED or CLOSED purchase order is one of them** (`parent_not_receivable`, "Purchase order cancelled or closed", approval-blocked: nothing may be received against an order the business has called off, so approval cannot release it; the alignment and the manual receipt refuse the same state). A booked-in status write goes through the purchase-order workflow (`validatePurchaseOrderStatusTransition`), so a late book-in against an INVOICED or returned order lands its stock and landed quantity but never overwrites the status (o3d-yaazk). Events that instead exhaust their retries go `DEAD` and surface in the cross-connector [sync exception inbox](./sync-exceptions.md) (`/sync/exceptions`), which can safely re-queue them.

- Structural warnings block approval until the underlying IMS or Mintsoft data is fixed: remote quantity regression, missing IMS source line, unsupported source type, missing transfer cost-layer snapshot, an **unreadable remote quantity** and a **missing remote ASN item** (the last two are o3d-btiw: an operator acknowledging a warning cannot supply a quantity the warehouse never served).
- **`missing_local_line` means the ASN line names a source line IMS does not have — not that there was nothing to do for it (o3d-h66s).** The IMS purchase-order / stock-transfer rows are read for **every** line of the ASN, not only the ones with new quantity to apply, so a line whose remote quantity has not moved since the last callback is recognised as the healthy line it is. Until o3d-h66s that read was restricted to lines with a positive delta, so a zero-delta line reported its own existing IMS line as missing; because the warning is aggregate, that held the **whole** callback in an approval-blocked review and applied nothing for its other lines either. In practice that meant every partially booked ASN, every re-check of an ASN already settled, and any line whose `QuantityBooked` was a readable `0`. A `sourceLineId` that genuinely resolves to no IMS row still raises the warning and still blocks, with or without a delta.
- **The warnings are AGGREGATE, by decision.** One line's blocking warning holds the whole receipt event, including sibling lines that have units to credit: a receipt event has one `processingStatus`, so applying some lines while holding others would move stock under a row that reads `REQUIRES_REVIEW` and leave the `reviewDetails` an operator later approves describing a state that has already changed. What makes it workable is that the review is per-line underneath — `reviewDetails.lines[].warnings` and the `mintsoft_booked_in_review_required` activity entry name the offending `asnLineMapId`, and a healthy line's warning list is empty — so an unknown line can never be silently skipped. Whether the hold should become per-line is tracked as **o3d-0qtvb**.
- `received_over_expected` is a variance warning. It always requires admin review, and approval accepts the over-receipt: for a purchase-order line the FULL booked quantity is received (stock, a cost layer at the PO unit cost, `qtyReceived`, the receipt journal) and the ASN closes (o3d-hqvrp.119; `allowOverReceipt` in `reconcileBookedInQuantities`). The review lists the quantity approval will book. A transfer line is still capped at the expected quantity (the excess has no cost layer). A later re-check reading the same remote figure does not warn again.
- **Closing a short-delivered PO ASN (o3d-hqvrp.117).** `closeMintsoftAsnShort` (`lib/domain/wms/asn-close-short.ts`, the **Close short** button on the PO ASN table, `purchasing.receive`) sets `closedAt` on a PARTIALLY_BOOKED_IN purchase-order ASN. It is an operator action because DISCREPANCY / PARTIALLYBOOKED / BOOKEDIN-PARTIAL are not terminal in Mintsoft. It books and writes off nothing; every open-ASN reader filters on `closedAt IS NULL`, so the manual-receipt guard, the ASN creator's reuse, the align-down pending count and the watchdog release the remainder at once. It refuses transfer ASNs and ASNs with an unprocessed booked-in event. Goods Mintsoft books later against the closed ASN are not read by the re-check; receive them on a new ASN.
- Approval requires fresh admin auth and the admin mutation header. Successful approvals stamp `reviewedAt` and `reviewedBy`; failed approval attempts remain visible through `lastError` and activity logs without stamping those success fields.
- Activity logs include aggregate and line-level warning details so post-hoc audits can identify which ASN lines were approved.
- The Mintsoft dashboard shows the newest 20 events and the total review backlog. Use the JSON inspection endpoint for full line-level detail until a dedicated review queue UI exists.

## Booked-In Webhook Signing

Mintsoft ASN booked-in webhooks must include:

- `x-mintsoft-signature`: HMAC-SHA256 digest, hex or base64, optionally prefixed with `sha256=`.
- A fresh timestamp in `x-mintsoft-timestamp`, `x-webhook-timestamp`, or `x-timestamp`. New senders should use `x-mintsoft-timestamp`.

The signed payload is:

```text
${timestamp}.${rawBody}
```

### Maintenance-mode fence (o3d-hl8l)

The booked-in webhook route consults maintenance mode as its **first** statement — before the body is read and before the signature is verified — and returns `503 {"skipped":true,"reason":"maintenance_mode"}` with `Retry-After: 300` while the flag is on. Nothing is persisted and no activity row is written.

The refusal is written to the **process log** at the moment it happens (route + reason + the remedy). That is the only sink available: an activity row is a database write, and a row written into this window is being replayed over — which is the whole reason the callback is being refused. Treat it as a log line, not an alert.

The flag is set only by the database **restore** endpoint, and it stays on when a restore backend cannot be confirmed dead. A row written into that window is being replayed over, so persisting the event would return `202 accepted` for something the restore then destroys; a `503` promises nothing and is the standard retry signal.

**If the sender does not retry, the booked-in trigger is dropped** — so there is an explicit way to recreate it. Neither of the existing replay paths could: the sync exception inbox's replay and `replayMintsoftBookedInEventsForAsn` both re-drive receipt-event rows that already exist, and a refused callback leaves none.

**Re-check** asks the warehouse directly. It reconstructs the *trigger* only: the webhook carries an ASN id and nothing else that is used, and processing re-fetches the ASN from Mintsoft and applies just the delta over what each line has already accounted. So the warehouse stays the authority for the quantities, pressing it when nothing is outstanding books nothing in, and a real callback arriving afterwards finds the delta applied. If the ASN already has outstanding receipt events (dead-lettered, mid-retry, awaiting review) those are re-driven instead of a second row being created alongside them.

The control is on the connector ASN table of **both** the purchase order (needs `purchasing.receive`) and the stock transfer (`stock-control/transfers`, needs `stock_control.adjust`) — one shared component, because both kinds go through the same callback processor and the same fence. Until o3d-hl8l r4 only the purchase-order table had it, so a refused callback on a transfer ASN left it `IN_TRANSIT` with destination stock unapplied and nothing an operator could press.

**Recovery is automatic within about five minutes of the maintenance window closing.** `disableMaintenanceMode` stamps the `wms_booked_in_recheck_due_since` setting whenever a real window ends, and the `mintsoft-webhook-sweeper` cron (every 5 minutes, enabled by default, itself fenced so it cannot run during the window) drains that stamp by re-checking **every open ASN** — both source types, because the candidates come from `wms_asn_maps` rather than from whichever screens have a button. The refusal is unrecordable by construction, so there is no set of "the ones that were refused" to target; re-checking indiscriminately is safe precisely because a re-check with nothing outstanding books nothing in. The stamp is **kept**, not cleared, if any candidate threw or the page truncated (default 100 per tick, oldest first), so the next tick finishes the job.

**Run it on demand** from *Sync → Exceptions → Maintenance window → Run the re-check now* when the sweeper cron is disabled or the scheduler is down — which is not a rare state on the day a restore was needed. It refuses while maintenance mode is still on (a re-check issued into the window is stopped at the same gate the callbacks were) and when no window is actually pending, and it does not clear the stamp itself: the drain clears it only once every open ASN has been attempted. The claim is not a lease: the pass re-reads the maintenance gate before it starts, before each ASN, and again under a row lock before clearing the stamp (together with "is this still the marker we drained"), so a restore starting mid-pass stops it with the stamp kept rather than writing into the window and recording it as recovered.

**The held-restore branch is covered too, as of o3d-hl8l r5.** It used to be the gap: when a restore times out and its database backend cannot be confirmed gone, the endpoint deliberately leaves maintenance mode on and never calls `disableMaintenanceMode`, so no stamp was ever written and the operator's only clear was a hand-written `UPDATE` on the `settings` row — which ends the window and schedules nothing. That is the **longest** kind of window, so it was the one most likely to have refused callbacks. The restore now records a *maintenance hold* naming the backend's pid and `backend_start`; the exception inbox renders it; and **End the hold** re-reads the flag and the record under a row lock, re-checks the backend against `pg_stat_activity` at the moment of the click, refuses by name if anything has moved, and stamps the booked-in re-check as it clears. It ends **the hold the page showed** — the button carries the record's pid, `backend_start` and `heldAt` — and a starting restore deletes any hold left by the previous window, so a second restore beginning between the render and the click is refused (`hold_superseded` or `no_hold_recorded`) instead of having its fences cleared. Clearing the row by hand still works and still schedules nothing — use the inbox action. If the hold record was lost with the restore's rollback there is no inbox row, and that window falls back to the watchdog and the per-ASN Re-check, as before.

The loss is also detected rather than silent — but on a scale of **days**, so it is worth stating exactly. The `wms-watchdog` cron (hourly, **enabled by default** as of o3d-hl8l r4 — it was previously off, which meant the bound this section claimed did not exist on a default installation) alerts on an open ASN past its ETA + 24h with no booked-in callback; with no ETA recorded, after 7 days of complete silence; and for an ASN that had already had a partial callback, after 7 days of renewed silence. It requires a WMS connector to be enabled and at least one active `ADMIN` to notify, and it alerts **once** per ASN (deduped by `sloAlertedAt`, which clears only on a fresh callback or a close). Its message names the Re-check remedy and links to the screen that carries it **for that ASN's kind**, so the reader is neither sent looking for a receipt-event row that a refused callback never created nor pointed at a purchase-order page for a transfer ASN.

Every re-check — automatic or operator-initiated — writes a `mintsoft_asn_booked_in_recheck` activity entry recording whether it minted a trigger or re-drove existing work, and each automatic pass additionally writes a `wms_post_maintenance_recheck` entry naming the window it was recovering from.

The `timestamp` string must be the exact header value IMS uses for freshness validation. Prefer ISO-8601 timestamp strings. Numeric timestamp headers are accepted, but the signature prefix must match the exact header value; for example, `1776852000.0` and `1776852000` are different signature prefixes. Body-only signatures and payload-only timestamps are rejected.

### Migration Runbook

1. Discovery: before deploying this change, check recent sync activity for Mintsoft webhook signature failures and confirm which senders are still using body-only HMAC.
2. Sender migration: update each sender to send `x-mintsoft-timestamp` and sign `${timestamp}.${rawBody}` using that exact header value.
3. Rollout: deploy only after every sender signs timestamp-bound payloads and sends the timestamp header. Body-only signatures and payload-only timestamps are intentionally unsupported.
4. Monitoring: watch sync activity for `mintsoft_webhook_rejected_missing_timestamp`, `mintsoft_webhook_rejected_stale_timestamp`, and unauthorized responses from the webhook route.

## Product And Bundle Sync

- Product sync normalizes Mintsoft payload variants before creating or updating IMS links.
- Barcode conflicts are surfaced as discrepancies; IMS should not overwrite a non-matching barcode silently.
- Bundle checksums are stable across component order and ignore tiny quantity drift.
- **A bundle create that may have reached Mintsoft is never repeated by the clock.** `PUT /api/Product/Bundle` is marked *sent* in IMS just before it leaves. If it then fails in any way other than this installation's own outbound-write hold refusing it (a timeout, a dropped connection, a 5xx, an unusable answer), IMS looks the bundle up straight away and links it only if Mintsoft returns a complete bundle whose components equal IMS's. A 404, an unreadable answer or an error proves nothing (an accepted create can still appear later), so the claim stays and no further create is sent, however long it is. A bundle answer with component entries IMS cannot read is never compared or linked. A claim is retaken after ten minutes only if it carries the `pending:unsent:` mark, which proves no request was handed over; every other claim, including a `pending:<time>` one written before this mark existed, is treated as sent.
- **Resolving a kept claim.** The claim is raised as a bundle conflict and listed under **Sync > Mintsoft > Bundles**. After looking in Mintsoft the operator either links the Mintsoft bundle id (the next bundle check compares it with IMS) or states that a search found no bundle for that SKU, which releases the claim. The release is refused while the create may still be in flight (12 minutes by default: 14 timed requests at `CONNECTOR_FETCH_TIMEOUT_MS` plus five minutes) and unless a lookup made at that moment returns a readable "no bundle" (a 404 or an empty 200); a found, unreadable or failed answer refuses with the reason. The list is paged and searchable by SKU. The claim change and a durable audit row commit together, so a decision whose audit cannot be written is not made. **The limit nothing closes:** immediately before it sends, a worker re-verifies its claim in one conditional update (exact id and value) and refreshes the claim's timestamp, and sends nothing if that fails; when its answer arrives it writes the link only if the claim is still exactly its own, and otherwise records the late result for reconciliation instead of overwriting. A process that is paused or frozen for longer than the release window *between* that check and the request leaving can still complete after a release. Mintsoft offers no idempotency, so IMS cannot rule that duplicate out, and the confirmation says so. The statement itself is the operator's and IMS cannot verify it: it is recorded as such in the activity log and the Event Timeline, and if it is wrong the next sync creates a second bundle.

## Product Sync Parity With The Retired Python Sync (flags, default OFF; o3d-zvec.20)

Four behaviours of the plugin's Python product sync are ported behind two settings. **Both are OFF by default and nothing here is live.** A setting reads ON only for the exact string `true`; anything else (absent, blank, `TRUE`, a typo) is OFF, and an unreadable setting fails the run rather than reading as consent. There is no settings-page switch yet: an administrator sets the rows in the `Setting` table.

`mintsoft_product_parity_enabled` (default OFF) gates every changed product **write**. With it OFF the product payload, its hash and the options handed to the connector are byte-identical to before (pinned by `tests/mintsoft-product-parity.test.ts`, following the identifier-split pattern), and cost layers are not even read. With it ON:

- **Names (`fit_mintsoft_name`, ported exactly).** Mintsoft refuses a Name of 100 or more characters with a bare "Invalid Data!". The name is fitted to 99 UTF-16 units: the parent part is cut at a word boundary (when one is at or past half the cut) with `...`, and the variation suffix (` (a, b)`; IMS stores a variation as `<parent> — <attributes>`) is kept whole. If the suffix leaves fewer than 10 characters for the parent, the variation SKU stands in as the suffix; with no SKU the tail of the suffix is kept. A name that fits is unchanged. Golden tests run the Python function itself (`tests/fixtures/mintsoft-fit-name-golden.json`). Owner decision 2026-11-18: with parity on, IMS sends the plugin's own `Parent (a, b)` format (the attributes of the stored `Parent — a / b` re-joined with `, `), so nothing already in Mintsoft is renamed at cutover.
- **CostPrice.** The IMS unit cost: the weighted average of the cost layers still holding stock (the figure the product page's inventory value divides to; a KIT or BOM costs its components), to four places, `Decimal` arithmetic. No stock or a zero cost sends no `CostPrice`. **Cost is business-sensitive:** it is in the outbound request only; the Mintsoft echo kept in the sync log has `CostPrice` removed, and it is in no activity, audit or console line. The product link still stores Mintsoft's saved read (needed for the dry run), which is not a log.
- **Inheritance.** A VARIANT inherits its parent's weight and each of height, width and depth, per field, where its own is missing (null). A recorded zero is its own value.
- **Bulk tools** (below) may `--apply`.

`mintsoft_parent_sku_delete_enabled` (default OFF, and inert unless the parity setting is also ON) is separate because it is **destructive**. At the end of a **successful full product verify run**, IMS deletes the Mintsoft SKU of a VARIABLE product's parent (`DELETE /api/Product/{id}`, ownership-map operation `mintsoft/product.delete`, behind the producer seam and the outbound-write hold) only when it can prove, from a **fresh read of the stored product links** (no Mintsoft call), that every non-archived variation is present in Mintsoft: each has a link with no error and a payload hash, refreshed by this very run, whose stored Mintsoft record carries the link's id and the variation's SKU; no two variations share a record; none is the parent's record or has the parent's SKU. The read is repeated immediately before the call. On any doubt it deletes nothing and records a refused action (Event Timeline, action `parent_sku_delete_refused`, naming the SKU and every reason) for an operator. A shadow, a hold, a refusal by Mintsoft (for example a record linked to orders) or an error leaves the parent and its link as they were.

**Bulk tools (dry run by default).** `scripts/mintsoft-bulk-product-data.ts trade|coo <csv>` ports `force_mintsoft_trade_update.py` and `coo_push.py`. A dry run prints a no-write comparison of the CSV against IMS and the Mintsoft record IMS last stored, and writes nothing. `--apply` is refused unless the parity setting is ON, writes the validated values (declarable CN8 code, ISO country, customs description) onto the IMS products by compare-and-set, and the ordinary product sync then sends them through its guarded writer: the tools have no Mintsoft path of their own. Only the owner runs `--apply`.

**Catalogue dry run.** `scripts/mintsoft-catalogue-dry-run.ts` is read-only (SELECTs only, no Mintsoft call): it builds what IMS would send for every eligible product, as today and with parity on, and diffs both against the stored Mintsoft record, listing the products the parity setting would change. Costs are hidden unless `--show-cost` is given. Run it, and review the unexpected diffs, before turning parity on.

## Product Content To Mintsoft

Product **content** (description, short description, picture) is authored in WooCommerce and flows **WooCommerce -> IMS -> Mintsoft**; IMS is the hub and there is no direct WooCommerce -> Mintsoft path. Product **meta** (name, barcode, weight and dimensions, customs data, Mintsoft product id) is a different operation (`mintsoft/product.upsert`, `woocommerce/product.meta` in the writer-ownership map): the woo-mintsoft plugin owns it in P1 and IMS from P2. The two are kept apart on purpose: a content update never carries meta.

**Where the content comes from.** The WooCommerce product import stores each product's and variation's short description, long description and picture references in IMS (`product_contents`, one row per product; see [WooCommerce product sync](woocommerce.md#product-sync)). Nothing in IMS writes content back to WooCommerce.

**What is sent and when.** The Mintsoft product verify run (the existing cron `mintsoft-product-verify` and the *Run Product Verify* button on `/sync`) has a content step after each product's meta step. For a product that already has a Mintsoft link it compares, per field, the hub copy with what Mintsoft last accepted and sends **only the fields that changed**: `Description` (long), `ShortDescription` and `ImageURL` (the first picture). The request is `POST /api/Product` with the product id, the SKU and those fields only. A product with no Mintsoft link yet has no content sent; it follows the first run after the product exists there.

**Never empty.** A blank or missing value is not in the projection, is not compared, is not sent, and the request builder refuses it too. Mintsoft content is never cleared from IMS, by an empty WooCommerce field or by anything else.

**Shadow until IMS is the live writer.** The step asks `producerDisposition('mintsoft', 'product.content')`, which is decided from the environment alone: LIVE only when the Mintsoft outbound-write grant and the live-from instant are both set and reached, and the ownership map says IMS owns the operation (P2). Until then — which is every installation today — the disposition is SHADOW: the step records a `shadow` row in the sync log (what *would* be sent, a 300-character preview per field) and **calls nothing**. The same shadow is recorded once, not on every run. A LIVE disposition still goes through `connectorFetch` and the outbound-write hold; if the hold refuses, the run logs the product as *held* (a `skip` row saying the request never left IMS), records nothing as accepted, and offers the fields again on the next run.

**Field names not yet verified.** `ImageURL` is a field IMS already sends in the product upsert. `Description` and `ShortDescription` are the names the connector plan lists, but their exact wire names and whether a body of id + SKU + changed fields leaves the other fields untouched were **not verified against Mintsoft** (no live call was permitted while this was built). Until `MINTSOFT_CONTENT_WIRE` in `lib/connectors/mintsoft/api/product-content.ts` marks a field `verified: true`, that field is recorded as a shadow even when the disposition is LIVE, and the log says so. Verify with a read-only `GET /api/Product/{id}` capture, then one controlled granted update, before flipping it.

**Where the operator sees it.** The product verify run's job summary (`/sync`, WMS sync jobs) carries a `content` block (`sent`, `shadowed`, `held`, `errors`), the run message and the activity log end with one sentence built from it (`Content: ... recorded but NOT sent (IMS is not the live writer yet) ...`), and the job's log rows show each product's outcome: `updated` (fields accepted), `shadow` (recorded, not sent), `skip` (held by the outbound-write hold), `error`. These are not terminal exceptions, so they do not appear on `/sync/exceptions`; a content failure makes the job `PARTIAL`.

**Known overlap.** The product upsert (meta) also sends `ImageURL` from the product's primary image, which is the same address as the content step's first picture. Both write the same value; removing it from the meta payload is a P2 decision.

## Mintsoft Suppliers (mapping, and the supplier on an ASN; o3d-qk7z0)

Mintsoft needs a supplier on every ASN. Before this, `buildMintsoftAsnPayload` sent none: the supplier reference and carrier went into `SupplierNotes` only, and IMS held no list of Mintsoft's suppliers. Most of Qoblex's suppliers already exist in Mintsoft, with minimal details and names that are not identical to IMS's, so IMS **maps** to them first and creates only when an operator chooses to.

**The contract (from the published Mintsoft swagger; UNVERIFIED against the live tenant).** In Mintsoft a supplier is a `ProductSupplier`. `GET /api/Product/Suppliers` lists them (`PageNo`, `Limit` max 100, `ClientId` admin-only) and `PUT /api/Product/Suppliers` creates one (answers a `ToolkitResult`); there is no update route, so IMS cannot overwrite an existing supplier. `NewASN.ProductSupplierId` (int32) is the ASN's supplier (`NewASN.Supplier` is a free-text name and is not used). Every name lives in `lib/connectors/mintsoft/suppliers/contract.ts`, marked UNVERIFIED, so a correction is a one-line change.

**Controlled-run step (owner-sanctioned; NOTHING here has been run).** Before `mintsoft_asn_send_supplier_enabled` is turned on (and so before `mintsoft_asn_supplier_required`, which cannot be saved ON without it) at step M:
1. One read of `GET /api/Product/Suppliers` (the screen's *Refresh Mintsoft supplier list* does exactly this and writes nothing): confirm the paging, the field names, that a client user sees its own suppliers, and whether `ClientId` must be omitted for a client user (as it must be on `NewASN`).
2. One ASN create carrying `ProductSupplierId` on stage or the sanctioned test tenant, read back with `GET /api/ASN/{id}` to see the supplier on the ASN, then `DELETE /api/ASN/{id}`.
3. Only if IMS is to create suppliers: one `PUT /api/Product/Suppliers` with a throwaway name.

**The read-only sync.** *Refresh Mintsoft supplier list* walks the list (limit 100, a pause of 400 ms between pages), refuses a partial list (a repeated id, a row it cannot read, a malformed page, more than 200 pages, or an empty answer from a tenant it had suppliers for) and caches it in `mintsoft_suppliers`. A supplier the latest full list no longer holds is marked missing, never deleted, and a mapping to it is refused for use.

**Suggested matches.** For every IMS supplier without a mapping the screen offers the top three Mintsoft suppliers. Names are compared after folding case, accents, punctuation, whitespace, `&`/`and` and legal suffixes (Ltd, Limited, Inc, plc, LLC, GmbH, Co, Company and the rest of the list in `suppliers/match.ts`), as the larger of a character-bigram similarity and a token overlap. A shared e-mail (+25), VAT number (+30) or account number equal to the Mintsoft code (+20) adds to the score and can surface a pair whose names differ. (An equivalent of the CRM company-suffix fold is used here: that fold has not reached `development`.) Nothing is ever mapped automatically.

**The mapping screen** (Integrations > Mintsoft > Mintsoft suppliers, `/sync/mintsoft-suppliers`; ADMIN and MANAGER). For each IMS supplier the operator can confirm a suggestion, pick any Mintsoft supplier, choose *Create in Mintsoft*, or unmap (not on a `CREATING` row). Every decision is audited in the same transaction as the change (activity actions `mintsoft_supplier_mapped`, `_unmapped`, `_create_pending`, `_created`; the decision source, the score the operator saw and who decided are kept on `mintsoft_supplier_links`).

**Create in Mintsoft is a real write.** It is ownership-map operation `mintsoft/supplier.create` (step M, P1 owner the operator by hand), goes through the producer seam and the outbound-write hold, and is behind `mintsoft_supplier_create_enabled` (default OFF). Off, the choice is recorded as `CREATE_PENDING` and nothing is sent. On, IMS first requires a fresh list read and refuses when a similar supplier is cached (see the safety rules below), takes a `CREATING` claim before the request so two clicks cannot create twice, releases the claim on a clean refusal, and **keeps** it when the outcome is unknown (a transport error): the supplier may exist, so an administrator checks Mintsoft, refreshes the list and resolves the unknown outcome. IMS never updates an existing Mintsoft supplier; enriching one from IMS would be a separate opt-in write and is not built.

**Transfers.** Transfer ASNs carry the supplier "One Two Enterprises Ltd" (owner decision 2026-11-19): the setting `mintsoft_transfer_supplier_id` names that IMS supplier, and it is mapped through the same screen. With none chosen, a transfer ASN is treated like an unmapped PO.

**On ASN create** (`createMintsoftPurchaseOrderAsn`, `createMintsoftTransferAsn`; after the producer seam, before any sync job or reservation). Sending the supplier has its OWN switch, `mintsoft_asn_send_supplier_enabled` (default OFF; ADMIN, fresh sign-in), because `ProductSupplierId` is UNVERIFIED against the live tenant: **it goes ON only after controlled-run step 2 has read the field back.**
- send switch OFF (the default): **nothing about the supplier reaches the ASN, even when suppliers are mapped** (byte-identical body; pinned by a test). If `mintsoft_asn_supplier_required` is ON while the send switch is OFF, the ASN is refused instead (the screen will not save that combination);
- send switch ON and the supplier (the PO's, or the transfer supplier) is mapped to a Mintsoft supplier that is present AND active in the cache and was in the latest read: its id is sent as `ProductSupplierId`;
- send switch ON and the mapped Mintsoft supplier is absent from the cache, missing from the latest read, or inactive: the create is **refused** with a standing task and the supplier is never sent, whether or not `mintsoft_asn_supplier_required` is on;
- send switch ON, no mapping, required OFF: the ASN is created exactly as before (no supplier field);
- send switch ON, no mapping, required ON: the create is **refused**, nothing is reserved or sent, and a standing task is raised (Sync > Exceptions, *ASN not created: supplier not mapped in the warehouse*, "Map supplier X in Settings > Mintsoft suppliers"). The task closes when the supplier is mapped or the ASN is created.
`SupplierNotes` (supplier reference and carrier) is unchanged.

**`mintsoft_asn_supplier_required` MUST be ON before step M**, once every active supplier and the transfer supplier are mapped and the send switch is ON: step M hands ASN creation to IMS, and Mintsoft rejects or mis-files an ASN with no supplier. Both ship OFF so current behaviour is unchanged until the mapping work and controlled-run step 2 are done. The switch screen shows how many suppliers are still unmapped.

**Safety rules of the screen (review round 1).**
- *Inactive and stale suppliers.* Only suppliers present in the latest read AND active are suggested, pickable or sent. The screen shows the age of the list (from the sync's own record `mintsoft_supplier_last_sync_at`, never from row timestamps) and flags it when it is older than `mintsoft_supplier_cache_max_age_minutes` (default 30).
- *Create in Mintsoft* (a real write) requires a list read within that many minutes, and refuses when any cached supplier scores 55 or more against the name, or shares an e-mail, VAT number or code, unless the operator confirms **Create anyway** with a reason (audited). Refusals, the claim and every outcome are audited (`mintsoft_supplier_create_refused`, `_claimed`, `_declined`, `_unknown`, `_created`, `_created_claim_lost`, `_created_unrecorded`).
- *Unknown outcome.* A create whose outcome is unknown keeps its `CREATING` row. **Unmap, remap and Create are refused on it.** The only way out is **Resolve unknown outcome** (ADMIN, fresh sign-in, a reason, and a list read after the attempt): record the Mintsoft id found by hand (mapped) or mark it not created. Every later write on the row is a compare-and-set on that claim; if the claim was lost during a live create, the created supplier is still cached and audited, never rolled back.
- *Fold.* Only true legal-form endings fold (Ltd, Limited, Inc, plc, LLC, GmbH, Co, Company and the like). Region words and two-letter forms (eu, uk, ag, sa, ab, as) do not, so "Bambu Lab EU GmbH" is not "Bambu Lab Ltd".
- *Several IMS suppliers on one Mintsoft supplier* is allowed but warned about (on the screen and in the audit).
- *Single-flight.* The read sync takes an advisory lock (a second Refresh is refused, never queued) and upserts in batches of 100, not one long transaction.
**Review round 2 fixes (o3d-ypqzi), all in force before the create or send switch goes on.**
- *Sync stamp and sweep.* `mintsoft_supplier_last_sync_at` is the time the walk STARTED, not ended, and the missing-sweep skips any row created at or after that moment (an IMS create inserts its cache row with `createdAt` = now). "Resolve unknown outcome" therefore still needs a read that began after the attempt. The create path takes the SAME advisory lock as the sync (`WMS_SUPPLIER_LIST_SYNC_LOCK_NAMESPACE`): a create is refused while a refresh runs, a refresh is refused while a create runs, and two creates (for any IMS suppliers) are serialised, so two similar IMS suppliers cannot both pass the duplicate guard before either is cached.
- *Duplicate guard* blocks from `SUGGESTION_MIN_SCORE` (55), not 80, unless "create anyway" with a reason.
- *ASN cache age.* With the send switch ON, a mapped supplier is sent only when the list was fully read within `mintsoft_asn_supplier_cache_max_age_hours` (default 24); otherwise the ASN is refused with the usual operator task and nothing is sent.
- *Scheduled sync: not added, on purpose.* The read is manual (*Refresh Mintsoft supplier list*), the ASN age check above makes a missed refresh fail safe (a refused ASN with a task, never a stale id sent), and each read costs up to 200 paced requests on the shared live tenant. A cron route would add a route, a crontab entry, a route-auth entry and outcome wiring for a read an operator does in one click. If the daily click becomes a burden, add it then, default OFF, following `mintsoft-bundle-verify`.
- *Resolve unknown* needs the attempt to be at least 2 minutes old (`RESOLVE_UNKNOWN_MIN_WAIT_MINUTES`).
- *Shrink guard.* A read at least 20% smaller than the cached live list (when 10 or more are cached) is refused before anything is written and logged (`mintsoft_supplier_sync_refused_shrink`); an administrator with a fresh sign-in can confirm it (`mintsoft_supplier_sync_shrink_confirmed`).
- *Session-lock connection.* The sync holds one of the 6 pooled session-lock connections for the walk. It cannot be released between pages: the exclusion IS the held session lock (a transaction lock cannot span the page requests, and releasing it would let a create start mid-walk). One refresh or create at a time costs one connection; revisit the pool size if more long leases appear.
- The transfer supplier and all three switches are ADMIN with a fresh sign-in, and their audit rows are written in the same transaction as the change.

## Reconciliation Pack Reads (R1)

`npm run reconcile:pack -- --vendor-reads-only` reads Mintsoft for item R1 (IMS on-hand against `TotalStockLevel` per bound warehouse and SKU; the rules are in the installation guide, "Reconciliation pack"). The reader is `lib/connectors/mintsoft/reconciliation-read.ts`:

- It uses the **stored fixed API key only**. It refuses, with no request, unless `mintsoft_auth_mode` is exactly `api_key` and a key and a numeric `mintsoft_client_id` are stored; `POST /api/Auth` (which mints a new tenant key) is unreachable from it, and a 401 is reported, never refreshed. An installation configured through `MINTSOFT_AUTH_MODE` / `MINTSOFT_STATIC_API_KEY` alone is refused: the pack's environment is a short whitelist.
- It sends only `GET /api/Product/StockLevels?WarehouseId=<n>` and `GET /api/Product/List?PageNo=<n>&Limit=<n, at most 100>` (both on `MINTSOFT_READ_ALLOWLIST`), to the connection's own origin, and a redirect is an error.
- The live `Product/List` row shape (read 2026-10-23: `ID`, `SKU`, `ClientId`, `Bundle`, `DisCont`, ...) is what the reader parses: `ID`, `SKU`, a boolean `Bundle` (required) and `ClientId` when present. `Bundle` must agree with every warehouse's stock list (else `IDENTITY_CONFLICT`). `DisCont` is not read: discontinued products are still compared. Mintsoft pages `Product/List` with no total, so completeness is proven by exact pages, the empty page after the last, no repeats, two equal scans and containment of every stock row.

## Stocktakes and Mirrored Warehouses

An IMS-side stock count against a WMS-bound warehouse is coordinated with the stock sync (6oyu.3): under **Align To WMS** posting is **blocked** — the WMS is the stock master, so perform the stocktake there and let the sync import the corrections; under **notification-only** posting **warns and requires acknowledgement**, since any remaining divergence against the WMS is re-flagged as a discrepancy on the next sync. Unbound (or sync-disabled) warehouses are unaffected.

## Silent-Failure Watchdog (scheduled)

The `wms-watchdog` cron (hourly, ships disabled — enable in System Settings → Scheduler) alerts once per breach (WARNING activity + admin bell, deduped until the condition heals): **open ASNs past their ETA** (persisted from the ASN dialog) **with no booked-in callback** — naming any unreconciled alignment credits, which silently suppress real PO receipts until the callback arrives — and **bindings without a successful stock sync** for 3× their own cadence (dead cron — or one whose every attempt fails; FAILED attempts don't count as freshness). A fresh callback / ASN close, or the next successful sync, re-arms the alert. If a breach alert cannot be delivered (notification insert fails, or no active admin exists) the breach stays unclaimed for retry and the run returns HTTP 500 so scheduler monitoring goes red.

## Mutation Audit Timeline (q66in.4.6)

Every connector mutation — outbound (order create/update/hold/cancel/release, warehouse comments, ASN create, product/bundle upsert) and inbound (booked-in receipts, align-up/align-down corrections, dispatch application, returns-inbox staging) — records a `WmsMutationEvent` row with operational **before/after images** (states, SKUs, quantities, totals; PII keys are masked at write time by `scrubWmsMutationPayload`). Browse it at **Integrations → Event Timeline** (`/sync/events`): filter by connector/direction/action/outcome or exact entity/external id, and expand a row for the before/after JSON. Recording is best-effort (an audit failure never fails the mutation); rows are purged by the activity-cleanup cron after 365 days.

## Order Reconciliation (scheduled)

The `wms-order-reconcile` cron (default daily, ships disabled — enable in System Settings → Scheduler) runs a connector-agnostic order-level reconcile of IMS intent vs WMS truth (`lib/domain/wms/order-reconcile-sweep.ts`). Because the WMS API cannot enumerate orders, it verifies IMS-known truth per order: eligible orders with no live push link (`NOT_PUSHED`), live links whose WMS order vanished (`MISSING_IN_WMS`), and cancelled/held orders still active in the WMS (`ACTIVE_AFTER_CANCEL` — admins are belled; the warehouse may ship them). The dispatch sweep adds a fourth category from the status it already reads: `CANCELLED_IN_WMS`, a live IMS order the WMS shows as cancelled / deleted / voided / rejected and not despatched (`lib/domain/wms/terminal-status.ts`). It is reported only; IMS never cancels the order, releases stock or re-pushes it. A hold or cancel refused on identity or not-found grounds now raises an investigative operator task (stamped settled only after the task is recorded), and the courier-fallback task key carries the fallback episode (the link's push time) so a later fallback for the same service after a Done task raises a new task. Findings land on an `ORDER_RECONCILE` sync job and surface in the [sync exception inbox](./sync-exceptions.md).

## Order Dispatch Push (Phase 8)

IMS pushes sales orders outbound to the WMS so the 3PL can fulfil them. The work is done by a connector-agnostic sweep (`lib/domain/wms/order-push-sweep.ts`) driven by the `wms-order-push` cron (`/api/cron/wms-order-push`, default every 10 minutes). **The cron ships disabled** — enable it in System Settings → Scheduler once a warehouse is bound.

- **Eligibility.** An order is pushed when it is paid, in a ready status (`PROCESSING` or `ALLOCATED`), and its ship-from warehouse is bound to the active WMS. Orders in unbound warehouses are skipped.
- **Idempotency.** Each order tracks one `WmsOrderPushLink` (unique per order). Create uses the order's external reference so a re-run never double-creates. State machine: `PENDING_CREATE → SYNCED`, then `HELD` (order put on hold), `CANCELLED` (order cancelled), or `DEAD_LETTER` (repeated failures or an unresolvable conflict).
- **Claim before the remote call (o3d-5r8).** The create pass writes the `PENDING_CREATE` link **before** it calls the WMS, inside a transaction that takes the sales order's row lock. That link is the deleter's evidence: `deleteSalesOrder` takes the same lock and **refuses to hard-delete any order that has a push link at all** (`Cancel the order instead so the WMS order is withdrawn`). Without the pre-push claim, a hard delete landing while a create was on the wire left the WMS holding an order IMS had no record of. Deleting an order is therefore never the way to withdraw it from the WMS — cancel it, and the cancel pass propagates the cancellation.
- **Create / update / cancel.** New eligible orders are created in the WMS; subsequent edits while the WMS order is still `NEW` are amended; orders put on hold are cancelled in the WMS and parked `HELD` (and re-created if released); IMS-cancelled orders propagate a cancel.
- **Retries.** A failed push increments an attempt counter and retries on the next sweep; after 5 attempts it dead-letters for manual review rather than looping forever. A line with no SKU fails the whole order (never a silent partial push).
- **Recipient.** The order is addressed to the **delivery recipient**, not the customer account (`lib/domain/wms/push-recipient.ts`). The WooCommerce import stores the shipping address's first and last name, company, plain street line, phone and email. The push uses the shipping address when it has a street line; a shipping address without one (blank, name-only or company-only) is not a destination, so the whole billing address is used instead (name, company and street always come from one address, never mixed). If neither address has a street line the order is **not pushed**: it parks as validation-failed with the reason "Neither the shipping address nor the billing address on this order has a street line…"; add a street line to the shipping address. Phone and email take the delivery address's own value and fall back to the billing one, then (email only) to the customer account's email; they are trimmed but never reformatted, so international numbers go to the carrier as typed. This differs from the old plugin in two deliberate ways: the plugin always sent the billing phone and email, and sent an empty name when the address had none (IMS falls back to the customer name). Orders imported before these fields were stored keep their old behaviour: their street line still contains the company and the customer name is used. Re-importing the order stores the new fields.
- **Payload total check (advisory).** After a successful create, the sweep checks that the figures it SENT add up to the order total IMS holds (`lib/domain/wms/push-total-guard.ts`, Decimal arithmetic): sum(quantity x unit price ex VAT) + shipping ex VAT - discount ex VAT + total VAT, against the order total less the gross value of any refunded units left out of the payload. Because WooCommerce rounds each stored amount to the minor unit but computes the order total from unrounded figures, rounding accumulates; the tolerance is half a minor unit per independently rounded amount that appears in the comparison (the net of each pushed line, shipping ex VAT and discount ex VAT when present, the VAT total, the order total, and net plus VAT of each line with refunded units), capped at 13 minor units (the plugin's bound); per-line VAT amounts are not in the comparison and add no slack. The recorded figure is clamped to the 32-bit column. A difference inside it is not shown. Outside it the order is **still pushed** (the check never blocks or alters a payload) and appears under *WMS pushes - order-total mismatches* on `/sync/exceptions`, with the figure and the reason in the server log. Known causes it reports: a gross order-level discount on a VAT-inclusive order (sent as one ex-VAT figure with no VAT part), and refunded units left out of the lines while `TotalVat` still includes their VAT. The VAT split across shipping is **not** itemised (`ShippingTotalVat` is sent as 0 and the shipping VAT sits only in `TotalVat`); that is reported by the guard as `vatItemisationGap` and is not a penny mismatch. Both checks (the order's own components and the pushed payload) always run after the warehouse accepts the order, in exact decimal arithmetic, and the LARGER difference is recorded. The column is named pence but holds minor units of the order currency, and the exceptions page scales it by that currency's decimal places. It is measure-first by owner decision: nothing here becomes blocking until the exceptions list shows real divergence.
- **Store credit is a payment, not a discount.** Store credit a customer redeemed (WooCommerce Smart Coupons) is kept out of the order's discount, so the order is pushed with the **full** goods value and `DiscountTotalExVat` carries only genuine coupons (customs and IOSS see the real value). Nothing for the credit is sent to Mintsoft: no payment or credit field exists on the push, which is the same as the existing woo-mintsoft sync plugin, which strips the credit coupon back out of `DiscountTotalExVat` and sends no payment. The credit is recorded on the IMS order (`storeCreditForeign`, gross). The push-time total check (`totalMismatchPence`) expects it: it compares the order total with goods + tax + shipping − discount **− store credit**, so an honest credit order is not flagged. An order with store credit that was not created by the credit-aware import (no provenance mark), or that is held for store-credit review, is **withheld from the push** and parked `VALIDATION_FAILED` with a reason, rather than telling the warehouse a reduced goods value.
- **IOSS number (`mintsoft_send_ioss_number`, default OFF; D5).** The shop has one IOSS number, kept in the admin-edited, audited setting `shop_ioss_number` (IM plus ten digits; Integrations > Mintsoft). No WooCommerce plug-in records an IOSS number on the order, so IMS does not read one from it. Instead the importer reads the order's **existing EU VAT stamp** (`sales_orders.eu_vat_regime`, decided once by the IOSS/VOEC/DDP treatment, which needs the Sales Invoices switch on) after every import or update: a stamped IOSS order stores `ioss_number` = the shop number and `delivery_term` = `IOSS_DDP`; a stamped DDP order stores `delivery_term` = `DDP`; anything else (VOEC, a skip, no stamp yet) stores neither. `DDU_DAP` is never inferred. An IOSS order with no valid shop number stores no number and raises one `shop_ioss_number_missing` warning on the order's activity. With the push setting off or unset the create payload is **byte-identical** to the one built before the setting existed (`tests/mintsoft-ioss-number-push.test.ts` pins it against a literal). With it set to `true`, `IOSSNumber` is added to the create payload only for an order whose stamp is IOSS (the push input carries `iossStamped`, not a number), and the number is the shop setting `shop_ioss_number` **read at the moment of the create** (`readShopIossNumber`), never the copy stored on the order: changing the setting applies to every order not yet created in Mintsoft, clearing it (or an invalid value) sends no `IOSSNumber`, and orders already in Mintsoft are never amended. The importer mirrors the stamped regime on every successful create-path return, including a held sales invoice, on the same create-only rule as `VATNumber`; amendments never send it. The toggle is a checkbox on Integrations > Mintsoft (`saveMintsoftSendIossNumber`, audited as `mintsoft_send_ioss_number_updated`); only exact `true` is on.
- **Mirrored duty/tax columns (D5).** The importer also stores `sales_orders.wclc_duty_component` / `wclc_tax_component` / `wclc_handling_component` (`_wclc_*_component`), `sales_order_lines.wc_customs_unit_value` (line meta `_wc_label_customs_unit_value`, order currency, the label plug-in's grammar: a plain decimal above zero) and, on products, `wc_us_hs_code` (attribute `pa_us_hs_code`) and `wc_dutify_hs_codes` (meta `_dutify_hs_codes`, `{ISO-2: code}`). They follow WooCommerce on every order or product update (a removed value clears; a payload with no meta list leaves the stored values alone) and are never recomputed. When an update moves a component away from the stored split, the fee lines and invoice built from the old split are NOT rebuilt, so one `wc_duty_tax_components_changed` WARNING is written on the order's activity. Only the IOSS number is pushed (above); the rest are shown on the order page. The product columns are separate from the IMS-owned `products.hs_code`, which is what IMS pushes to Mintsoft; the Woo mirrors are informational and never written into it.
- **Couriers.** The order's shipping service is mapped to a Mintsoft `CourierServiceId` via the courier map; unmapped services fall back to the default courier id, or pass the name through for Mintsoft to resolve.

## Refused or stalled actions (o3d-zvec.10)

A refusal that used to be a string on a link or a `pending` result is now a row in `refused_actions` (`lib/domain/refused-actions.ts`), keyed on (entity, action, gate), with permanence, a severity taken from the intent, a PII-free intent, first and last seen, and `resolvedAt`. Two instances write it:

- **`WMS_ORDER_AMEND` / `WMS_ORDER_NOT_NEW`**: the amendment pass reached an order Mintsoft has moved past `NEW` (`updateOrder` answers `updated: false`). The link still stays `SYNCED` with `lastError` set and `pushedAt` moved (no hammering), but the refusal is recorded first, with the full `pushIntentSummary` and the Mintsoft status; if it cannot be written the link stays due. Severity: the amended lines (SKU or quantity, compared with the lines recorded on the Mintsoft order) differ or cannot be compared, HIGH, which also raises an `AMENDMENT_NOT_APPLIED` operator task with the exact lines; otherwise LOW (no task, no alert). Orders reach this pass only while `PROCESSING` or `ALLOCATED`, so every refusal here is an order Mintsoft is picking or about to pick. No order comment is written. Only line changes are told apart: the sweep holds no earlier courier, VAT or price to diff against, so those are LOW.
- **`WMS_SPLIT_ORDER_COMPLETE` / `WMS_SPLIT_PART_CANCELLED`**: a split order with a cancelled part can never reach all parts despatched. MEDIUM. It is its own outcome: NOT `unresolved`, so it never joins the connector-drift cohort, never counts as a failure (no dead-letter) and does not hold the delta watermark (the record is the durable trace; a record that cannot be written does hold it). It is bounded by its own per-link read count, `DISPATCH_MAX_CONSECUTIVE_STALLED_READS` (5), after which the link is set aside and the admins told. That bound applies only to a PERMANENT stall (every despatched part's shipment recorded, the part set complete and known, and every other part cancelled). A despatched part whose lines cannot be read keeps it RETRYABLE: the link is never set aside and the delta watermark is held for it (`holdWatermark`, not the drift cohort) until the shipment is recorded. While another part can still despatch the stall is RETRYABLE: the link stays fully polled and is never set aside, so that part's despatch is still recorded.

The WMS watchdog cron (`/api/cron/wms-watchdog`) closes refusals whose order is cancelled, despatched, completed, fully refunded or deleted, then alerts once per record past its severity's age (`REFUSED_ACTION_ALERT_AFTER_MS`: HIGH 2h, MEDIUM 24h, LOW never). A later success closes the row (the amendment pass for `WMS_ORDER_AMEND`, the dispatch sweep for the split order); a person pressing Done on the query task does NOT close it: the push sweep re-reads the Mintsoft order's lines (read-only, up to `AMENDMENT_VERIFY_BATCH` open serious rows per sweep, least recently tried first by `refused_actions.last_verified_at`, stamped on every attempt including a failed read, so no row starves another) and closes it only when they equal the intent. The rows are listed on Sync > Exceptions under "Refused or stalled actions"; HIGH and MEDIUM count in the banner.

## Merge Candidates (flag mode, default OFF; o3d-zvec.11)

Same-customer orders that are all still `NEW` in Mintsoft are flagged for a person to merge in the Mintsoft UI. **IMS never merges** (Mintsoft has no merge API) and **this feature writes nothing to Mintsoft or WooCommerce and makes no Mintsoft call**: warehouse staff do not read order notes, so the warehouse-facing output is an IMS operator task (reason `MERGE_CANDIDATE`, Sync > Exceptions > Raise a warehouse query), never a Mintsoft or Woo order note.

- **Setting `wms_merge_candidate_mode`** (Settings table, edited in Integrations > Mintsoft > Merge candidates, `settings.company`, audited): `off` (default) or `flag`. Anything else, including the reserved `hold`, reads as `off` (`lib/domain/wms/merge-candidate-mode.ts`). Off computes and writes nothing. Holding the orders is the separate, flagged feature below (Merge Holds).
- **Matching** (`lib/domain/wms/merge-candidate-match.ts`, pure): normalised billing email (falling back to the order email) plus the effective delivery address (street line 1, line 2, city, postcode, country) from `resolvePushRecipient`, so the shipping address, or the billing address when shipping has no street line. Text is lower-cased, accents removed, and everything that is not a letter or digit dropped. NI, JE, GG, IM, XI and UK fold to GB; EL to GR.
- **Open orders only:** IMS status PROCESSING, ALLOCATED, PICKING or PACKING, not shipped, archived, erased or fully refunded, no pending or approved withdrawal, a push link in `SYNCED` or `MERGED`. A backordered order (any line the allocations do not cover, from the backorder report) is excluded.
- **Mintsoft gate, from the stored snapshot only** (`wms_order_status_snapshots`): status `NEW` (case-insensitive), not split, no lookup error, read within the last 3 hours, and the snapshot's connector and warehouse order id agree with the push link. **Tenancy:** a snapshot carries no ClientId, but every snapshot is written from a ClientId-scoped lookup that refuses another client's row (`assertMintsoftOrderClient`), so a snapshot is trusted only while `mintsoft_client_id` is configured; with none configured nothing is flagged. **Duplicate Mintsoft ids collapse:** orders already merged into one Mintsoft order count once, the oldest IMS order standing for it. A group needs two distinct Mintsoft orders; three or more is one group (a chain).
- **Warnings:** an EU destination gets a customs / IOSS warning (EU orders ARE flagged); a group with a FedEx member (shipping label, courier key or method id contains "fedex") gets a "label by hand" warning.
- **When it runs:** at the end of an order push sweep that created at least one warehouse order (outside the sweep lock), and at the end of every order-status sweep. The second is needed because a freshly pushed order has no snapshot until the status sweep has read it, so the push-time pass rarely sees it; the status pass makes candidates appear even when the push happened earlier and resolves a group when an order leaves `NEW`. A pass (compute, raise, resolve) runs under a per-connector advisory lock (`withMergeCandidateLockOrSkip`) so overlapping passes cannot resolve each other's task; a pass that cannot get the lock skips and leaves an owed marker (setting `wms_merge_candidate_owed:<connector>`); the holder runs ONE more pass when it finishes if the marker is set, and a marker set during that rerun is left for the next sweep. Before a group's task is raised or re-opened, its members are re-read under their order locks (the same locks the status sweep takes to write a snapshot) and the task is raised only if the group still qualifies on the current snapshots. Both passes only read and write IMS tables, and a failure is logged and never reaches the push or the status sweep (`runMergeCandidateDetectionSafe`).
- **Output:** a **Mergeable** badge with partner links on the sales order (computed on read), an activity entry per member (`wms_merge_candidate_flagged`, written once when the task is raised), the list on the Mintsoft screen, and ONE operator task per group, keyed on the set of order ids (`lib/domain/wms/merge-candidates.ts`). A group that stops qualifying has its open task resolved by the system (`doneBy` `system:merge-candidate-cleared`, activity `wms_merge_candidate_cleared`); if it qualifies again that task is re-opened, whereas a task a person marked Done is left alone. A chain that grows is a new group and a new task.

## Merge Holds (setting `wms_merge_hold_enabled`, default OFF; o3d-zvec.12 / o3d-zvec.13)

Builds on Merge Candidates. When on, IMS HOLDS every order of a detected same-customer group in Mintsoft (`GET /api/Order/{id}/MarkAwaitingConfirmation`, the order stays alive, unlike the cancel-based withdrawal hold) so a person can merge them in the Mintsoft UI. **IMS never merges and NEVER RELEASES a merge hold**: there is no `MarkConfirmed` call and no release verb anywhere (`tests/mintsoft-merge-hold-verb.test.ts` and `tests/wms-merge-holds.test.ts` read the sources and are red if one appears). A person confirms the merged order in Mintsoft.

- **Switches.** `wms_merge_hold_enabled` is a system-managed setting (only the exact value `true` turns it on; unset, blank or unreadable is off; set with `npm run settings:set`, not an editable form) AND `wms_merge_candidate_mode` must be `flag` (the groups come from the detection). With the setting off, `placeHolds` returns before any read of an order or write, the status-sweep maintenance returns after ONE read of `wms_merge_holds` when no hold stands, and every query the push sweep gained matches no row: behaviour is identical to `development`. (`placeMergeHolds` / `runMergeHoldMaintenance` in `lib/domain/wms/merge-hold.ts`, port in `merge-hold-port.ts`.)
- **The hold's identity lives in IMS, not in Mintsoft text** (owner ruling 2026-11-16; the stale-marker hazard of o3d-3a0t): table `wms_merge_holds`, one row per (connector, order), states `HOLDING` (written BEFORE the request leaves), `HELD`, `NOT_HELD`, `CLEARED`, with an `episode` counter. No Mintsoft order comment, no WooCommerce order note: the warehouse-facing output is an IMS operator task (Sync > Exceptions > Raise a warehouse query). A hold is current only while its row is active for the warehouse order it names; it clears on an OBSERVED status read taken after the hold (the stored snapshot, same warehouse order id, no lookup error, `fetchedAt` later than `heldAt`) that no longer says awaiting confirmation, when the link is MERGED or re-pointed (a merge IMS detected), or when the order despatched. An old or foreign snapshot clears nothing.
- **Connector verb.** `WmsConnector.holdOrder` -> `holdMintsoftOrderForMerge` (`lib/connectors/mintsoft/api/order-push.ts`): the cancel gate (ClientId-scoped ownership read, exact order number, not merged, not cancelled) and the order must be `NEW`, then ONE request. A definite refusal (`Success: false`, or a direct 4xx with no redirect hop) RETURNS `held: false, status: 'REFUSED'`; a transport failure (timeout, 5xx, a 4xx after a redirect, the outbound-write hold, an answer with no verdict) THROWS, so it is never read as a refusal or a hold. The request goes through the producer-side hold (`order.hold`) first; shadowed means nothing is written.
- **Per order, non-fatal.** `HOLDING` row, request, then `HELD` (activity `wms_merge_hold_placed`) or `NOT_HELD` (`wms_merge_hold_failed`, the badge says "Not held"). A transport failure is retried, one attempt per pass, at most 5 in all (an order whose group is no longer detected because its sibling was held is retried from its own row); a refusal is not. One group gets ONE operator task (reason `MERGE_HOLD`) naming the held orders, the orders that are NOT held, the EU customs / IOSS warning and the FedEx "label by hand" warning where they apply, and saying IMS will not release.
- **Lost answer = `UNKNOWN`.** A request that throws (timeout, 5xx, no Success field) leaves the row `UNKNOWN` (may be held; `wms_merge_hold_unknown`), never `NOT_HELD`. The group task is raised when any member is held OR unknown. The upkeep settles it from the stored snapshot (read after the attempt): `AWAITINGCONFIRMATION` = `HELD`; `NEW` = `NOT_HELD` retryable, but only on a snapshot read at least `MERGE_HOLD_NEW_GRACE_MS` (the 10 minute lease) after the row was last written, because a request IMS gave up on may still land late; a recognised status past NEW (`ALLOCATED`, `PICKING`, `PACKED`, `CANCELLED`, ...) = `NOT_HELD` with `refused` (never re-held, the withheld pushes resume); an unrecognised or empty status stays `UNKNOWN` and raises ONE `MERGE_HOLD` task per order and episode (the status is not in the dedupe key; the open task is re-worded). An `UNKNOWN` row that reads NEW after a person already confirmed a sibling of its group (`CLEARED` `left awaiting confirmation`) is `CLEARED` the same way, not retried. `UNKNOWN` rows get the reminder, the "act in" notice and the withdrawal/cancel escalation like `HELD` rows (worded "may be on merge hold"), the status sweep keeps polling an order with an active row after IMS cancels it, and the push sweep runs the maintenance after each run. `requestHold` has an overall deadline (`MERGE_HOLD_REQUEST_DEADLINE_MS`, 3 minutes) shorter than the lease. A `HOLDING` row younger than 10 minutes is an attempt in flight and is not touched. A retry that meets `NOT_HOLDABLE` is `HELD` when the snapshot shows it held, else `UNKNOWN`. The merge-candidate task is not resolved while a member is `HOLDING`/`UNKNOWN`. A HELD row is only cleared by a recognised non-held status (never by `''` or an unknown name: a task is raised instead). Every transition writes an activity entry.
- **Decided groups.** A row cleared with `left awaiting confirmation` or `merge detected` for the same group basis (= same member set) and warehouse order is not held again (`decideBeginHold`); neither is a group whose candidate task a person marked Done. A changed group has a new basis and is a new decision.
- **Reminder.** After `MERGE_HOLD_REMIND_HOURS` (environment variable, default 4; a non-positive or unreadable value is 4) a hold that is still `HELD` gets, ONCE (compare-and-set on `reminded_at`, in one transaction): an operator task (`MERGE_HOLD_OVERDUE`), a WARNING activity entry (`wms_merge_hold_overdue`) and a notification; the sales order badge turns red ("Merge hold overdue").
- **While held.** The push sweep's amend, hold and cancel queries leave the order out, so an edit, a cancel, a full refund or a withdrawal hold is not pushed and the hold is never cancelled or released by IMS. A pending edit shows under Exceptions as `WMS_ORDER_AMEND` / `WMS_MERGE_HELD` ("Act in Mintsoft"; closed when the hold clears). A withdrawal (pending or approved) or a cancel / full refund raises ONE `MERGE_HOLD_WITHDRAWAL` task per episode for a person. The withdrawal flow's own cancel-based hold of OTHER orders is unchanged.
- **Where it runs.** Placement at the end of the merge-candidate detection pass (inside its lock, after the group's candidate task); maintenance (clear, remind, blocked changes) at the end of every order-status sweep. Both only touch IMS tables except the one `holdOrder` request per order. A failure in either is logged and never reaches the sweep.
- **Not covered / accepted.** A third order that arrives while two are held is not grouped (a held order is no longer `NEW`); the person merging sees it in Mintsoft. The snapshot status name for a held order is assumed to be `AWAITINGCONFIRMATION` (`MERGE_HOLD_WAREHOUSE_STATUS`, matched case/space/underscore-insensitively); if Mintsoft names it differently the hold clears on the first fresh read (fail-safe: IMS then pushes again) and no reminder fires.

## Systemic-Failure Circuit Breaker (order push and dispatch sweeps)

Dead-lettering is isolation, and isolation only makes sense when the thing isolated is the exception. A Mintsoft schema change, a broken endpoint or an expired credential fails every order at once; parking them one at a time quarantines the whole tenant and demands a manual replay after the dependency has recovered. So the sweeps that park a record after exhausted retries decide that park **once, at the end of the pass**, where one broken record and a broken connector can be told apart. The rule is the one the woo-mintsoft sync plugin runs (`MINTSOFT_SYSTEMIC_*`), ported parameter for parameter. The decision is the pure function `decideSystemicFailure` in `lib/domain/wms/systemic-failure.ts`; the persistence and the incident are in `lib/domain/wms/systemic-failure-store.ts`.

| Parameter | Value | Why it exists |
|---|---|---|
| Floor (`SYSTEMIC_FAILURE_MIN_RECORDS`) | 3 | The ratio alone misfires on a quiet tick: one failing order of one is not an outage. |
| Ratio (`SYSTEMIC_FAILURE_RATIO`) | 0.5 | The floor alone misfires on a big store: three broken orders among two hundred are not an outage. Floor **and** ratio must hold. |
| Bound (`SYSTEMIC_MAX_CONSECUTIVE`) | 5 | Suppression must be bounded. Three permanently broken records in a three-record cohort would otherwise read as systemic for ever and never be isolated. After five consecutive systemic passes the sixth parks per record anyway. |
| Endpoint passes (`SYSTEMIC_ENDPOINT_FAILURE_PASSES`) | 3 | A one-record tenant can never meet the floor, so a total outage there would be silent for ever. Every attempt failing for three passes running raises the incident at any size. It reports; it never withholds a park by itself. |

**What a pass counts.** `attempted` is the records the pass actually asked the warehouse about (a write the outbound-write hold refused is not an attempt); `failed` is every one that failed this pass, **not only those that ran out of retries** (retry clocks are staggered, so during an outage three old orders may exhaust while ninety-seven equally broken newer ones have not, and scoring only the exhausted subset would park the three mid-outage); `exhausted` is the subset that would be parked. Nothing is at stake unless `exhausted` is above zero.

**What a systemic pass does.**

1. Parks nothing. A record that has run out of retries is written as the retryable state it would be after any other failed attempt (`PENDING_CREATE` / `PENDING_VERIFY` with the attempt count at the bound, or the dispatch failure count at the bound with no dead-letter stamp), so every record stays eligible and recovers automatically once the connector answers.
2. Raises **one** incident per sweep per connector: an activity row, an `error` notification to each active admin (individually, never a broadcast) linking to `/sync/exceptions`, and a read-only **WMS connector-wide failure** section on that page. A fault that lasts a hundred passes announces itself once.
3. Increments a persisted consecutive counter in the settings row `wms_systemic_failure:<connector>:<sweep>` (reserved: it cannot be written from the settings UI). The row is the incident: it exists while the incident is open.
4. After the bound, the sweep isolates per record as it always did, and **says so**: the incident is escalated (second notification, the page row reads "Isolating one by one again"). The counter stays saturated so the next pass of the same fault keeps isolating.
5. A clean pass, or a per-record pass (attempts, but not mass failure), resets the counter and resolves the incident (an activity row records it). A pass that attempted nothing changes nothing. A mass-failure pass with nothing exhausted yet leaves the counter alone.

**Fail toward the old behaviour.** Suppression is only safe while it is counted. If the state row cannot be read, or the suppressing verdict cannot be saved, the pass isolates per record instead and logs why: an uncounted suppression would be an unbounded one. The breaker never throws into the sweep it protects.

**Covered sweeps.**

| Sweep | What is deferred | Counter key |
|---|---|---|
| Order push, create pass (`wms-order-push`) | the DEAD_LETTER of an order whose create failed for the 5th time; parked at the end of the pass by compare-and-set on the claim stamp the pass wrote | `order-push` |
| Order push, verification pass | the quarantine of a link still unverifiable after 5 attempts; compare-and-set on `PENDING_VERIFY` | `order-push-verify` |
| Dispatch sweep (`mintsoft-dispatch-sync`) | the dead-letter of a link at 5 consecutive reconcile failures (`deadLetterDispatch`, the same compare-and-set as before) | `dispatch` |

Not covered, because they have no retry-then-park mechanism: the stock sync, the order-status sweep and the order-reconcile sweep. The unresolved-record quarantine of the dispatch sweep (an unreadable record, not a failed call) keeps its own older breaker (see Dispatch Ingestion & Reconciliation). The other DEAD_LETTER writes in the push sweep (a hold with no confirmed remote cancellation, a link that belongs to another tenant) are decisions about one record's evidence, not exhausted retries, and are unchanged.

**Exit status.** A systemic pass is a **failed** cron run (HTTP 500), not a quiet green one. Every attempt in it failed, the run-log and monitoring read the exit status, and handling an outage gracefully is not a reason to report success. Skipped and held keep their meaning (a deliberate no-op, and the outbound-write hold). The order-push result carries `systemicSuppressed`, which the cron mapping reads as a failure; the dispatch result carries the same field and its error count already fails the run. The verdict is also written as a `WmsSyncLog` error row on the dispatch job so it is queryable.

No feature flag: behaviour changes only on a pass where records failed, and the breaker fails toward the previous behaviour.

## Producer-Side Hold For Mintsoft (before the grant, and after it)

The outbound-write grant (`MINTSOFT_WRITE_ALLOWED`) is the transport's permission. A second, earlier check decides whether IMS should PRODUCE a Mintsoft write at all. It is off by default; when `PRODUCER_HOLD_ENFORCED_DESTINATIONS` names `mintsoft`, a write is produced only once both the grant and `MINTSOFT_WRITES_LIVE_FROM` are in force and the ownership map says IMS owns that operation (IMS owns `mintsoft.order.amend` from the live phase, judged on the time of the change being propagated, not on when the order was paid, so an order the bridge created is amended once it is changed after the live-from instant, while a change made before it stays a shadow; only an order create is limited to orders paid from the live-from instant; ASNs and order notes are done by hand in Mintsoft until then). See "Producer-side hold" in the installation guide for the variables. Until then every Mintsoft write IMS would have made is kept as a *shadow record* in `outbound_shadow_writes` (destination `mintsoft`, operation, the order or product, how many times it was produced) and nothing is claimed, queued or sent.

- **Order push.** The `wms-order-push` cron claims nothing: no `WmsOrderPushLink` is created, stamped or moved for a shadowed order, so an eligible order is simply offered again on the next sweep and the first sweep after writes are allowed picks it up. While the hold stands the create pass walks the eligible orders by a rotating cursor (a setting), so every eligible order gets its shadow record within a few sweeps instead of the same oldest batch being recorded every time. Because no link exists, the daily order reconcile does not report these orders as "not pushed" while the hold stands, and it closes findings it had opened before with an explicit held disposition; an order's hard delete is refused while a durable warehouse shadow record exists for it (the bridge may have created the warehouse order). Amendments, holds and cancellations of already-pushed orders are shadowed per order and touch no link. The passes that only re-open a create (releasing a held order, revalidating a failed payload, re-queuing an unknown create) stand down. A link that is waiting for its ownership to be proved (`PENDING_VERIFY`) or is parked as an unknown create (`AMBIGUOUS_CREATE`) is never turned into a shadow, and the verification itself (a read) goes on. The sweep result carries a `shadowed` count only when something was shadowed.
- **Buttons.** **Replay** on an order's push chip and **Re-push** in the exception inbox are refused with the sentence "Not sent by IMS: writes to Mintsoft are held on this installation (...)" and change nothing: no link is re-queued and no finding is resolved. **Create ASN** (purchase order and transfer) is refused with the same sentence before any reservation, sync job or request exists, so nothing is left pending. The product and bundle **verify** buttons report how many products or bundles were *not* sent.
- **Products, bundles and content.** A product that would have been created or updated is shadowed without stamping its payload hash or sync time, so it is offered again until it is really sent. A bundle is shadowed before its claim slot is taken. Product descriptions and pictures keep their own record on the product link and are additionally gated by the same switch.
- **Notes.** The warehouse notes the sweep posts and the note added when an order that was pushed is refunded are shadowed too; the refund itself completes as it always did.
- **Last barrier.** Whatever slips past, the Mintsoft transport refuses any write while the destination is not live, before the key is even looked up (so a held write cannot mint a key). The refusal uses the outbound-write hold's own wording, so queues that recognise a hold spend no attempt on it. Reads, the despatch poll, the stock alignment and key handling are unaffected.
- **A shadow does not say Mintsoft is unchanged.** The sentence names who owns the operation in the current phase (for example the WooCommerce-Mintsoft plugin for order creation). IMS did not send it; look in Mintsoft before acting on the assumption that the order, product or ASN does or does not exist there. A shadow is never delivered afterwards: when writes are allowed, IMS produces from the current state (an order paid before the live-from instant is never created by IMS).

## Dispatch Ingestion & Reconciliation (Phase 8)

The reverse direction — WMS despatch → IMS shipment — is driven by the **connector-agnostic** dispatch sweep (`lib/domain/wms/dispatch-sweep.ts`, hoisted from the Mintsoft module in `q66in.1.3`), triggered by the `mintsoft-dispatch-sync` cron (`/api/cron/mintsoft-dispatch-sync`, every 15 min, a registered job that is on by default and reaches the crontab through the in-app scheduler's Save & Apply; it never logs in, so it needs a fixed API key or an unexpired stored key (see Authentication) — the poll is Mintsoft's path; a push-primary WMS would ingest despatch via webhooks instead). It polls pushed-but-not-shipped links (`WmsOrderPushLink.state` in `SYNCED`/`MERGED`) and feeds despatches into `applyExternalFulfillmentUpdate`, which progresses the IMS shipment to `SHIPPED` and carries the tracking number/courier through (and, for storefront orders, onward to WooCommerce so the customer is emailed — see [`woo-mintsoft-plugin-parity-gap.md`](./todo/woo-mintsoft-plugin-parity-gap.md)). The per-order step `reconcileOneOrder` is exported so a webhook-primary WMS can reconcile a single order on a shipment event.

- **Despatch detection.** Each connector normalises a `dispatched` flag onto `WmsOrderStatus`/`WmsOrderPart` (Mintsoft: status `DESPATCHED`/`INVOICED` or a tracking despatch date), so the sweep stays connector-agnostic. Mintsoft is the only WMS connector as of `o3d-remove-shiphero`; the seam is exercised by a fictitious connector in `tests/wms-second-connector-seam.test.ts` — see [`archive/shiphero-connector-removal.md`](./archive/shiphero-connector-removal.md).
- **Split orders.** Mintsoft can split an order into N parts that despatch independently. Each despatched part is pushed to the storefront as a **partial shipment** (the onetwoInventory Helper plugin records it into the storefront's partial-shipment UI + customer email; idempotent per part). The IMS order is marked `SHIPPED` only once **every** part has despatched, using `NumberOfParts` as the authoritative total. Tracking from all parts is aggregated onto the single IMS shipment.
- **Merged orders.** When Mintsoft merges an order into a survivor (combined `a+b` OrderNumber), the original WMS order is destroyed. The link is **repointed** to the survivor and parked `MERGED` so the outbound push sweep's update pass skips it (no dual-sync amending the survivor). The hold and cancel passes DO select `MERGED` links, but they never cancel the survivor: it holds the other orders' goods too, so IMS records an **operator notice** on the link (see *Holds and cancellations Mintsoft cannot honour* below) and leaves a warehouse note on the survivor naming what to take out. For a **cancel or full refund** IMS first tries to take that order's own lines out of the survivor by their recorded item ids (see *Removing a cancelled order's lines from a merged order* below) and raises the notice only when it cannot do that whole. A merged **and** split survivor is reconciled **atomically** (no per-part partial shipments — its parts mix several original orders), completing the IMS order when the survivor is fully despatched.
- **Full-coverage refusal (o3d-okbd).** Before a despatch is applied as `SHIPPED`, the IMS shipment lines are compared against ordered quantity **net of refunds**, in leaf (component) units — the same basis the dispatch cap and the allocation-coverage selector use. If they do not cover it, the update is **refused** and logged as `external_fulfillment_short` (WARNING) naming each short line, rather than marking the order shipped for less than left the warehouse. Unlike an operator shipping short, there is no outstanding remainder here for a later shipment to carry: the goods have already gone, so accepting it would permanently under-book stock movement and COGS and leave the difference on hand in IMS. Resolve it by allocating and adding the missing units to a shipment, or by closing the order short deliberately (`ALLOCATED`/`PICKING`/`PACKING` → `SHIPPED` is a legal manual transition with the `sales.process` permission). Lines that can never carry shipment coverage — description-only lines and non-stock-tracked `NON_INVENTORY`/`VARIABLE` lines — are excluded. A refund reduces the demand it actually returns, line by line; a `FULL` refund is **not** a blanket exemption, because `refundStatus` reaches FULL on a monetary-only refund (store credit, shipping-only, unlinked external) that returns no goods — and a monetary refund cannot un-ship what the 3PL already dispatched. Nor does a refund whose OWN record says the goods already left: one that **restocked** to a return warehouse (goods can only be received back if they went out, and `buildRefundFallbackReturnRows` refuses to restock a line with no despatched shipment behind it) or one marked a **chargeback** (scjz.70 suppresses restock and COGS reversal precisely because the customer keeps the goods). Netting either out of demand would let the matching outbound be skipped while the inbound was still booked. What does net is the ordinary case a quantity-bearing refund line is for: a line cancelled before it shipped, with no return warehouse and no chargeback.
- **Idempotency.** A dispatched order reconciles to `SHIPPED` and drops out of the poll set; partial-shipment pushes are de-duplicated per `(order, part)` on the storefront side.
- **Holds and cancellations Mintsoft cannot honour.** An IMS hold or cancel is propagated by cancelling the Mintsoft order, which Mintsoft only allows while it is `NEW`. When it cannot be done, the link is **not** dead-lettered (a dead-lettered link leaves despatch polling, so the despatch that follows would never be recorded). Instead the link stays `SYNCED`/`MERGED`, `hold_notice_at` / `cancel_notice_at` is set, the reason is written to the link's last error, one warehouse note is posted, and the order appears in **Sync → Exceptions** ("Hold / Cancel not honoured by the warehouse"). The hold and cancel passes skip a link that carries the notice for that intent: one attempt, one note. The cases are: the Mintsoft order is already **past NEW** (picking, packing, despatched); the order **404s** (a 404 is never recorded as a successful cancel or hold, because an order merged into another one looks the same, and a "held" order would later be re-created and picked twice); and the link is a **merged survivor**. The warehouse note is stamped delivered (`hold_notice_comment_at` / `cancel_notice_comment_at`) only once it has been posted, and only while the link still has the same notice, state and warehouse order it was posted for; a failed, held or unsupported note is retried on later sweeps while the notice stays (a note has no remote idempotency key, so a repeat is possible only if the post succeeded and recording it failed, or two sweeps overlapped). A notice is cleared when the IMS order leaves the held or cancelled state, so a later hold or cancel is sent and noticed afresh (a release and re-hold inside one sweep interval cannot be told apart). Nothing about the IMS order, its stock or its money is changed by a notice. A despatch that follows a hold is applied as usual. A despatch that follows an IMS **cancel** is never applied to the cancelled order (its stock was released): the dispatch sweep keeps polling a cancelled order that carries a cancel notice, and the dispatch sweep refuses it (for any order IMS intends not to ship: cancelled, fully refunded and not yet despatched, judged on the order's current state, which is the cancel pass's own test; a leftover cancel notice alone never refuses a shipment) BEFORE any split-part storefront push or shipment write (`applyDispatch` refuses as well), so it surfaces through the ordinary dispatch dead-letter path for a person to decide. The cancel intent is re-read immediately before each split-part storefront write; the window that remains is a cancel or refund committing between that read and the POST, which IMS cannot close (the partial shipment then reaches the storefront for an order IMS cancelled, and the rest is refused) (recall the goods or reinstate the order).
- **What the live API does (checked 2026-11-10).** A duplicate `OrderNumber` gets HTTP 200 with `Success:false, OrderId:0` and "Order Number already exists!", and a cancelled order keeps its number, so the duplicate answer can point at a cancelled order: IMS selects the existing order only when exactly one same-client row on a complete search page carries BOTH this order's `OrderNumber` and its own `ExternalOrderReference` exactly (a reused reference under another number is another order), reads it back by id, checks the same two fields on that read (the search row's own status is not trusted), and refuses to bind unless that read shows a present status other than `CANCELLED` (status 3); otherwise the push fails for an operator. `Order/Search` finds an order about a second after creation and echoes `ExternalOrderReference`, but it is a term search (order number, tracking number, reference) returning at most 10 rows with no documented ClientId filter, so the reconcile read filters by ClientId and exact fields itself, treats a full page as possibly truncated, and never adopts a cancelled order. `/Cancel` works on a `NEW` (1) or `ONBACKORDER` (9) order; on an already cancelled order it still answers `Success:true` ("was already cancelled"), so IMS reads the order's status first and reports `ALREADY_CANCELLED` as its own outcome (satisfies a cancel, never counts as a confirmed hold). **Merges (live-confirmed):** when order B is merged into C the survivor keeps C's id, its `OrderNumber` becomes `<absorbing>+<absorbed>` (so an IMS order's number can be ANY part), its `ExternalOrderReference` stays the absorbing order's, and it gains the order name/value `MergedOrder=True`; B then 404s on every endpoint, exactly like a deletion. `Order/Search` by either original number returns the survivor. All original item ids carry over, and nothing says which order a line came from. THE COMBINED NUMBER IS ONLY A CANDIDATE FILTER, NEVER PROOF (a survivor "A+B+C" lists B too and may be someone else's): before a link is re-pointed at a candidate survivor, IMS reads the candidate's lines fresh and requires that they contain EVERY recorded line id of this order (`wms_order_push_items`, trusted ids only) with the recorded SKU and quantity (`proveMergeLineage`, `lib/domain/wms/merge-lineage.ts`). A missing or untrusted record, an unreadable candidate, or any absent or different id means no re-point: the link stays as it was and the hold / cancel notice says the order was not found and a possible merge could not be proven, to check it in the WMS. Every re-point is a COMPARE-AND-SET on the link still being what was read: the dispatch sweep's `repointLink` matches only a live (`SYNCED` / `MERGED`) link still on the candidate's warehouse order id and answers false otherwise, in which case nothing is written, no despatch is applied and the link is left unresolved for the next sweep (a cancel that marked it `CANCELLED` between the proof and the write is never flipped back); the push sweep's re-points already used `updateLinkIfLinked`, and the amendment mismatch notice now uses `updateLinkIfState`. The same proof guards the dispatch sweep's re-point (`WmsDispatchSweepDeps.proveMergeLineage`), which otherwise would also apply the survivor's despatch to this order; there the link stays unresolved for a person. So when a hold or cancel meets a 404, IMS does one read-only `Order/Search` by the order's own number: if exactly one same-client result has that number as an exact `+` part AND carries `MergedOrder=True`, the link is re-pointed at it as `MERGED` and the MERGED operator notice is raised (note on the survivor); otherwise it is the plain not-found notice. The lookup answers FOUND, ABSENT or INCONCLUSIVE; only ABSENT (a conclusive search with no such order) gives the plain not-found notice. A lookup that fails, returns a full page of 10 or finds several candidates is INCONCLUSIVE: nothing is stamped, the link stays in the hold/cancel pass with a transient reason, and it is retried for 5 sweeps (counted on the link), after which an operator notice says the merge check could not settle it. IMS never cancels the survivor for one of its orders while it holds another order's lines (see **Removing a cancelled order's lines from a merged order** below).
- **Removing a cancelled order's lines from a merged order (live-confirmed 2026-11-12).** The merge keeps every original line on the survivor under its ORIGINAL Mintsoft item id, even when both orders carry the same SKU (two separate lines, never consolidated), and `DELETE /api/Order/{survivorId}/Items/{itemId}` answers `200 {Success:true, Message:"OrderItem: <SKU> removed from Order"}`: the message names the SKU, not the line, so only a re-read proves which line went. IMS therefore records the item ids of every order it pushes in `wms_order_push_items` (link, Mintsoft order id, item id, SKU, whole quantity): one `GET /api/Order/{id}/Items` read-back right after the create (the create response carries no lines) and a fresh snapshot after an accepted amendment (an amendment can delete, add or consolidate lines). The read-back is best effort and never fails the push; a failed one stores nothing and the order keeps the operator notice. Nothing is backfilled.
  When an IMS order whose link is `MERGED` into a survivor is cancelled or fully refunded (the same cancel intent and selection as any cancel; reached either from a `MERGED` link or straight from the 404 that finds the merge), the cancel pass asks the `order.cancel` producer seam (a shadow, or the outbound write grant being off, sends nothing and changes nothing) and calls the connector's `removeOrderItems`: (1) the survivor is read through the ownership gate and must be NEW (1) or ON BACKORDER (9), the statuses `/Cancel` works on; (2) its lines are read strictly and every stored item id must be present with the stored SKU and quantity, BEFORE any delete; (3) when the stored lines are ALL the survivor holds nothing is deleted and the survivor is cancelled normally (`ONLY_LINES_LEFT`); (4) one `DELETE` per stored item id, each followed by a re-read that must show that line gone and every other line exactly as it was. On success IMS tries to leave one warehouse note naming the order and the lines removed (best effort, through the `order.comment` seam: a note that is shadowed or fails to post is audited but not retried, so it is not guaranteed; the removal itself is verified by the re-reads, not by the note), and the link becomes `CANCELLED` (absorbed-order semantics: it leaves despatch polling; the survivor continues under the other order's link). Any other outcome (stored ids missing, status past NEW/ON BACKORDER, line missing or different SKU/quantity, a delete or re-read that fails or is inconclusive, another line changing) falls back to the MERGED operator notice, whose reason names the exact SKUs, quantities and item ids still to be taken out, and, when some deletes had already landed, what was removed (those ids are forgotten) and what remains. Nothing is retried after a refusal (the notice stops the pass). A hold of a merged order still only raises the notice. The ABSORBING order keeps the survivor's id, so its link can still be a plain `SYNCED` link: `cancelMintsoftOrder` (hold and cancel) reads the order by id through the ownership gate first and, when it is flagged `MergedOrder=True` or its number is a combined `a+b`, answers `MERGED_SURVIVOR` without calling `/Cancel`; the sweep re-points the link as `MERGED` (compare-and-set) and takes the cancel through the same removal path (a hold raises the notice). A failed read throws before anything is sent, so the link stays retryable. A merged order is ONE flagged `MergedOrder=True`; a `+` in the number alone does not make an order merged. The only caller that may cancel a merged order is the last-lines case, through the separate `cancelMergedOrder` method (same `order.cancel` clearance, given the stored lines): the connector re-reads the survivor's lines immediately before `/Cancel` and cancels only while they are still exactly this order's stored lines, otherwise it answers `MERGED_LINES_CHANGED`, cancels nothing and the notice is raised. Mintsoft has no conditional cancel, so a line added in the sub-second gap between that re-read and the `/Cancel` is an accepted inter-system race limit.
  The recorded line ids are stored ONLY when they provably are this order's: the order read back must not be flagged merged (a merge between the write and the read-back would put both orders' lines on one id) and its lines must match exactly what IMS sent (a create: the same SKU and quantity line for line; an amendment: the same quantity per SKU, since it consolidates duplicates), with no extra line. Otherwise nothing is stored, the reason is logged, and a later removal falls back to the notice. After an ACCEPTED amendment the stored set is replaced by a verified re-read; when that cannot be had (the read-back failed or did not match, the write failed, or the line amendment itself did not finish) the old set is DELETED, never kept, so a later removal cannot work from lines that predate the amendment: with no stored ids it raises the notice. (No per-amendment version stamp: instead `line_snapshot_unsafe_at` is set on the link BEFORE any amendment is sent, and cleared only by a verified replacement written in the same transaction as the new rows or by an amendment that provably changed nothing. Each mark carries a GENERATION TOKEN (`line_snapshot_token`): only the amendment holding the current token may store its replacement snapshot or clear the mark (compare-and-set, taken first in the transaction so the row lock serialises overlapping amendments); an older amendment finishing late changes nothing and leaves the newer one's mark set. The order-push sweep is NOT single-flight (its cron route `app/api/cron/wms-order-push/route.ts` only rate-limits it, and `runWmsOrderPushSweep` takes no job lock, unlike the dispatch sweep), and its update pass is the only caller of `updateOrder` (no operator action, webhook or dispatch path amends a warehouse order), so two overlapping sweeps could amend the same link. A DURABLE PER-LINK LEASE (`amend_lease_owner`, `amend_lease_expires_at`, 10 minutes) therefore covers the whole remote amendment: it is taken by compare-and-set together with the mark before anything is sent, a link whose lease another owner holds is skipped (left due, nothing written), the snapshot write releases it (or the failure path releases it leaving the mark set), and while it is live `readOrderItems` answers none so a merged removal cannot settle. The acquisition also reports whether the mark was ALREADY set (an earlier amendment interrupted after changing lines but before its snapshot): an attempt that then writes nothing (not NEW, or refused as merged) only releases the lease and never clears a mark it did not set, so a pre-existing mark is cleared ONLY by a verified replacement snapshot or by deleting the stored ids (the only paths that clear `line_snapshot_unsafe_at`: the token-guarded snapshot replacement, including the empty set, and the un-mark of an attempt that set the mark itself). THE CREATE WRITES ITS SNAPSHOT IN THE SAME TRANSACTION AS THE SYNCED LINK (`upsertCreatedLinkWithItems`: the link upsert, the reset of any stale lease and mark, and the order's line-id rows, in one transaction), so there is never a moment when a link is live without its create snapshot, and no amendment can take the lease before the snapshot exists. If the read-back failed or found nothing (`items` null or empty) the link is written SYNCED with the untrusted-ids mark SET in that same transaction, never trusted-and-empty. The tokenless snapshot write no longer exists: `replaceOrderItems` takes a REQUIRED token (a compare-and-set on the link still holding it) and its only callers are the amendment paths; a source test pins that every call passes the amendment's token. The generic `upsertByOrder` is untouched for every other caller; a port without the new method falls back to it and stores no snapshot (so nothing is trusted). The only paths that clear the mark are the token-guarded replacement and the un-mark of an attempt that set the mark itself. THE MERGED-ORDER REMOVAL TAKES THE SAME LEASE, so removal and amendment are mutually exclusive: `claimLineIdsForRemoval` locks the link row (`SELECT … FOR UPDATE`), and in that one transaction checks the lease, the mark and the recorded ids, and takes the lease; the lease is held through the remote removal, the `/Cancel` and the link settlement and released afterwards (also when the work is shadowed or fails). While another owner's lease is live the removal is skipped and the link stays due (nothing sent, written or noticed); an amendment that finds the removal's lease live is skipped likewise. An EXPIRED lease is taken over with the mark kept, and the previous owner's late snapshot write fails its token compare-and-set. The accepted limit: a remote write that stalls for longer than the lease (several request timeouts) can still land after a takeover; the next amendment's verified re-read and the per-delete re-reads of a removal narrow, but cannot close, that window. While it is set `readOrderItems` answers none, so a crash, a partial amendment, or a failed cleanup can never leave stale ids trusted: the merged-order removal falls back to the notice. If the mark cannot be written nothing is sent.) The replacement (or deletion) is written BEFORE the link advances (`pushedAt`), so a crash between the two leaves the amendment still due and never a current-looking link over a stale snapshot; if even the deletion cannot be written the link is not advanced. ONE IDENTITY GATE FOR EVERY WRITE TO AN EXISTING ORDER: `verifyWarehouseOrderIdentity(detail, { orderNumber, clientId, id })` (pure, `lib/connectors/mintsoft/api/order-push.ts`) judges the fresh order detail the write path just read and answers `OK` (the number is present and equals the number IMS pushed, with the same id and client, and the order is not flagged merged), `MERGED` (flagged `MergedOrder=True`, checked first), `MISMATCH` (a present number, id or client that is not this order's, including an UNFLAGGED combined `a+b` number) or `UNVERIFIABLE` (the number, id or client is missing, or the caller could not say which number to expect). Only `OK` proceeds; `MERGED` goes down the merged paths, which verify lines; `MISMATCH` and `UNVERIFIABLE` write NOTHING, leave the link live and not `MERGED`, and raise a notice once. The write entry points are `updateMintsoftOrder` (amend, including the courier change and the item reconcile), `cancelMintsoftOrder` (cancel AND hold: the connector's `cancelOrder`, `cancelMergedOrder`) and `removeMintsoftOrderItems`; each reads the order through `fetchMintsoftOrderStatusId`, which calls the gate, and the connector contract now carries the expected number (`cancelOrder(id, { orderNumber }, clearance)`, likewise `cancelMergedOrder` and `removeOrderItems`; the sweep passes the link's recorded number, the pushed number for a created order). `IDENTITY_MISMATCH` / `IDENTITY_UNVERIFIABLE` on a hold or cancel raise the ordinary hold / cancel notice (once; the passes skip a link carrying it) saying the order could not be verified and to check and act by hand, with no note posted on the unverified order; an amendment gets the durable amendment notice. The one deliberate exemption is `addMintsoftOrderComment` (an additive fixed-wording note, and the merged-order notices go to a survivor whose number is by definition not IMS's). A source test pins that no other function sends a write to an existing order. IDENTITY IS VERIFIED IMMEDIATELY BEFORE EACH WRITE PHASE: an amendment verifies the order's identity (`identityRefusalBeforeWrite`: the detail is read and `verifyWarehouseOrderIdentity` must answer `OK`) directly before EVERY header POST, the first and each courier fallback (the legacy-form and default-courier retries each get their own read; a merge seen before a retry sends no retry), and again before its item changes; an earlier read only decides NOT_FOUND / NOT_NEW and the first refusal. A cancel / hold and a merged-line removal verify in the read that precedes their write. Anything other than `OK` gives the refusal with no write in that phase. A STRUCTURAL SOURCE TEST (an AST walk of `order-push.ts`) requires that every write call site on an existing order (POST/PUT/DELETE or `/Cancel`) is directly preceded, among the requests of its function, by the identity gate, with only read-only item fetches between them; the comment is the one documented exemption and the item helper is checked through its only caller. ACCEPTED INTER-SYSTEM LIMIT: IMS verifies the warehouse order's identity immediately before each write phase (header POST, item changes, cancel/hold, removal). A merge performed in Mintsoft within the single request round-trip between that verification and the write cannot be detected; a human merging in the Mintsoft UI within those seconds can still have the write act on the combined order. AMENDMENTS ARE GATED THE SAME WAY: `updateMintsoftOrder` makes two distinct refusals, both BEFORE any order post or item write: (1) the order read is flagged `MergedOrder=True` -> `MERGED_SURVIVOR`; the sweep marks the link `MERGED` (below); (2) the order is NOT flagged but its number is not the number IMS pushed (a merge whose flag is missing, or a rename; any mismatch, with or without a `+`) -> `ORDER_NUMBER_MISMATCH`: the link is NOT moved to `MERGED` (a number mismatch proves no merge) and stays `SYNCED` and due, and the sweep sets the durable amendment notice (`amend_notice_at`, and the number now seen in the reason) ONCE (only while none is set, so it does not repeat every sweep); a later amendment that succeeds, once the number matches again or the flag appears and the normal paths take over, clears it. That is how the safety for a merge with a missing flag is kept without persisting a wrong `MERGED` state. For the flagged case the absorbing order's link can still name the survivor and the item planner would otherwise diff ALL its lines against one order's and delete or consolidate the other's, so the sweep marks the link `MERGED`, sets `amend_notice_at` and writes the reason on the link: it is listed in **Sync > Exceptions** as "Change not sent to the warehouse (merged order)" with an **Acknowledge** button (`acknowledgeWmsAmendNotice`, compare-and-set, logged) until an operator has applied the change by hand. That amendment is not retried (a merged link is not selected by the update pass). Every write to an existing order is now gated: amend (this), cancel and hold (`MERGED_SURVIVOR`), item removal (stored ids, strict re-reads); the warehouse note is additive and is not gated. The re-read before a last-lines `/Cancel` is required whenever the caller names the lines, whatever the merge flag says on that read: a mismatch cancels nothing, a failed read throws (nothing sent, retried next sweep). Differing prices on a shared SKU do not matter: lines are deleted whole, never edited. Limits: the removal is one read-modify-write per line against a warehouse that can change under it (a picker allocating between the check and the delete); the re-read catches a change after the fact and stops, it cannot prevent one. The producer census and shadow-reader census declare the new sites (it reuses the `order.cancel` operation: it is the cancel of this order's part of the merged order).
- **A create whose outcome was never recorded.** A `PUT /api/Order` that times out, answers 5xx, or whose link write fails may well have been honoured. The link is parked `AMBIGUOUS_CREATE`. Before the presence probe, the ambiguous-create pass runs the connector's `reconcileAmbiguousCreate`: the same ClientId-scoped `Order/Search` the push dedupe uses (a read; nothing is written). If exactly one order comes back, it is not a merged survivor, and its `ExternalOrderReference` equals this order's own id, the matched order is then read back by id and adopted only if that read succeeds, is ours, and carries a status that is not `CANCELLED` (the search row's own status is not trusted; a missing status or a failed read leaves the link parked with the reason shown). The verify pass (by id and by reference) proves an order ours only when it carries BOTH the order number IMS sent AND its own `ExternalOrderReference`, exactly, and a present status other than `CANCELLED`; a field the order does not echo leaves it unverified (retried, then quarantined for an operator), and a present field that differs is another order's. Then, the link is bound to it as `PENDING_VERIFY` (the id is still proved by the verify pass before anything is amended, cancelled or despatched) and no create is sent. A number-only match, several matches or a merged survivor are left parked with the reason on the link. When Mintsoft has merged this order into another (a same-client order whose number lists ours as an exact part), the reason names the survivor and says it must not be cancelled on this order's behalf, because it also holds the other order's goods; Replay shows the same text. **Replay** on such a row runs the same read and links an exact match; it never re-queues a create while Mintsoft holds the order. When the create succeeded and only the link write failed, the id Mintsoft returned is kept (`PENDING_VERIFY`) instead of being discarded.
- **Tool-agnostic.** The whole reconcile (`lib/domain/wms/dispatch-sweep.ts`) is behind the generic `WmsConnector` contract — the connector supplies `fetchOrderStatus` (with `dispatched`/`isMerged`/`isSplit`), `fetchOrderParts`, and `fetchOrderPartItems`; the storefront write goes via the shopping facade. A second WMS inherits dispatch/split/merge by implementing the contract.

## Mixed-warehouse orders (scoped push and despatch; flag `wms_mixed_warehouse_push_enabled`, default OFF)

Design and invariants. With the flag OFF no code below reads the scope columns and every pass is development's: the whole order is pushed and a despatch for an order that holds another warehouse's shipments is refused (`wms_other_warehouse_shipments`, fail closed).

- **Scope** (`lib/domain/wms/mixed-scope.ts`, pure; loaded by `mixed-scope-loader.ts`). A function of the order's allocations, shipments, lines and money. Modes: `FULL` (no allocation or shipment outside the warehouse the link serves: the order is sent exactly as always, byte for byte), `MIXED` (only the units allocated to the warehouse), `HOLD` (a unit is unallocated: nothing is sent, Q1), `REFUSED` (a kit split inside a unit, or a fractional kit, Q4) and `EMPTY` (nothing allocated to the warehouse). Kits are whole units. The discount is pro-rated by sent net (Q3); shipping and the VAT that is not on a goods line go with whichever part ships first (Q2: the Mintsoft part carries them unless a non-Mintsoft shipment has already SHIPPED); every split uses largest-remainder apportionment in minor units. `HOLD`, `REFUSED` and `EMPTY` are local build failures on a create (parked VALIDATION_FAILED, revalidated when sendable; the scope is re-read after the claim). On an amendment they gate the LINE SET only: a standing `WMS_SCOPE_UNSENDABLE` row is written (MEDIUM for HOLD, HIGH otherwise), and a due header change (address, service, notes) is still sent, built on the recorded scope (`loadRecordedScopeForOrder`). `EMPTY` records `scope_frozen_reason = UNSENDABLE:EMPTY` and raises the one standing HIGH row; IMS does NOT cancel the warehouse order for it (the cancel predicate is development's), and moving the units back lifts it and amends the order again. It is examined for a shipped order too (a dirty MIXED link), and the link is stamped so it does not sit at the head of every amend batch. The shipping decision (Q2) is stored once in `scope_shipping_carried` when the part is first sent.
- **Snapshot.** `wms_order_push_links.scope_*` records the scope sent: mode, version (bumped when the part changes), hash, the apportioned money and the checked/dirty/frozen stamps. `wms_order_push_scope_lines` holds the units sent per scope version. `wms_despatch_applications` holds one idempotency-keyed row per applied despatch.
- **Dirty marking.** Every writer of an order allocation, a shipment line, or a shipment's existence or status calls `markWmsScopeDirtyInTx` (`lib/domain/wms/scope-dirty.ts`) in its transaction. `tests/wms-scope-dirty-census.test.ts` fails when one does not (writers that cannot change what is sent are listed there with the reason). The amend pass selects dirty links (flag on only), recomputes the scope, and compares its hash with the one sent: unchanged means no call. Changed and the warehouse order is NEW: amended, the new scope recorded (the dirty mark is cleared only if it was set before the scope was read). Changed and past NEW: frozen (`scope_frozen_reason = NOT_NEW`), a HIGH `WMS_ORDER_NOT_NEW` refusal is recorded (Q5) and the link is no longer re-selected for it. Only a MIXED link is amended in the warehouse it was pushed for (`push_warehouse_id`); every other link amends as before, ship-from changes included. A MIXED link keeps its scoped behaviour when the flag is turned off (link data decides). A scope that cannot be read falls back to development for a link that is not MIXED and for a new order, and fails closed only for a MIXED link. A settled link is never amended.
- **Scoped despatch** (`applyScopedWmsDespatch` in `lib/fulfillment/external-fulfillment.ts`). For a MIXED link the despatch ships only the shipments in the link's warehouse, once per scope version, after checking that the scope IMS would send now carries the units that were sent and that the warehouse's shipments hold exactly the warehouse's allocations; otherwise `wms_scope_mismatch` (retryable, not an error to the dispatch sweep: not counted, never dead-lettered, never read by the systemic breaker, and it does NOT hold the delta watermark; the link stays polled and a standing HIGH `WMS_DESPATCH_SCOPE` row names it). It clears when the warehouse's shipments are all shipped by hand (the despatch then records itself) or the order is reallocated to match. A frozen or FULL/unscoped link whose order is now split is refused the same way while a warehouse shipment is open. A settled link is a no-op for a despatch (flag-independent), and the reconcile and probe selectors skip it. The application row and `despatch_settled_at` are written in one transaction; the order is promoted and the storefront completed only when every shipment has shipped. Dispatch polling and the hold/cancel passes skip a settled link.
- **WooCommerce echo (Q6).** A storefront `completed` for a MIXED link whose warehouse part is open is refused as `wms_part_open` (permanent: acknowledged, and recorded as a refused completion on Sync > Exceptions); nothing is shipped.
- **Known limits.** The scoped despatch does not hold the order lock across its check and the shipment transitions (a concurrent reallocation between them is caught by the next pass's exact-match check, not prevented). A mismatch is re-polled each reconcile rotation and logs a warning each time (unbounded; a person clears it).

## Order Status Chip

In-flight orders show a WMS status chip on the sales list and detail pages. The cached value is refreshed by the `wms-order-status` cron (`/api/cron/wms-order-status`, default every 15 minutes) and the detail page also fetches live on load. The chip deep-links to the order in the WMS admin using the admin order URL template.

The connector builds that deep link and stores it on the cached snapshot (core flows never reference a connector-specific URL format — see the connector boundary). So a change to the admin URL template reaches the **list** chips on the next status sweep, while the **detail** page — which queries the connector live — reflects it immediately.

### NOTFOUND after repeated 404s

Behind `wms_not_found_after_strikes_enabled` (default off, only `true` is on; unreadable is off). While off the sweep is exactly the pre-NOTFOUND behaviour: no strike counted, nothing marked, no task, a NOTFOUND snapshot is polled again, and the first confirmed-absent answer is not re-probed. The rest of this section describes the on state. One-way: nothing resumes polling a marked order except switching the setting off (follow-up filed).

The status sweep counts, per order, the CONSECUTIVE lookups that found an order IMS pushed genuinely absent: `fetchOrderStatus` returned nothing AND the presence probe answered missing (a lookup that failed, or a probe that could not run, neither counts nor resets). A found order, a merged or ambiguous one, resets the count (`wms_order_status_snapshots.notFoundStrikes`). An order IMS has not pushed (no SYNCED push link with a warehouse id) is never counted, because absence is expected until the push settles. An order that IMS pushed is probed on every lookup, not only the first, so a later merge is seen before a strike is counted. Before counting, the absence is confirmed by identity: the connector's by-id read (`probeOrderAmendable` on the stored warehouse order id) must answer the warehouse's own 404 (`NOT_FOUND`); any other answer (the order exists under its id, merged, renamed, past NEW) resets the count, and a failed read or a connector without that read counts nothing. At `WMS_NOT_FOUND_THRESHOLD` (3, the old bridge's threshold) the snapshot becomes status `NOTFOUND` (`notFoundAt` set, `lastError` still the confirmed-absent marker, so the delete guard reads it as an authoritative absence), the order leaves the sweep's batch, and ONE `ORDER_NOT_FOUND` operator task and one activity row (`wms_order_not_found`) are written in the same transaction. Nothing is written to Mintsoft or WooCommerce.

### Configuration-change audit (q66in.7.2)

Connection, binding, courier-map and order-dispatch saves all write an activity entry carrying a **before/after diff**, not just the new values. Only fields that actually moved appear, so an unchanged save is silent.

| Action | Entry |
|---|---|
| Connection save | `mintsoft_connection_updated` — base URL, label, lookup connector, active, auth mode, and **which secret slots were rotated**. Secret values never appear; presence is recorded as booleans and `scrubWmsMutationPayload` masks credential-shaped keys as defence in depth |
| Binding save | `mintsoft_binding_updated` / `mintsoft_binding_created` — every operator-settable binding field, including the stock-sync mode, thresholds, recipients and align-down reason |
| Courier map save | `mintsoft_courier_map_updated` — added / changed / **removed** service names, plus both maps. A removal is logged at `WARNING`: a dropped entry silently falls back to the default courier id |
| Order dispatch save | `mintsoft_order_dispatch_settings_updated` — logged at `WARNING` when the ClientId/ChannelId/WarehouseId delta scope changes, because that also **discards the delta cursors** |

Both the connection save and the order-dispatch save read their **before** image inside the write transaction, behind a row lock on the rows being replaced. Reading it beforehand let two concurrent saves produce an entry describing a transition that never happened — and, for the dispatch save, decide the delta-cursor reset from the same stale value.

Discarding the cursors is not enough on its own, because the sweep is what **writes** them, from another process. A dispatch sweep that started before the scope change commits is still holding an old-scope watermark, and an unconditional write would put it straight back — restoring the reset cursors from a scope that no longer exists, with nothing afterwards to show it happened.

So the reset does two things in one transaction, under the five-row dispatch lock: it deletes the cursors **and** increments `mintsoft_order_delta_generation`. The sweep carries the generation it read its cursors at and writes them only if that number still stands, re-read under the same lock. Comparing the **scope** instead is not sufficient and was the earlier defect: the scope token is a function of the current configuration, so an operator who corrects ClientId 89 → 101, spots the mistake and puts 89 back has caused *two* resets and left the token exactly where it began — the comparison passes and the stale watermark is written over both. A generation is minted once per committed reset by whichever transaction holds the lock, so it never returns to a value a running sweep can be carrying; the ordering comes from the lock rather than from any clock, so no host's time participates.

A refused write is not an error: the pass did its work, its cursors are simply no longer meaningful, and the next run restarts from the lookback window exactly as the reset intended. The advance is **dropped whole rather than merged** — a watermark is one claim ("everything changed up to this instant has been applied"), and a run whose cursors were reset underneath it never established that claim, so there is nothing to combine with the cleared state. It is logged (`the inbound delta cursors were reset during this pass`) because a silently dropped advance would otherwise look identical to a pass that never ran. A write that carries a scope but no generation is refused rather than waved through on the weaker comparison, and changes nothing.

**The generation is also written into the cursor value, because the comparison above only binds writers that run it.** A rolling deploy — or a rollback — puts an instance from a build *before* this fence in front of the same rows, and that instance never reaches any of the checking: it upserts `mintsoft_order_delta_since` with a bare timestamp out of its own bundle. So each cursor row stores `{"g":<generation>,"at":"<instant>"}`, and the reader **ignores a cursor it cannot attribute to the generation currently in force** — unstamped (a pre-fence writer), unreadable, or stamped for a superseded generation — logging which. Ignoring it costs one wider `Order/List` window, which re-applies nothing; trusting it is the unrecoverable direction, because a stale instant that is *later* than anything the current scope has fetched skips every order changed in between and says nothing. **On the first sweep after this ships the existing unstamped cursors read as absent and the delta starts once from the lookback window** — the same work a reset asks for, once.

### Retention (q66in.7.4)

Two System Settings → Data Retention windows cover the WMS tables:

- **WMS Inbound Events** (default 3 months) — **compacts** resolved (`PROCESSED`) rows in `wms_inbound_receipt_events` and `wms_webhook_events`: the `payload` (and the receipt table's `reviewDetails` dry-run image) is cleared, the row itself is kept because `(connector, externalEventId)` is the idempotency key that stops a redelivered callback booking stock twice. `DEAD`, `REQUIRES_REVIEW`, `PENDING`, `PENDING_RETRY` and `FAILED_RETRY` rows are **never** touched — a dead letter is replayable evidence, not an old row.
- **WMS Sync Runs** (default 12 months) — deletes **finished** `wms_sync_jobs` rows, which cascades their per-SKU `wms_sync_logs` lines. Unfinished (`PENDING`/`RUNNING`) runs are kept: an old timestamp on a stuck run is a reason to keep it, not to remove it. So is **the one dry run** each unconfirmed `ALIGN_TO_WMS` binding is waiting on — the exact row `confirmMintsoftAlignmentMode` reads, resolved through the shared `alignmentDryRunEvidenceQuery` so retention and the confirm action cannot ask different questions. It is deliberately one row and not the whole warehouse: a stock sync writes one log line per checked SKU per run and runs on a schedule, so pinning every run for a warehouse would have exempted the highest-volume table here without bound, for as long as an operator left the decision open. A binding with no qualifying dry run pins nothing. The 12-month default matches the 365-day mutation-audit window the runs are correlated with.

## Manual receipts beside an open ASN

`receivePurchaseOrder` refuses a manual receipt for a PO line that has a live ASN row (`closedAt` null and status `CREATE_IN_FLIGHT`, `OPEN`, `PARTIALLY_BOOKED_IN` or `BOOKED_IN` - the creator maps an ASN the warehouse had already received to `BOOKED_IN` and leaves it open while local reconciliation is owed - or `CREATE_PENDING` with `remoteCreateAttemptedAt` set, the state a stale in-flight create is demoted to while the warehouse may already hold the ASN; a `CREATE_PENDING` that was never claimed is an unsent local reservation and does not count). The check runs in the receipt transaction after the `purchase_orders` row lock (the same parent-first order the booked-in service and both ASN creators use, so it takes no ASN lock) and is preceded by an unlocked early read for a clearer message; a call carrying an idempotency token skips the early read so a retry of a committed receipt still reports success. See `lib/domain/wms/po-receipt-asn-guard.ts`. Receipts accepted before the guard existed are untouched; the book-in reconciliation still reads them through the manual-receipt pool.
