### Despatch-switch follow-ups: snapshot lock failure is loud, despatches never wait on it (inventory, WMS)
- The daily inventory snapshot now takes its exclusive floor lock on every real run (not only while the despatch-date switch is effective), so a switch flipped mid-run or a failed settings read can no longer leave a run unfenced. If the lock holder fails after taking the lock (the 4 h cap, a killed backend), the run stops writing, records an `inventory_snapshot_unfenced` ERROR activity row and fails the cron run; a run past half the cap writes an `inventory_snapshot_slow` WARNING. A writing snapshot backfill takes the same lock.
- A warehouse-dated despatch that finds the snapshot holding the lock is refused at once (it no longer holds the order lock and a pool connection for the whole snapshot and then times out) and is applied on the next sweep pass; it is not counted as a failure and raises nothing.
- A held despatched-units mismatch stores Mintsoft's last-changed stamp (the order, or each part) with the units and re-applies them only while the stamp is unchanged. No partial shipment of a split order is pushed to the storefront while such a hold stands.
- Readiness: a warning when the latest snapshot run is older than 26 hours while the despatch-date switch is effective; the stale-lock-date warning now also covers a lock date that was read recently but does not parse.
- The mixed-warehouse despatch path now has the in-transaction units fence the other path already had; the stock-adjustment in-place edit takes the stock-level lock before its guards read.
