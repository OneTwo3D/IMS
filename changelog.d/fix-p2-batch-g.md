### Sign-in and two-factor hardening (security)

- **Adding a passkey, or turning on / replacing two-factor authentication, now needs a recent re-authentication.** A stale session gets the usual "Confirm it's you" box (password, plus authenticator code if 2FA is on) and the action continues. Confirming or disabling 2FA is also rate limited per user (5 attempts / 5 min).
- **Resetting a password by email now removes the user's passkeys**, so a passkey planted from a stolen session cannot outlive the reset. The user signs in with the new password and re-adds a passkey.
- **Authenticator codes are single use.** The matched 30-second step is recorded per user (existing `one_time_tokens` table, no migration); replaying a code at sign-in, in the re-authentication box or when disabling 2FA is refused. Re-authentication is also refused for a session that has not yet completed its 2FA challenge (it was a second, separately rate-limited way to guess the code).
- **Login brute force is bounded without any lockout.** Per account, after 5 failed checks each attempt must wait out a cooldown that doubles (1 s, 2 s, 4 s ... capped at 15 min) from the last failure; it is enforced before the password is checked (the answer is "try again in N seconds"), so guessing is held to about one try per cooldown, and the owner waits the same short time then signs in normally (a correct password clears the counter). A browser that has signed in before carries a signed, HttpOnly device cookie bound to the account; a request with a valid cookie skips the per-account cooldown (so someone failing against the account from elsewhere cannot keep the real user out), while the cookie has its own failure counter and cooldown so a stolen cookie cannot be used to guess. Only one password check per account (per device for a cookie request) runs at a time, so concurrent requests cannot get around the counter. Per IP, only failed attempts are counted, and past 20 (200 when the IP is not known or trusted) an attempt from that address is slowed by 2 s; there is no per-IP lane, so it is never refused for that reason and an attacker sharing a public IP or the unknown bucket cannot stop anyone's correct password. This holds with no trusted proxy configured too. State is in the existing `one_time_tokens` table (no migration). Password-reset requests answer the same silent acknowledgement always; per address there is only a 2-minute cooldown (one email per address per window), so nobody can block someone else's reset, and the per-IP reset caps are skipped when the client IP is not known.
- **`X-Forwarded-For` / `X-Real-IP` are only trusted when `TRUSTED_PROXY_IPS` / `TRUSTED_PROXY_CIDRS` is configured.** Without them the client IP is "unknown" (per-IP caps are skipped; database restore binds its token to the session instead of the IP and stays available). Configured proxy addresses do not authenticate the headers (Next cannot see the socket peer): bind to loopback and firewall the e2e port. New setting `LEGACY_UNTRUSTED_FORWARDED_FOR=true` keeps the old behaviour for a proxied deployment that has not configured the proxies yet. `ims-stage-dev.service` now listens on loopback only. Documented in `docs/installation.md` and `.env.example`.
