### Storefront confirmation e-mail on release: follow-ups to the first release marker (sales, cutover)
- A held storefront import that the import auto-allocated before it was paid is now released by WooCommerce's `processing` (claim of the one-shot marker, one confirmation); an operator hold with no internal token (not a store-reported or EU-withdrawal one) disarms the leftover marker, so a later hold-release cannot fire it.
- The release claim now runs inside the status-change transaction, after the move is validated, together with the queued e-mail (atomic: one winner, no lost e-mail, no armed marker after a crash).
- New `npm run storefront:hand-send` for step W: unpaid held orders (information only), paid pre-switch-on orders by the store's recorded paid time (`--natives-off-at`, `--paid-since`), orders released in IMS without a payment (check first), and an audited, idempotent `--mark-sent <order> --by <name> --yes` that removes an order from the lists (refuses unpaid and IMS-confirmed orders). The release claim records the refusal (with the store's paid time when there is one) for this. IMS still never confirms an order placed before the switch-on.
- A failed external-dispatch batch queues no partial e-mail (unchanged); the lost partial is an accepted, documented limit. A failed release queue fails the WooCommerce webhook so it is retried.
- `bridge_writers_status.py`: system journal only for `journal_earliest`, `/run` and `/usr/lib` journald drop-ins read, boot consistency checked, `--assume-groups` only honoured with a test-only environment variable.
