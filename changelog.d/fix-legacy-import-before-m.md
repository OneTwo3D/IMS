### Legacy bridge import before step M: windowed history, grouped blocker, resolve guards
- `cutover:legacy-import` reads cancelled and refunded WooCommerce orders only when modified inside a window: `--history-days N` (default 60) or `--history-since YYYY-MM-DD`. The window limits linking and the grouped decision only: the whole older history is also read, cheaply and paced, for a queued bridge action, a fence or an unproved verify id, and such an order blocks as `historic-queued`; the report previews the counts (in window, outside it, linked, not linked) before anything is applied.
- A cancelled or refunded order is linked for IMS's own cancel pass only when IMS already shows it CANCELLED. One IMS holds PROCESSING (a missed cancel) or PROCESSING with a full refund (an old despatch the dispatch sweep would apply) is listed instead of imported.
- Every in-window cancelled or refunded order with a Mintsoft order that is not linked is ONE grouped gate blocker, cleared by `--resolve-all-historic-cancelled --as cancelled --reason "..."` (each member is re-read in Mintsoft and must be cancelled or despatched; a new order after the decision blocks again).
- `--statuses` always gets cancelled and refunded added.
- `--resolve`: `not-ours` is refused when the bridge proved the id; `ours` and `cancelled` first read the order's number and status from Mintsoft (read only) and refuse any mismatch; a `--resolve` dry run reports "MET IF RECORDED" (exit 3), never MET.
- A resolve-only `--apply` is audited as `legacy_bridge_import_resolve_applied`. The WooCommerce read compares id sets (a second ids-only walk) instead of X-WP-Total, so a new order mid-walk no longer fails it and a leave plus a join is caught. No migration.
- `--as cancelled` for a Mintsoft order absent by id also needs the order-number search to find nothing. IMS-present historic members have their own `--resolve` path (a merge survivor holding another order is resolved on its own with `--as ours`), and the grouped decision leaves out members that are live, merge survivors, unresolved or found only by number instead of deadlocking. The drift check is anchored on the set's highest id read before the first walk. A refused decision exits 5. `--no-drift-check` (preview only; `--apply` refuses it) skips the second walk. Historic orders IMS holds PROCESSING are flagged, with the create-floor dependency documented.
- Round 3 (the bridge's fence): the bridge's fence is a file on the bridge host and a fenced order carries NO Mintsoft id in WooCommerce, so the import now blocks, inside and outside the window, on the signals WooCommerce shows: a cancelled or refunded order with a queued update or cancel and no id, `_mintsoft_verify_pending` with no id, and `_mintsoft_dead_letter` with no id. They are cleared only by a read-only Mintsoft lookup by order number (`cancelled`: none there or CANCELLED there; `ours`: exactly one live order, which is linked by the id found). The dead `_mintsoft_fence*` rule is removed. A full `--apply` now needs `--bridge-fence-cleared --by <name>` (recorded in the apply audit), the operator's attestation that `var/manual_reconcile.json` on the bridge host is resolved and empty and `var/minted_orders.json` holds no `intent` entries (superseded in round 4: both files are now given and every entry resolved).
- A decision on an order with no readable id is never passed without a Mintsoft read; `--as not-ours` on a cancelled or refunded order with a verify id needs both the id and the number search to say absent; a merge survivor adopted with `--as ours` is MERGED when Mintsoft's number is "a+b" or its MergedOrder flag is set; orders the history cutoff dropped are checked by the outside check directly; the outside history is read first; every refusal through the run exits 5; a Mintsoft read error in the grouped decision leaves out only that member. No migration.
- Round 4 (journal and fence files): WooCommerce can show nothing for an order the bridge's journal or fence holds (the plugin deletes the queue entry when a customer cancels an order with no id and no verify marker), so a journalled Mintsoft id with a lost writeback could ship for a cancelled order while the gate read MET. A full `--apply` now requires `--bridge-journal <path>` and `--bridge-fence <path>`, copies of the bridge host's `var/minted_orders.json` and `var/manual_reconcile.json`, parsed strictly (an unreadable file or unknown format refuses). Every journal entry (an id, `intent`, `intent-unseen`) of an order with no trusted Mintsoft id in WooCommerce is a `journal-unlinked` blocker and every fence entry a `fence-entry` blocker (inside the window, outside it as `historic-queued`, or, when the order was not read, unresolvable until it is); they are resolved with `--resolve <id> --as ours|cancelled` through a read-only Mintsoft lookup (by the journal id, or by the bare number for an intent). The attestation now means every entry was RESOLVED, not cleared; both files' sha256 and entry counts are recorded in the audit. The docs and runbook step M say to copy both files after the final sweep.
- The Mintsoft number lookup uses the BARE WooCommerce number (what the bridge sent), and `--resolve` is refused while `woocommerce_order_prefix` is set. `--resolve <id> --as ours|cancelled --mintsoft-id <n>` names the order when the lookup is AMBIGUOUS (re-read, must carry the number, the choice is recorded). The `sync-pending-no-id` wording now matches the plugin (it deletes the queue entry when there is no marker). A dry run or resolve-only run without the files or the attestation reports `met-pending-bridge-step` (exit 3) and says what is owed, never MET. No migration.
