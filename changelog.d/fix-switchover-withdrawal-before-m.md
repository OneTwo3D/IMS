### Switchover: withdrawal-outcome and PR B follow-ups before step M (cutover)
Everything here stays inert until step M is live and `wc_withdrawal_outcome_enabled` is on, except the invoice-note clean-up and the stock-drift acknowledgement (both operator-side). Companion plugin 1.5.2 is NOT deployed.

- **A later request B is never lost.** A rejection stored under the unknown request key is no longer copied to a newly known request id (never aliased for a rejection; a note only aliases for the same hold generation), and the "another request" check now also covers the unknown key, so a second request whose id was never captured raises one operator task per submission instead of being skipped silently.
- **Operator tasks are keyed on request and generation.** `WITHDRAWAL_REJECT_NOT_WRITTEN` no longer dedupes on order and action for good: the request key and the hold generation are in the dedupe basis, so a later failure on the same order raises a task even if an earlier one was closed.
- **Hold generation moves only on a real new submission.** The `order.updated` echo of IMS's own outcome write (the plugin saves the done-marker on HPOS) no longer bumps `withdrawalHoldGeneration`, so it cannot raise a false "another request" task or make an operator release look stale. The outcome identity read-then-write now runs under the order's row lock.
- **Companion plugin 1.5.2 (not deployed).** The captured request id is a top-level order response field `_oti_wdraw_request_id` (no synthetic id-0 `meta_data` entry that a round-tripping client could persist; the `_oti_wdraw_request_id` order meta is no longer read), kept in one option per order (`oti_wdraw_req_<order>`) so two simultaneous captures cannot lose an entry. The capture only starts once IMS has posted its first outcome: a request filed before that ends as a "reject by hand" operator task (documented, accepted). The id lookup runs only when the capture switch is on and the order is in a withdrawal status (or already carries IMS's outcome markers), as one `$wpdb` row select (never `get_option`, so a miss adds no `notoptions` entry); the cleanup hook looks only at order post types and HPOS order deletion.
- **The withdrawal-outcome writer checks step M's own live-from directly** as well as the ownership-map hold, so it is held until step M whether or not the producer enforcement variable names woocommerce.
- **An invoice note queued while `wc_invoice_note_enabled` was on and sent after it was turned off** ends as SKIPPED: the sync row is retired (CANCELLED, claim-fenced) by the processor, so it is not re-claimed after the stale window, writes ONE `wc_invoice_note_skipped_switched_off` activity warning, and does not come back when the switch is turned on again.
- **Stock-drift:** an IMS push explains a change only when it was made after the previous look, and a reviewed acknowledgement exists: `npm run switchover:stock-drift-ack` (additive migration adds who, when and why to `wc_stock_drift_events`; an activity-log entry is written; the `STOCK_DRIFT` reader no longer counts acknowledged events).
- **`switchover:gaps` G_despatch** also lists SHIPPED orders with no `shippedAt` that were created before S, however long before the window, when they were touched inside it (bounded by the list limit).
- **Echo detection by content.** Where the order payload carries the plugin's done-marker meta, an event is an echo only when the newest marker is one IMS has an outcome row for and the time sits in that row's window; the time window over any row is only the fallback for a payload without the markers.
- **No second note or rejection** when a request id becomes known for a request already rejected under the unknown key in the same hold generation.
- **`switchover:gaps` G_despatch** no-shippedAt rows are also bounded by `updatedAt <= S` (a later sweep or erasure does not flood the list) and ordered NULLS FIRST, so a truncation never drops them.
