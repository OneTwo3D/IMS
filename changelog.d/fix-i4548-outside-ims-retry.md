### Owed first-seen despatch retry: real 14-day window, no churn, reopened orders unfenced (WooCommerce)
- The retry of a despatch owed for want of stock now backs off (15 minutes, 1 hour, 4 hours, then daily) and counts each real attempt exactly once, so the 14-day bound is actually reached (it gave up after about 7.5 hours, about 3.75 hours with partial stock). The help-docs now say what the code does.
- A retry with nothing changed in what allocation draws on (on-hand and reserved quantity per warehouse of every kit/BOM component of the order) is skipped: no reserve/release, no stock syncs, no activity rows. A real attempt is forced at least every 23 hours, and the comparison is kept only after a genuine stock shortfall. A failed or gone live read gets a next-check time too.
- When the store shows an owed order back in processing / on hold / pending payment, the retry no longer touches the "settled outside IMS" fence: the entry is parked (not terminal; re-read daily, so a store that completes it again resumes the owed retry, and a cancel closes it) under Sync > Exceptions as "store reopened - operator decision needed" (the goods may already have left; an on-hold can be a payment dispute). A new audited operator action, "Confirm IMS may fulfil" (confirm dialog, sync permission, fresh sign-in, live store re-read, audit with the user in the same transaction), is the only way the fence comes off. Cancelled and refunded orders close and stay fenced.
- First-load apply: the 45-day extract-age check is no longer applied to a verification-only resume of an APPLIED run or to the start of a resume once the cut-off is recorded (it is still applied just before the first opening-stock write of a resume that has opening-stock rows to load), and a refusal is reported under its own rail `stock-extract-age` instead of `data-classes`. The apply report format version is 3 (the readiness gate reports an older report as `format-version`).
- Additive migrations: a partial index on the open completion-refusal rows the retry scans, built CONCURRENTLY in its own migration (no write block), with a validity check migration (repair steps in docs/development.md).
- Documented limits: `stockExtractedAt` is operator-typed and cannot be cross-checked (the stock files carry no extract time); WooCommerce exposes no status-change time, so a custom shipped/delivered status with no completion date falls back to the paid date.
