### Warehouse order amendments are built from the SKU actually sent at create (fix)
- The SKU sent for each order line is now recorded on the warehouse push link when the order is created (new nullable `sent_line_skus` column, additive migration) and refreshed whenever a line amendment is accepted. Every amendment, and the check of a refused amendment against the warehouse's lines, is built from that record whatever `wms_sku_rename_remap_enabled` says at that moment. An order created as the old SKU while a rename was open is no longer swapped to the new SKU on a later change, and turning the switch off after on no longer makes orders created as the new SKU be amended with the old one (the item delete plus failed add that lost the goods line). The switch now only decides lines never sent before. Orders created before this release have no record and follow the switch as before (documented in help-docs/warehouse.md).
- The rename history used by the remap is now read across all warehouses of the product, so a warehouse binding added after a rename no longer loses it.
- With the switch off, the order read now carries an explicit empty remap, so a stale remap from the list read cannot survive a re-read in the same pass.
- A create parked after the claim because its payload no longer builds now writes the same audit event as the candidate-build park.
- A mixed-warehouse amendment now stamps the warehouse it was actually sent to (the ship-from when the push warehouse is unmapped).
