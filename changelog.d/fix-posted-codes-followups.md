### Fix: an update of a posted invoice keeps its posted tax codes; credit-note defaults per line kind; ambiguous posted codes refused (sales)
- Editing a posted invoice re-sent the tax rates' current codes after a remap, moving Xero's lines onto new codes. The SALES_INVOICE_UPDATE now keeps the posted code of every line whose VAT rate the posted record names, and of the discount's per-rate parts, the single discount line and shipping; a line at a rate the invoice never carried takes the current code. Shipping and the single discount line keep the posted code only while the order's default rate is still the one it was read from, so an edit that changes the order's VAT rate, or a WooCommerce zero-rated postage, is unchanged. A re-sent posted code is not bound to its rate (a rate a re-key cleared no longer blocks the edit). An update still pending lends its codes to the next edit. With no usable record (or a posted code the tenant archived, or a record naming no line rate) the update uses the current codes (as before) and, once queued, writes the order warning `sales_invoice_update_used_current_tax_codes`.
- A no-snapshot credit-note line takes its code per kind (shipping: the posted shipping code; discount: the posted header discount code; others: the current default) in the credit-note builder, the retry fence and the display.
- A VAT rate the posted record gives two different codes now refuses the update and any refund of those lines instead of falling back to the current code.
- Live path changed: the update of a posted invoice whose rate was remapped since posting now sends the posted code instead of the current one; with no remap, or no record, the payload is unchanged. After a tax re-key the retired-code guard still wins over a posted code (documented and pinned, unchanged).
