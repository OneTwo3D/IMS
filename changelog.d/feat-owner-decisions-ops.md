### Owner decisions: no-duplicate customer emails, soft refund delete, ghost payment assertion, refund adopts restocked return
- Customer emails (confirmation, invoice, dispatch, quotation) are now single-send: a lost final SMTP response ends the email FAILED with an operator warning that it "may not have been delivered", never a retry that could duplicate it.
- Refund delete (still OFF behind `refund_delete_enabled`) is now a soft delete: new nullable `deleted_at`, `deleted_by_id`, `delete_reason` columns on `sales_order_refunds`; readers skip deleted refunds, the tombstone keeps the lines, the Xero credit-note cascade is unchanged.
- An ADMIN can assert that a retired (unstamped CANCELLED) payment registration never existed in Xero: audit row (who, when, why) plus the pre-call stamp, which frees the receipt for deletion.
- With returns-in-transit ON, a refund adopts an already-restocked returns-inbox arrival for the same order and product (new table `sales_order_refund_inbox_adoptions`, one row per refund, arrival and quantity; an arrival an expectation already received, a legacy restocking refund covered or an earlier adoption consumed is not adopted again, and two racing refunds serialise on the order lock): no new expectation, stock-in or transit debit.
- Round-1 review fixes: the data reset and the Mintsoft e2e reset delete refund adoption rows first (a census test now fails when a new table with a restrict foreign key is not covered); adoption is sized from the units the refund would actually return (shipped, costed), not every refund line; an adopting refund books the COGS reversal and reclassifies the inbox restock's stock-gain credit (Dr reason account / Dr or Cr Inventory / Cr COGS), or reports it as an owed posting when the restock booked no journal; customer email kinds are never reclaimed after a stale claim (parked as outcome unknown) and every send has a 5-minute deadline under the 15-minute stale window; the unknown-outcome wording for a lost final reply is separate from the deadline wording; the refund-delete tombstone's line copy is classified as retained and the docs say the lines are copied into it.
- Round-2 review fixes: an adopting refund no longer posts any journal (the automatic reclass is removed); it raises ONE owed-posting record naming the refund, inbox rows, quantities and original cost, with the manual reclass (Dr the restock's reason account / Cr COGS, never Dr Inventory), marked ADVISORY for mixed or partly adopted rows; the original cost is keyed by product; deleting the refund closes that record. A customer email whose 5-minute deadline passes before the message was handed to the mail server (no DATA) is retried with backoff instead of parked as outcome unknown, and a stale row whose worker never entered the sender is requeued, not parked as "may have reached the recipient" (new nullable `email_outbox."sendEnteredAt"` column, stamped just before the send).
- Round-3 review fixes: a send deadline that passes before DATA now DESTROYS the mailer's own connection before the email is marked retryable (nodemailer's `transport.close()` does not stop a running send), so the old send cannot deliver a duplicate or outlive the purchase-order send lock; connect and greeting timeouts are half the deadline. A stale row that never reached the sender counts each requeue as an attempt and is parked with an operator notice at the last attempt. A new data-only migration (`20261119100000`) marks rows that were PROCESSING at the earlier migration as "may have sent". The adoption owed-posting record says plainly when no restock record exists for a row.
- Merge with development (nodemailer 10.6): the send deadline now aborts the send through an `AbortController` signal passed to `sendMail` (nodemailer closes the connection and refuses a late connect) instead of destroying a socket the mailer owned, which nodemailer never used; a deadline before DATA is retryable only after the abort, so the old send cannot deliver a duplicate. Tests run the real transport against the fake SMTP server.
- Round-4 review fixes: when the sent-status write fails after the mail sender reported delivery, the row is now settled as SENT (retried a few times) and never requeued, so a customer or purchase-order email is not sent twice; if the sender itself throws, the row ends FAILED with the outcome-unknown notice. The purchase-order send guard's backstop now aborts the mailer through a signal (including a send still reading the SMTP settings), so nothing is delivered after the send lock is released, and a send with a deadline sets `socketCloseTimeout: 0` so an abort destroys the socket.
