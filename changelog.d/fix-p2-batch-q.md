### Fulfilment: holds, returns of shipped goods, allocation release (sales / stock control)

- **Fixed: an On Hold order no longer fulfils.** Confirm allocations (Create Shipments) is refused on an On Hold order instead of silently moving it to Allocated (which lifted the hold, and left a withdrawal hold set on an order that no longer showed as held). In-app moves of its shipments through Picking and Packed are refused too. Warehouse progress reports are still recorded.
- **Fixed: returning units that already shipped no longer cancels the unshipped remainder of a part-shipped line.** Only units whose return movements have committed, and only up to the units that actually shipped, stop netting out of what is still to ship; one shared computation feeds the dispatch cap, the completion check, shipment building, allocation demand and the allocation sweep. Chargebacks, refunds awaiting an accounting retry, and refunds of unshipped or backordered units still net as cancellations. Returned units are credited to the refund line they came back for (never to another line of the same product), and a new warehouse order push sends the same netted quantity, so it never asks the warehouse to withhold units IMS still owes. An amendment of an order already pushed keeps the previous quantity (ordered minus the refund) for any line that has shipped, so the quantity sent to a live warehouse order never rises. Known limit, by design: units whose return has no committed movement yet (a return still in transit, or a movement removed by retention) net as a cancellation until it does.
- **Fixed: closing an order as Shipped, Completed or Delivered releases its unshipped allocation.** Previously the excess stayed reserved for ever. Best effort: a release that cannot be made does not block the status change.
- **Added (flag, off): releasing reserved stock for a stock removal.** With the setting `stock_adjustment_release_reserved` set to `true`, a single stock removal that cuts into reserved stock releases the newest orders' allocations in the same transaction, instead of being refused. A replayed submission (same idempotency token) returns the earlier result without releasing anything, including when two identical submissions arrive at the same moment (the key is claimed first under a lock). The previous post-commit release could never act, because the database never lets reserved exceed on-hand.
