### Refund delete: a void is closed as never sent only on Xero's word; give-up task, wait counter and notice fixes (#1136 review follow-ups) (accounting)

- **A refused void is checked against Xero before it is closed (MED-1).** When the refund delete is refused under the locks, the worker now always reads the credit note in Xero (bounded, read only) before it decides anything. The void row is closed CANCELLED as never sent only when Xero shows the credit note still standing and the row's own facts (the stamp marker under custody, no attempt stamp) say no attempt was sent. Before, the row's facts alone were enough, and a rollback or deploy-overlap build that claimed the row (re-asserting custody) and posted the void without stamping it left exactly those facts while Xero held the credit note voided. Xero showing it voided now raises the existing "voided in Xero, IMS refund still stands" task; a read that fails or runs out of budget closes nothing and hands the work back without spending a retry. `retireRefusedRefundDeleteVoid` itself refuses without a standing status. Must be in place before `refund_delete_enabled` is switched on.
- **No Xero read for a not-sent wait (LOW-1).** An attempt refused before its void (no time, a lock wait, the transport's refusal, the call budget, a 429) is a wait and no longer reads the credit note on every wait.
- **The give-up task is raised by the fenced failure write (LOW-2).** `REFUND_DELETE_VOID_STUCK` is raised inside `applyMainSyncFailureRetry`, in the same transaction as the write that made the row FAILED (the refund's order locked first), never from an unfenced read of the retry count. It is keyed per give-up (the attempt revision), so a later give-up after an operator's retry is told again once the earlier task is done; none is added while a stuck or voided-not-unwound task for the refund is open.
- **The wait cap counts since the last failure or retry (LOW-3).** Each wait's evidence row records the retry count it was taken at; the 96-wait cap counts the run at the row's current count.
- **Credit-note allocation behind a document delete (LOW-5).** One INFO evidence row for the first wait (not one every 15 minutes), and after 3 days of waiting the row fails for a person instead of waiting for ever.
- **A receipt held behind a document delete is a hold, not a refusal (LOW-6).** It is recorded as `invoice_payment_held_document_delete` (once per receipt), so the scheduled receipt sweep registers it once the delete has cleared; inline callers still read it as on record.
- **Removed `completeRefundDeletionAfterVoid` (LOW-12)**, which had no production caller and a transaction-path hazard.
