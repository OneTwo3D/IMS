### Order discount VAT per rate: the last review items before `sales_order_discount_tax_apportion_enabled` can be turned on (sales, Xero, refunds, reconciliation pack)

The accountant has approved the treatment. All of this applies only to orders priced with the switch on, and to the stored split (`sales_orders.discount_tax_split`) of an order that already carries one; the switch stays OFF and with it off every new order write and invoice payload is byte for byte what it was. "Unchanged with the switch off" holds only while no order carries a split: stage check `select count(*) from sales_orders where discount_tax_split is not null` (needs an owner-approved database read; not run here).

- A draft saved while its VAT rate had no accounting tax code is no longer refused at finalisation after the operator maps the rate. The code of each discount group is now read from its tax rate when the draft is finalised, in the finalisation check, in the invoice build and in the refund's per-rate discount reversal, so the three cannot disagree (the code stored in the split at save time is a snapshot and is no longer what is posted). The help text and the installation guide no longer say the draft has to be re-saved.
- Reconciliation pack R12: the IMS side now prices the discount lines of a split order the way Xero does, per order: entries merged by tax code, the invoice's own discount parts, VAT at 2 decimal places per part (out of the gross when the invoice is VAT-inclusive), put in base by the order's own rate. Before, it subtracted the 4 decimal place `taxBase` of each entry, so the difference to Xero added up per (country, category, month) key (about 75 or more split orders could pass the GBP 0.05 tolerance). The R12 text in the installation guide (generated from `lib/reconciliation-pack/constants.ts`) is corrected. A part with VAT on a rate R12 cannot place is still VAT_MAPPING_UNVERIFIED; a split whose parts do not add up to the discount is BAD_VALUE. A part that rounds to nothing once merged by code is skipped, as the invoice skips it.
- The explicit `NONE` accounting tax code is treated as no code (a discount part cannot be posted on it). The refusal is skipped while accounting sync is off, because no invoice is queued then. Its message now ends according to where it is shown (live save, finalisation), and the "out of step with its total" prefix is no longer put in front of it on an order edit or an exchange.
- The order default rate lookup is read once in the refund; the detached doc comment in `app/actions/sales.ts` is fixed.
- Tests: exact-text and per-guard assertions for the save and finalisation refusal, a DB test that saves a draft with an unmapped rate, maps it and finalises, a DB refund test of the order-default fallback and of a stale snapshot code, and R12 cases for VAT-inclusive, foreign-currency, merged-code, no-rate and 200-order-per-key estates.
- Not changed, documented in the installation guide: an exchange reaches only the backstop in the invoice build (its advice is to fix the rate mapping and retry), and the DB tests do not yet cover the invoice update, credit note, VAT report "No tax rate" row, CANCELLED and instant-boundary cases for split rows.
